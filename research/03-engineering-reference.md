# Building a Sub-20ms Game-Streaming / Remote-Desktop System (2025–2026): Component-by-Component Engineering Reference

> Research compiled 2026-08-03. Part 3 of the "build something better than Parsec" research series.

**Ground truth for the target:** Parsec advertises ~7 ms of added latency on wired LAN at 1080p60 ([parsec.app/technology](https://parsec.app/technology)); well-tuned Sunshine/Moonlight setups report single-digit-ms host processing on LAN ([LizardByte discussion #17](https://github.com/orgs/LizardByte/discussions/17)). Sub-20ms added is achievable, but only if every stage is event-driven and zero-copy. The design rule throughout: never wait for anything you don't have to (no vsync waits, no queues, no jitter buffer, no B-frames).

---

## 1. Screen Capture

### Windows: DXGI Desktop Duplication (DDA) vs Windows.Graphics.Capture (WGC)

**DDA** (`IDXGIOutput5::DuplicateOutput1` → `IDXGIOutputDuplication::AcquireNextFrame`) is still the lowest-latency full-display path. `AcquireNextFrame(timeout)` blocks until DWM produces a new desktop image, so you capture at native compositor cadence with no polling. You get a shared `ID3D11Texture2D` you can feed straight to the encoder (see §2 zero-copy). Key facts:

- **Dirty/move rects:** `GetFrameDirtyRects` / `GetFrameMoveRects` give changed regions — essential for remote-desktop-style bandwidth savings, less useful for full-frame game encoding.
- **Same-adapter restriction:** the duplicating D3D device must be on the GPU driving the output (a real problem on laptops with hybrid graphics) — WGC works cross-GPU with no user intervention ([OBS forum comparison](https://obsproject.com/forum/threads/windows-graphics-capture-vs-dxgi-desktop-duplication.149320/)).
- **HDR:** `DuplicateOutput1` with `DXGI_FORMAT_R16G16B16A16_FLOAT` yields scRGB FP16 frames on HDR desktops; you tone-map or convert to PQ/P010 yourself.
- **Protected content:** DRM-protected surfaces come back black; DDA cannot capture them (by design).
- **24H2 regression:** Windows 11 24H2 changed DDA internals to be heavily dependent on Multiplane Overlay (MPO) support, causing black captures/perf issues on some systems ([Lossless Scaling FAQ](https://sageinfinity.github.io/docs/FAQ/dxgiwgc), [MS Q&A report](https://learn.microsoft.com/en-us/answers/questions/2284634/did-something-change-in-server-2022-remoteapps-to)). Ship WGC as a fallback path.

**WGC** (`Windows.Graphics.Capture`, `Direct3D11CaptureFramePool`, [namespace docs](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture?view=winrt-26100)) adds per-window capture, cross-GPU operation, and proper HDR handling; overhead vs DDA is small but nonzero. Historically it lacked dirty rects; **Windows 11 24H2 added `DirtyRegionMode`**, letting consumers know which parts of the frame changed and skip unchanged frames — the reason Chromium moved its capture to WGC ([windowslatest](https://www.windowslatest.com/2025/04/19/microsoft-fixes-chromes-washed-out-dull-hdr-colours-on-windows-11-24h2/)). The yellow capture border is suppressible (`IsBorderRequired = false`) for apps with the `graphicsCaptureWithoutBorder` capability. WGC also respects `SetDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` and DRM exclusions — protected content is excluded, not black-boxed.

**Recommendation:** DDA primary (full-screen, lowest latency), WGC fallback/per-window, both delivering D3D11 textures into the same encode pipeline.

### macOS: ScreenCaptureKit

`SCStream` + `SCStreamConfiguration` (macOS 12.3+) is the only modern option (CGDisplayStream/AVCaptureScreen are legacy). It is GPU-backed with **zero-copy IOSurface-backed `CMSampleBuffer`s** you can hand directly to VideoToolbox; set `minimumFrameInterval` to native refresh and `queueDepth` small (3) for latency ([Apple docs](https://developer.apple.com/documentation/ScreenCaptureKit/capturing-screen-content-in-macos), [WWDC22 session](https://developer.apple.com/videos/play/wwdc2022/10156/)). It also captures **system audio** (48 kHz, macOS 13+). Frames arrive only when content changes — handle the "no new frame" case with your own keepalive timer. Permission: Screen Recording TCC prompt; **macOS 15 Sequoia re-prompts monthly and after reboots** ([SetMe docs](https://docs.set.me/permissions-on-mac/allow-accessibility-permissions-on-mac-instructions-for-expert)) — a real UX consideration for an always-on host.

### Linux

Three tiers, all used by Sunshine ([Sunshine capture implementations](https://deepwiki.com/LizardByte/Sunshine/5.3-platform-specific-capture-implementations)):

1. **KMS/DRM capture** (read the scanout framebuffer via DRM APIs, before/below the compositor): lowest latency, works headless, needs `cap_sys_admin`. Best choice for a dedicated streaming host.
2. **wlr-export-dmabuf / KWin direct screencast**: compositor-specific DMA-BUF export (wlroots: Sway/Hyprland; KDE added direct screencast support that Sunshine adopted in 2026 alongside PipeWire and Vulkan encoding — [GamingOnLinux, May 2026](https://www.gamingonlinux.com/2026/05/sunshine-game-streaming-tool-adds-vulkan-encoding-plus-xdg-pipewire-and-kwin-direct-screencast-capture/)).
3. **xdg-desktop-portal ScreenCast + PipeWire**: the universal Wayland path (GNOME/KDE/wlroots all support it); negotiate DMA-BUF (not SHM!) buffers for zero-copy into VAAPI/NVENC. The portal route (compositor → portal → consumer) adds a hop of latency vs KMS ([LizardByte discussion #402](https://github.com/orgs/LizardByte/discussions/402), [freedesktop screencasting talk](https://indico.freedesktop.org/event/10/contributions/405/attachments/250/337/Screencasting%20on%20Wayland.pdf)).
4. X11: XSHM/XComposite (CPU copies, high overhead) and **NvFBC** (NVIDIA Framebuffer Capture — excellent but officially restricted to professional GPUs; consumer use requires patches, and NVIDIA is steering people to PipeWire — an NvFBC PipeWire backend now exists for Wayland ([NVIDIA forum](https://forums.developer.nvidia.com/t/screen-capture-does-not-work-in-obs-studio-on-wayland/224353))). Treat X11 as legacy.

### Virtual displays (headless hosts)

- **Windows:** IddCx (Indirect Display Driver Class Extension) is the sanctioned way to create a monitor that doesn't exist. Study **[parsec-vdd](https://github.com/nomi-san/parsec-vdd)** (standalone use of Parsec's signed IddCx driver; up to 4K@240 Hz) and **[VirtualDrivers/Virtual-Display-Driver](https://github.com/VirtualDrivers/Virtual-Display-Driver)** (open-source IddCx, custom EDIDs/resolutions). **HDR on virtual displays requires Windows 11 24H2 + IddCx 1.10+**; [SudoVDA](https://github.com/SudoMaker/SudoVDA) does HDR + auto-resolution matching for Sunshine forks (Apollo uses it). Driver signing (WHQL/attestation) is your main productization cost here.
- **macOS:** no public API. The private **CGVirtualDisplay** API is what BetterDisplay and others use to create system-real virtual screens ([BetterDisplay](https://github.com/waydabber/betterdisplay), [example project](https://github.com/crazyathlete220-stack/oldmac-display)); it can break in any OS release. Fallback: HDMI dummy plug.
- **Linux:** headless is easy — KMS capture doesn't need a display at all; otherwise Xorg `dummy` driver, DRM `vkms`, or run games inside **gamescope** (a nested Wayland compositor) and capture its output.

## 2. Hardware Encoders

### NVENC — the reference low-latency configuration

From the [NVENC Programming Guide (Video Codec SDK 13.x)](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvenc-video-encoder-api-prog-guide/index.html):

- `tuningInfo = NV_ENC_TUNING_INFO_ULTRA_LOW_LATENCY`, preset P1–P4;
- **CBR** rate control with tight VBV (`vbvBufferSize` ≈ 1 frame's worth of bits) — this is what makes per-frame size predictable so a frame fits the network budget;
- **No B-frames** (`frameIntervalP = 1`), no lookahead, `enableOutputInVidmem`/async mode, one frame in flight;
- **Infinite GOP + intra-refresh** (`enableIntraRefresh`, `intraRefreshPeriod`, `intraRefreshCnt`): amortizes the I-frame bitrate spike into per-frame column stripes — smaller `intraRefreshCnt` recovers faster at slightly lower quality;
- **LTR + reference invalidation**: mark long-term references (`enableLTR`, `ltrNumFrames`), and when the client reports a lost frame, call `NvEncInvalidateRefFrames` so the next P-frame references only frames the client actually decoded — recovery without an IDR. NVIDIA recommends a large DPB so old valid references survive invalidation. This (Reference Frame Invalidation) is exactly what Moonlight/Sunshine and GeForce NOW use.
- **Zero-copy:** `NvEncRegisterResource` accepts the `ID3D11Texture2D` (or CUDA array/GL texture) from capture directly — the desktop image never leaves VRAM. Only caveat: NVENC **YUV444 is not exposed via D3D12**, use D3D11 or CUDA ([NVIDIA forum](https://forums.developer.nvidia.com/t/yuv44-hevc-encoding-in-d3d12/197834)).

Encode call latency in this mode is a few ms per 1080p frame (single-digit ms at 4K on Ada). A 2025 end-to-end measurement study ([arXiv 2511.18688](https://arxiv.org/html/2511.18688v2)) of full pipelines (capture→encode→decode→display at 60 fps) found: NVIDIA most consistent (~7 frames E2E across presets/codecs), Intel QSV lowest best-case (5 frames E2E for HEVC/AV1 in ultra-low-latency mode), AMD 6–9 frames and least sensitive to tuning; software encoders were 41–100 frames. Two takeaways: (a) ULL tuning matters, LL-vs-normal barely does; (b) quality preset barely affects latency, so don't run P1 out of fear.

### AMD AMF / Intel QuickSync / Apple VideoToolbox

- **AMF:** `AMF_VIDEO_ENCODER_USAGE_ULTRA_LOW_LATENCY`, B-frames off, CBR + low VBV; supports pre-analysis off for latency. Historically the weakest quality of the three on H.264; RDNA3+ AV1 is competitive. No 4:4:4 support.
- **QuickSync (via oneVPL/libvpl):** `TargetUsage=7` (speed), `AsyncDepth=1`, `LowPower=ON` (VDEnc fixed-function path), CBR/`LowDelayBRC`. Arc's AV1 encoder famously beat NVENC/AMF H.264 in quality-per-bitrate ([Tom's Hardware](https://www.tomshardware.com/news/intel-arc-av1-encoder-dominates-nvenc), [PCWorld deep-dive](https://www.pcworld.com/article/827992/tested-intel-arc-av1-video-encoder-vs-nvidia-amd.html)).
- **VideoToolbox:** create the session with `kVTVideoEncoderSpecification_EnableLowLatencyRateControl` ([Apple docs](https://developer.apple.com/documentation/videotoolbox/kvtvideoencoderspecification_enablelowlatencyratecontrol), [WWDC21 session](https://developer.apple.com/videos/play/wwdc2021/10158/)): hardware-only encode, no frame reordering (no B-frames), one-in-one-out, plus LL-specific features (temporal layers, max frame QP). Note LL rate control conflicts with CBR for H.264 and with VBR generally ([Apple forums](https://developer.apple.com/forums/thread/799459)) — you drive rate via average-bitrate + per-frame QP caps.

### Codec choice: H.264 vs HEVC vs AV1

- **Hardware AV1 encode:** RTX 40/50 (Ada/Blackwell), Intel Arc (Alchemist+, incl. Arc iGPUs in Meteor Lake+), AMD RX 7000 (RDNA3)+ ([PulseGeek AV1 matrix](https://pulsegeek.com/articles/compare-av1-support-across-gpus-for-streaming/)). At matched quality AV1 is ~40–50% smaller than H.264 and ~20–30% smaller than HEVC ([faceofit comparison](https://www.faceofit.com/av1-encoder-performance/)); latency of hardware AV1 encode is on par with HEVC on the same silicon ([arXiv 2511.18688](https://arxiv.org/html/2511.18688v2)).
- **Practical policy (what Sunshine/Moonlight do):** negotiate best common codec — AV1 > HEVC > H.264 — but note *decoder* availability on clients matters more than encoder (old phones/TVs lack AV1/HEVC decode). H.264 remains the universal fallback and has the widest 60fps+ decode support.
- **4:4:4 chroma (text sharpness for desktop use):** NVENC supports **HEVC 4:4:4** (and H.264 4:4:4) since Maxwell; **no vendor's hardware supports AV1 4:4:4** as of Blackwell — Blackwell added 4:2:2 and AV1-UHQ but not 4:4:4 ([NVENC Wikipedia matrix](https://en.wikipedia.org/wiki/Nvidia_NVENC), [Xpra issue #4612](https://github.com/Xpra-org/xpra/issues/4612), [LizardByte discussion #220](https://github.com/orgs/LizardByte/discussions/220)). Intel supports HEVC 4:4:4 (works with Sunshine's YUV444 mode on Arc — [moonlight-qt #1512](https://github.com/moonlight-stream/moonlight-qt/issues/1512)); AMD AMF does not. Client decode of HEVC 4:4:4 is the harder problem — Moonlight added it via Vulkan Video/libplacebo. Alternative used by remote-desktop products: encode 4:2:0 plus a second low-fps "text refinement" pass, or software-encode lossless regions.
- **10-bit/HDR:** pipeline = FP16 scRGB capture → GPU shader to BT.2020 PQ P010 → HEVC Main10 or AV1 10-bit + HDR10 static metadata. All three vendors support 10-bit HEVC/AV1 encode; H.264 10-bit hardware encode effectively doesn't exist. HDR needs the whole chain: 24H2 + IddCx 1.10 virtual display, WGC/DDA FP16 capture, Main10 encode, client HDR swapchain.

## 3. Transport

### Why not TCP

Head-of-line blocking: one lost segment stalls all data behind it for ≥1 RTT; congestion response (multiplicative decrease, retransmit timeouts) is catastrophic for a 16.7 ms frame cadence. Parsec's words: TCP "tends to freak out with loss"; they needed "the reliability of TCP with the latency of UDP" and built **BUD** ("Better User Datagrams") — UDP + DTLS 1.2, TCP-like reliability semantics *only where needed*, and a custom congestion controller that shares state bidirectionally with the encoder ("works hand-in-hand with our encoding and decoding modules in a way that using an off-the-shelf networking protocol could never do") ([Parsec protocol blog](https://parsec.app/blog/a-networking-protocol-built-for-the-lowest-latency-interactive-game-streaming-1fd5a03a6007), [parsec.app/technology](https://parsec.app/technology)). That coupling — CC signals directly setting next-frame encoder bitrate — is the single most important architectural decision; it's why off-the-shelf transports underperform here.

### The realistic options in 2025–2026

| Approach | Verdict for sub-20ms |
|---|---|
| **Custom UDP protocol** (Parsec BUD; Moonlight's GameStream-derived RTP-ish video + ENet control) | Best latency ceiling, full control of FEC/NACK/CC/encoder coupling. Most work. This is what the incumbents do. |
| **RTP/RTCP** (what Sunshine emits) | Fine as a wire format; you still write CC/FEC/NACK yourself. Gives interop with existing tooling. |
| **WebRTC** | Mandatory for a browser client; as a native transport it drags in ICE/DTLS/SRTP/SDP and a jitter-buffer-centric media stack. Parsec built a custom WebRTC-ish stack only for their web client ([Parsec web client blog](https://parsec.app/blog/game-streaming-tech-in-the-browser-with-parsec-5b70d0f359bc)). A 2025 study of remote-rendering found QUIC-based delivery ~30% better latency and ~60% faster connection setup than WebRTC ([arXiv 2505.22132](https://arxiv.org/abs/2505.22132)). |
| **QUIC / WebTransport** | QUIC gives you DTLS-grade crypto, connection migration, and **unreliable datagrams (RFC 9221)** ([datatracker](https://datatracker.ietf.org/doc/rfc9221/)). Pattern: datagrams for video/audio/input, one reliable stream for control. Or one QUIC stream per frame with `RESET_STREAM` on deadline miss. WebTransport exposes both to browsers. Very viable base in 2026; watch CPU cost of userspace QUIC at 100+ Mbps. |
| **MoQ (Media over QUIC)** | [draft-ietf-moq-transport-18](https://datatracker.ietf.org/doc/draft-ietf-moq-transport/) (May 2026), pub/sub over QUIC/WebTransport with relays; Cloudflare has relays in 330+ cities and 11 vendors demoed interop at NAB 2026 ([forasoft MoQ overview](https://www.forasoft.com/learn/video-streaming/articles-streaming/media-over-quic-moq)). It targets *sub-second at broadcast scale* — the relay/pub-sub model is aimed at distribution fan-out, not the 1:1 sub-20ms interactive loop. Use its ideas (priority, deadline-dropped subgroups), not the protocol, for a Parsec competitor — unless you want spectating/co-play fan-out, where it's genuinely interesting. |

### Syscall efficiency and pacing

Kernel bypass (DPDK) is unnecessary at game-streaming bitrates (10–100 Mbps). What matters:

- **`sendmmsg` + UDP GSO (`UDP_SEGMENT`)**: batch a frame's worth of packets in one syscall; Cloudflare drove a QUIC sender from 640 Mbps → 1.6 Gbps with sendmmsg+GSO ([perfplanet](https://calendar.perfplanet.com/2019/accelerating-udp-packet-transmission-for-quic/), [LPC paper](http://oldvger.kernel.org/lpc_net2018_talks/willemdebruijn-lpc2018-udpgso-paper-DRAFT-1.pdf)). Windows equivalent: `WSASendMsg` + `UDP_SEND_MSG_SIZE` segmentation offload.
- **Pacing:** a 100 KB 4K frame dumped as a line-rate burst overflows shallow router/Wi-Fi buffers and causes correlated loss. Pace packets across a few ms (a fraction of the frame interval) via a userspace token bucket or `SO_TXTIME`; note GSO trains conflict with per-packet pacing — send smaller GSO bursts with paced gaps ([LWN on GSO pacing](https://lwn.net/Articles/822726/), [QUIC pacing study](https://pure.mpg.de/rest/items/item_3655784/component/file_3655785/content)). Don't over-pace: spreading a frame across the whole 16 ms adds serialization latency; 2–5 ms per frame is the sweet spot.

## 4. Reliability and Rate Control

### FEC vs NACK

The decision variable is RTT vs frame interval ([U.Toronto low-latency error control paper](https://iqua.ece.toronto.edu/papers/semara-tmm21.pdf), [GetStream media resilience](https://getstream.io/resources/projects/webrtc/advanced/media-resilience/)):

- **NACK/selective retransmit** costs ~1 RTT per recovery. On LAN (RTT 1–5 ms) it's nearly free and strictly better than FEC (no bandwidth overhead). Over the internet at 30–70 ms RTT, a retransmitted slice arrives 2–4 frame intervals late — useless for the current frame.
- **FEC** recovers with zero feedback delay at a constant bandwidth tax (typ. 5–20%, adapted to measured loss). Schemes: XOR parity (cheap, 1-loss-per-block; FlexFEC-style), **Reed-Solomon** (MDS — optimal recovery for its overhead; Meta pairs RS with LTR for RTC resiliency ([atscale talk](https://atscaleconference.com/enhancing-video-network-resiliency-with-ltr-and-rs-code/))), **RaptorQ** ([RFC 6330](https://datatracker.ietf.org/doc/rfc6330/)) — fountain code, generate arbitrarily many repair symbols on the fly, best for large blocks/bursty loss, overkill per-frame. Moonlight/Sunshine ship per-frame RS-style parity shards; Parsec adapts bitrate + relies on invalidation.
- **The third tool — codec-level recovery:** LTR + reference-frame invalidation (§2) turns "frame lost" into "next frame references an older good frame" — one-frame glitch, no IDR spike, no retransmit wait. Combined policy that works: per-frame XOR/RS parity sized to recent loss, NACK only when RTT < ~1 frame interval, RFI as the backstop, intra-refresh instead of IDR for recovery floors.

### Congestion control

- **GCC/transport-cc** ([draft-ietf-rmcat-gcc](https://datatracker.ietf.org/doc/html/draft-ietf-rmcat-gcc-02)): delay-gradient estimator + loss estimator, target = min of both; feedback via transport-wide sequence numbers. Proven in WebRTC; sluggish (multi-second ramps) for game streaming defaults — retune filters for 100ms-scale reaction.
- **SCReAM** ([RFC 8298](https://datatracker.ietf.org/doc/rfc8298/), v2 with **L4S** support): self-clocked, window-based, designed exactly for low-latency interactive video; the L4S variant (ECN marking per [RFC 9330–9332](https://datatracker.ietf.org/doc/rfc9331/)) collapses queueing delay to near zero where the path supports it. NADA ([RFC 8698](https://datatracker.ietf.org/doc/rfc8698/)) is the other IETF option; both rare in browsers but fine to embed. The modern feedback format is CCFB [RFC 8888](https://datatracker.ietf.org/doc/rfc8888/), where 2026 momentum is ([forasoft WebRTC BWE overview](https://www.forasoft.com/learn/video-streaming/articles-streaming/webrtc-bandwidth-estimation)).
- **SQP** ([arXiv 2207.11857](https://arxiv.org/pdf/2207.11857)) is a purpose-built CC for interactive game streaming worth reading: it uses per-frame delivery timing to track bandwidth while keeping queues near-empty.
- **The integration rule:** CC output must set the encoder's *next-frame* bitrate/QP (per-frame rate adaptation), not a smoothed average — hardware encoders accept per-frame `NV_ENC_RECONFIGURE_PARAMS`/rate changes cheaply. Congestion response latency = 1 frame, not 1 GOP. This is Parsec's "protocol and encoder work hand-in-hand."

### Jitter buffer: don't

Parsec/Moonlight-class systems use **render-on-arrival**: decode the moment the last packet of a frame arrives, present immediately; late frames are dropped, never queued. Jitter shows up as micro-stutter instead of constant added delay. Moonlight added an *optional* minimum-latency buffer purely to improve frame pacing for users who prefer smoothness ([moonlight-qt PR #1139](https://github.com/moonlight-stream/moonlight-qt/pull/1139)) — the default remains zero-buffer. A VRR display largely dissolves the stutter penalty (§8).

## 5. NAT Traversal

- **Baseline stack:** ICE ([RFC 8445](https://datatracker.ietf.org/doc/rfc8445/)) + STUN + TURN ([RFC 8656](https://datatracker.ietf.org/doc/rfc8656/)). Hole punching succeeds for the large majority of consumer NAT pairs: Tailscale reports direct-connection rates "well north of 90%" ([NAT traversal improvements pt. 1](https://tailscale.com/blog/nat-traversal-improvements-pt-1)); Parsec claims 97% traversal / 95% of users able to P2P ([technology page](https://parsec.app/technology)).
- **Failure modes:** endpoint-dependent-mapping ("symmetric") NAT on both sides, CGNAT, and corporate firewalls. Mitigations: port-prediction/birthday-attack probing (Tailscale's approach), UPnP/NAT-PMP/PCP port mapping, and **IPv6** (no NAT at all — always attempt v6 candidate pairs first; a growing free win).
- **Relay fallback:** classic TURN, or the Tailscale **DERP** model — always start via the relay (instant connect), upgrade to direct UDP in parallel; relays forward end-to-end-encrypted bytes over HTTPS/443 so they pierce everything and never see plaintext ([Tailscale peer relays](https://www.sitepoint.com/tailscale-tailscale-peer-relays-nat-traversal-derp/), [pt. 3](https://tailscale.com/blog/nat-traversal-improvements-pt3-looking-ahead)). Cost model: relayed users burn your egress at full video bitrate (10–50 Mbps/user) — this is why every product pushes P2P hard, and why "relay only carries the 3–5%" is the economic linchpin. A legitimate 2026 shortcut is to *not build this at all* and require/bundle a WireGuard mesh (Tailscale/NetBird/headscale) under your UDP protocol — many Moonlight users already do exactly this.
- **Libraries:** [libjuice](https://github.com/paullouisageneau/libjuice) (tiny dependency-free C ICE-lite, single UDP component — what libdatachannel uses; ideal for this use case), [libnice](https://libnice.freedesktop.org/) (full ICE, GLib), [pion/webrtc](https://github.com/pion/webrtc) (Go), [str0m](https://github.com/algesten/str0m) / [webrtc-rs](https://github.com/webrtc-rs/webrtc) (Rust, §9).

## 6. Input

- **Client capture:** Windows Raw Input (`WM_INPUT`) for unaccelerated relative mouse deltas at device rate (1000–8000 Hz mice); browsers use Pointer Lock. Implement **relative mouse mode** as a first-class protocol mode (FPS games) alongside absolute mode (desktop use). Send input immediately on event (don't batch to frame ticks); coalesce only consecutive mouse deltas. Input packets are tiny — send them unreliable + duplicated or with immediate retransmit.
- **Host injection:**
  - **Windows:** `SendInput` with `MOUSEEVENTF_MOVE` (relative) / `MOUSEEVENTF_ABSOLUTE`, and scancode-based keyboard events (`KEYEVENTF_SCANCODE`). To inject on UAC/secure desktops and elevated apps the service must run as SYSTEM on the active session (this is why Parsec/Sunshine install a service). For sub-app-level injection some tools use the Interception kernel driver — avoid unless you need it.
  - **macOS:** `CGEventPost`/`CGEventTapCreate` — requires the Accessibility TCC permission; Sequoia tightened event-tap rules for background helpers and added recurring permission re-prompts ([Apple forums on Sequoia taps](https://developer.apple.com/forums/thread/758554), [Multi's remote-control engine writeup](https://multi.app/blog/building-a-macos-remote-control-engine) is the best practical reference).
  - **Linux:** `uinput` — create virtual keyboard/mouse/gamepad evdev devices from userspace; works identically under X11 and Wayland and needs only write access to `/dev/uinput`.
- **Virtual gamepad:** this is a genuine 2025–2026 pain point on Windows. **ViGEmBus was archived Nov 2023** (trademark conflict) with no maintained successor; it still works but Sunshine has an open issue to migrate off it, and Nefarius's "VirtualPad" replacement remains in development ([Sunshine issue #3527](https://github.com/LizardByte/Sunshine/issues/3527), [nefarius/ViGEmBus](https://github.com/nefarius/ViGEmBus)). Parsec ships its own signed **VUSB** driver. Realistic options: fork/re-sign ViGEmBus, write your own KMDF virtual Xbox360/DS4 bus driver, or license VirtualPad when it lands. On Linux uinput handles pads natively; on macOS there's no sanctioned virtual gamepad path (DriverKit HID is the frontier).
- **Keyboard layouts:** transmit HID scancodes/usages, never translated characters; apply the *client's* layout on the host or offer both modes — plus a separate "text injection" path (clipboard-style) for IME/Unicode. Clipboard sync and drag-drop ride the reliable control channel.
- **Budget:** client event→packet <1 ms; network (same as video); injection <1 ms; the game samples input on its next frame. The input path is cheap — the video path back is where the milliseconds live.

## 7. Audio

- **Capture:** Windows **WASAPI loopback** (shared-mode render endpoint capture; event-driven, ~10 ms default period, `IAudioClient3` supports 2.67 ms periods on modern drivers — [MS low-latency audio docs](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/low-latency-audio)); macOS **ScreenCaptureKit audio** (48 kHz, same stream as video); Linux **PipeWire** (capture a sink monitor with small quantum).
- **Encode:** **Opus** ([RFC 6716](https://datatracker.ietf.org/doc/rfc6716/)) at 5–10 ms frames, CELT/restricted-low-delay path: algorithmic delay drops from the 26.5 ms default to as low as 5 ms ([Consilient overview](https://www.consilient-tech.com/opus-interactive-audio-codec), [Opus low-delay paper](https://www.researchgate.net/publication/286609722_High-Quality_Low-Delay_Music_Coding_in_the_Opus_Codec)). 96–160 kbps stereo is transparent for game audio; enable in-band FEC + PLC for loss.
- **Sync:** run audio as an **independent stream** — do not delay video to sync with audio. At these latencies A/V skew is bounded by the pipeline itself (≤20–30 ms), below perceptibility thresholds. Keep a 1–2 frame client audio ring buffer (audio dropouts are far more objectionable than a repeated video frame).

## 8. Client Rendering

- **Decode:** D3D11VA/DXVA2 (Windows), NVDEC, VideoToolbox, VAAPI or Vulkan Video (Linux). Configure for low latency: no reorder buffering (streams with no B-frames signal `max_num_reorder_frames=0`), 1-in-1-out, and on Android set the low-latency MediaCodec flag — some SoC decoders otherwise buffer 2–4 frames. Hardware decode of 1080p on a desktop GPU is 1–3 ms; enable it always ([Moonlight FAQ](https://github.com/moonlight-stream/moonlight-docs/wiki/Frequently-Asked-Questions)).
- **Zero-copy render:** decode straight to GPU surfaces (D3D11 NV12 texture / `CVPixelBuffer`/IOSurface / VAAPI-DMABUF→Vulkan image) and sample directly in the present pass. Moonlight-qt is the reference implementation (D3D11VA renderer; libplacebo/Vulkan for HEVC 4:4:4 and HDR tone mapping).
- **Present:** flip-model swapchain (`DXGI_SWAP_EFFECT_FLIP_DISCARD` + `ALLOW_TEARING` for immediate present) or Vulkan `IMMEDIATE`/`MAILBOX`. Policy: **VRR display → present on arrival** (G-Sync/FreeSync absorbs the irregular cadence; the streamed frame cadence becomes the display cadence — the single biggest smoothness win); fixed refresh → choose tearing-with-minimum-latency or vsync-paced (up to +1 refresh) and expose the choice, as Moonlight does with its frame-pacing option ([PR #1139 discussion](https://github.com/moonlight-stream/moonlight-qt/pull/1139)).
- **Measuring:** hardware click-to-photon via NVIDIA **LDAT** or open clones ([Open-Source-LDAT (Teensy)](https://github.com/S4N-T0S/Open-Source-LDAT), [OpenLDAT paper](https://sid.onlinelibrary.wiley.com/doi/10.1002/jsid.1104), [LDAT methodology at TFTCentral](https://tftcentral.co.uk/articles/nvidia_reflex), [GO-EUC's LDAT-for-remote-desktop series](https://www.go-euc.com/measuring-input-latency-in-virtual-desktops-introduction-and-baselines-of-the-nvidia-ldat-research/)). In software: stamp every frame at capture with host clock, sync clocks (NTP-style handshake in-protocol), and log per-stage timestamps (capture→encode-done→first/last-packet→decode-start/done→present) — exactly the stats Moonlight's overlay exposes (decode time, render time, host processing latency, jitter).

## 9. Language/Stack Choices and Codebases to Study

**C/C++ remains the incumbent** (every OS/GPU/codec API is C): [Sunshine](https://github.com/LizardByte/Sunshine) (C++; direct NVENC/AMF/QSV/VideoToolbox integration, per-platform capture, RTP + ENet control — the single best open reference for the host side), [moonlight-qt](https://github.com/moonlight-stream/moonlight-qt) + moonlight-common-c (the client side: protocol, RFI, FEC, zero-copy renderers), Parsec SDK (closed but its C API shows the shape), OBS's libobs (battle-tested capture code for every OS), [libdatachannel](https://github.com/paullouisageneau/libdatachannel) ecosystem (C++ WebRTC data channels/media over libjuice), GStreamer (`webrtcbin`, `nvh264enc`, appsink pipelines — used by Selkies and Wolf for containerized cloud gaming), FFmpeg's hwcontext APIs.

**Rust is now a fully viable choice** and where most new 2025–2026 projects land: **RustDesk** (the proof — a complete production remote desktop in Rust), [windows-capture](https://github.com/NiiightmareXD/windows-capture) (WGC bindings, actively maintained), [screencapturekit-rs](https://github.com/svtlabs/screencapturekit-rs), [scap](https://github.com/CapSoftware/scap) (cross-platform capture; maintenance has stalled — check before adopting), pipewire-rs, [quinn](https://github.com/quinn-rs/quinn) (QUIC with datagram support), **[str0m](https://github.com/algesten/str0m)** — a sans-I/O WebRTC implementation born from the observation that [webrtc-rs](https://github.com/webrtc-rs/webrtc)'s async-callback port of Pion "requires locks and prevents idiomatic &mut" and is a very heavy dependency ([libp2p's migration issue #3659](https://github.com/libp2p/rust-libp2p/issues/3659)); sans-I/O means you own the UDP socket and event loop — exactly right for a latency-critical engine. Also: ffmpeg-next / nvidia-video-codec-sdk FFI for encoders, cudarc, wgpu for the client renderer, and kixelated's moq-rs if you explore MoQ. Sensible split: Rust core + thin C FFI to vendor encoder SDKs.

## 10. Latency Budget

Added latency only (excludes the game's own render latency and the display panel's response). "LAN" = wired GbE, desktop GPU both ends, 1080p–1440p @ 60–120 fps, tuned as per this document.

| Stage | Tuned LAN | Internet (same metro, good ISP) | Notes |
|---|---|---|---|
| Capture (event-driven, on compositor flip) | 0.5–3 ms | same | DDA/SCK/KMS deliver on flip; polling or portal paths add up to a frame |
| Color convert (RGB→NV12/P010 shader) | 0.1–0.5 ms | same | GPU compute pass, same VRAM |
| Encode (NVENC/QSV ULL, no B-frames) | 1–4 ms (1080p) / 3–8 ms (4K) | same | CBR + tight VBV; per [arXiv 2511.18688](https://arxiv.org/html/2511.18688v2) ULL tuning is what matters |
| Packetize + FEC + DTLS/QUIC seal | 0.2–0.5 ms | same | sendmmsg/GSO batched |
| Network (serialize + propagate + pace) | 0.5–3 ms | 8–30 ms | Frame paced over 2–5 ms; Wi-Fi adds 2–10 ms jitter; Parsec assumes <50 ms ping is workable |
| Depacketize + decode (hw) | 1–3 ms | same | Render-on-arrival, zero jitter buffer; +2–5 ms on mobile SoCs |
| Render + present | 0.5–2 ms (VRR/immediate) | same | +up to 1 refresh (8–16 ms) if vsync-paced on fixed-refresh |
| **Total added** | **~4–15 ms** | **~15–45 ms** | Matches Parsec's measured ~7 ms LAN claim ([technology page](https://parsec.app/technology)) |

An *untuned* pipeline (vsync-paced capture, default encoder preset, buffered decode, vsync present) easily lands at 40–70 ms added — e.g., the "typical" breakdown circulating in streaming guides (encode 15 / network 25 / decode 8 / display 10 ms, [Joltfly](https://joltfly.com/optimize-moonlight-game-streaming-for-ultra-low-latency/)) — which is precisely the gap this document's settings close. Budget discipline: every stage must be event-driven off the previous stage's completion; any stage that waits for a clock tick costs half that clock period on average.
