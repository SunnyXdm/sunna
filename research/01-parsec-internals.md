# How Parsec Works Internally

> Research compiled 2026-08-03. Part 1 of the "build something better than Parsec" research series.

## 1. Overview, History, and Business Context

- Parsec was founded in **2016** by CEO **Benjy Boxer** and CTO **Chris Dickson** in New York, originally as a consumer cloud-gaming tool (streaming games from AWS GPU instances — the founders were inspired by a Hacker News article about playing games on an AWS GPU instance) ([Parsec tech blog](https://parsec.app/blog/description-of-parsec-technology-b2738dcc3842), [AlleyWatch](https://www.alleywatch.com/2021/08/parsec-remote-working-gaming-collaboration-team-unity-technologies-3d-acquired/)).
- It pivoted from "cloud gaming rig rental" plumbing (the AWS/Paperspace provisioning integration was later discontinued) toward peer-to-peer game streaming and co-play ("Party Finder"/Arcade), then toward remote work for creatives. The **Arcade** co-play lobby system was shut down in **2023** ([Wikipedia](https://en.wikipedia.org/wiki/Parsec_(software))).
- Raised ~**$33M** total (last round Dec 2020); **Unity announced acquisition Aug 2021 for $320M cash**, completed September 2021 for total consideration of ~$333M ([Unity press release](https://unity.com/news/unity-enters-agreement-acquire-parsec), [Unity 10-Q via AlleyWatch/PocketGamer](https://www.pocketgamer.biz/news/77033/unity-picks-up-remote-working-and-streaming-firm-parsec-for-320-million/)).
- Product tiers: free consumer app; **Warp** (prosumer: 4:4:4 color, virtual displays, pen/tablet); **Teams/Enterprise** (SAML 2.0 SSO, SCIM provisioning, RBAC/admin roles, App Rules, group-based access, self-hosted High Performance Relay, SOC 2 Type 2 certification verified by Coalfire) ([parsec.app/security](https://parsec.app/security), [Teams SSO docs](https://support.parsec.app/hc/en-us/articles/32381486765588-Integrating-your-SAML-Identity-Provider), [SCIM docs](https://support.parsec.app/hc/en-us/articles/32381156284052-SCIM-Provisioning)). 2018: partnered with HP for "OMEN Game Stream" ([Wikipedia](https://en.wikipedia.org/wiki/Parsec_(software))).
- The client stack is written in **cross-platform C** ("native code implementation for performance control") ([parsec.app/technology](https://parsec.app/technology)). Their open-source cross-platform application layer is **libmatoya** (C, MIT — window/input/rendering/crypto/HTTP abstraction, originally by CTO Chris Dickson) at [github.com/parsec-cloud/libmatoya](https://github.com/parsec-cloud/libmatoya).

## 2. Architecture: Client/Host Model, Brokering, Authentication

Parsec is a **client ("guest") / host** system with a central backend used only for control-plane work; media flows peer-to-peer:

- **Backend API** ("Kessel", `kessel-api.parsecgaming.com`): account auth, session brokering, peer identity. The SDK required a `sessionID` + `peerID` "obtained through the Parsec API to identify users and make secure connections"; endpoints include `/v1/auth/` and `/auth/sessions` ([SDK docs/forks](https://github.com/MalfoyJW/parsec-sdk), [ParsecSoda source](https://github.com/FlavioFS/ParsecSoda/blob/master/ParsecSoda/ParsecSession.h)). All backend traffic is **TCP 443 (TLS)**; a WebSocket channel is used for signaling (the SDK error space includes a full `WS_ERR_*` range) ([Parsec Connectivity Requirements](https://support.parsec.app/hc/en-us/articles/32381460716180-Parsec-Connectivity-Requirements), [parsec.h](https://github.com/MalfoyJW/parsec-sdk/blob/master/sdk/parsec.h)).
- **STUN servers** (UDP **3478**) for reflexive-address discovery; Parsec even open-sourced a minimal Go STUN server at [github.com/parsec-cloud/go-stun](https://github.com/parsec-cloud) ([Connectivity Requirements](https://support.parsec.app/hc/en-us/articles/32381460716180-Parsec-Connectivity-Requirements)).
- **Media plane**: direct UDP peer-to-peer between client and host. Parsec states flatly: "All connections traveling through Parsec are peer-to-peer. They never transit Parsec's infrastructure … all data is transferred directly peer-to-peer, or optionally through a self-hosted relay server" ([parsec.app/security](https://parsec.app/security)).
- **Authentication/encryption**: account login (email/password + optional MFA; SSO enforcement for Teams). Streams are encrypted with **DTLS 1.2 (via OpenSSL)**; marketing/security pages state "DTLS 1.2 with AES128 or AES256 cipher enabled on every single packet" and "peer-to-peer sessions are encrypted using 128-bit AES-GCM" with a shared per-session AES key ([BUD blog](https://parsec.app/blog/a-networking-protocol-built-for-the-lowest-latency-interactive-game-streaming-1fd5a03a6007), [technology page](https://parsec.app/technology), [security page](https://parsec.app/security)). The SDK's error codes expose the underlying primitives: `AES_GCM_ERR_*`, `DTLS_ERR_*`, `STUN_ERR_*`, `SCTP_ERR_*`, `OPENSSL_ERR` ([parsec.h](https://github.com/MalfoyJW/parsec-sdk/blob/master/sdk/parsec.h)).
- **Permissions model**: desktop hosting adds an approval step; "Approved Apps" can restrict guests to specific applications; hosts can enable "exclusive input" (block remote input while local input is active — a `ParsecHostConfig` field) ([security page](https://parsec.app/security), [parsec.h](https://github.com/MalfoyJW/parsec-sdk/blob/master/sdk/parsec.h)).

## 3. The BUD Protocol ("Better User Datagrams")

Primary source: ["A Networking Protocol Built For Low Latency Interactive Game Streaming"](https://parsec.app/blog/a-networking-protocol-built-for-the-lowest-latency-interactive-game-streaming-1fd5a03a6007) (Nov 2017).

- **Origin**: Parsec launched on **TCP**, found it unusable ("TCP tends to freak out with loss"), evaluated WebRTC and raw UDP, and concluded "nothing could achieve the reliability of TCP with the latency of UDP for interactive game streaming." Raw UDP without reliability made "the screen … look like a tie-dye shirt." The changelog dates the switch: **12/29/2016 — "New low latency UDP protocol w/ dynamic bandwidth adjustment"** ([changelog](https://s3.amazonaws.com/parseccloud/changelog.txt)).
- **Design**: UDP + **DTLS 1.2 (OpenSSL)**, adding "your basic reliability semantics like TCP, but with a highly tuned and custom congestion control algorithm." Explicit priority order: **latency > frame rate > video quality**.
- **Loss handling**: BUD's stated mechanism is TCP-style reliability (i.e., ack/retransmission semantics) rather than forward error correction — no Parsec primary source describes FEC. The differentiator is cross-layer integration: "Our networking protocol works hand-in-hand with our encoding and decoding modules in a way that using an off-the-shelf networking protocol could never do" — i.e., on loss/congestion the encoder's bitrate and frame production are adjusted immediately rather than buffering.
- **Congestion control**: predictive rather than reactive — "we basically have to detect a congestion event before it starts. That means reading the tea leaves of all of our networking metrics, crunching numbers really fast, and making a split micro-second decision," aiming to "saturate that 12 Mb/s connection right at the edge without introducing loss or latency." If the network degrades badly, the stream shows a "network is bad, please hang tight" state and suspends after ~60 seconds. A major "BUD congestion control revision" for high-bitrate/high-latency links shipped **5/24/2021** ([changelog](https://s3.amazonaws.com/parseccloud/changelog.txt)).
- **Tuning assumptions** (2017): <50 ms ping, ~30 Mb/s bandwidth, with adaptive behavior added later.
- **vs WebRTC**: Parsec's web client uses WebRTC **data channels** ("all an RTCDataChannel is is UDP wrapped in an SCTP stream wrapped in DTLS") but the native protocol avoids SCTP; they made **"BUD's current NAT traversal ICE compatible"** so the same host can accept both BUD and browser DTLS/SCTP connections without bundling libwebrtc. They considered compiling BUD to WebAssembly but kept the browser path standard ([browser tech blog](https://parsec.app/blog/game-streaming-tech-in-the-browser-with-parsec-5b70d0f359bc)). The SDK exposes both as `PROTO_MODE_BUD` and `PROTO_MODE_SCTP` ([parsec.h](https://github.com/MalfoyJW/parsec-sdk/blob/master/sdk/parsec.h)).
- Claimed results: "97% NAT traversal success rate and lightning fast adjustment to packet loss and congestion," optimized "based on data gathered over a three year period" ([technology page](https://parsec.app/technology)).

## 4. Video Pipeline

Primary source: ["The Technology Behind A Low Latency Cloud Gaming Service"](https://parsec.app/blog/description-of-parsec-technology-b2738dcc3842).

- **Capture (Windows)**: **DXGI Desktop Duplication API** (Windows 8.1+) — "essentially gives you a direct framebuffer grab and places the frame in video memory." macOS hosting (preview 8/24/2021, H.265 host encode added 1/19/2022) uses Apple's stack ([changelog](https://s3.amazonaws.com/parseccloud/changelog.txt)).
- **Zero-copy GPU pipeline**: "Parsec is designed from that point onward to never let the raw frame touch system memory" — capture → color conversion → encode all stay in VRAM; on the client, decode → render happens without CPU-side copies. RGBA→NV12/YUV conversion is done with **GPU pixel shaders** (DirectX/OpenGL). Marketing calls this a "zero-copy GPU pipeline to the encoder" ([technology page](https://parsec.app/technology)).
- **Hardware-only codec policy**: "only support hardware enabled video encoding and decoding," calling vendor SDKs directly (NVIDIA NVENC/CUVID from 10/2016, Intel QuickSync 2/2017, AMD (AMF) 3/2017, macOS VideoToolbox 6/2018) "with no wrapper layers." Result: "total encode/decode latencies lower than 10 ms" ([tech blog](https://parsec.app/blog/description-of-parsec-technology-b2738dcc3842), [changelog](https://s3.amazonaws.com/parseccloud/changelog.txt)).
- **Codecs**: **H.264** is the default/baseline; **H.265/HEVC** optional (experimental for Maxwell+ NVIDIA on Windows since 6/1/2018; a host config flag `encoderH265` exists in the SDK). **No AV1 support** appears anywhere in the changelog or docs as of this research. ([changelog](https://s3.amazonaws.com/parseccloud/changelog.txt), [parsec.h](https://github.com/MalfoyJW/parsec-sdk/blob/master/sdk/parsec.h))
- **Chroma / color accuracy**: default stream is **4:2:0**. "Prefer 4:4:4 color" is a **Teams/Warp** feature for design/animation/text work (launched for Teams 6/25/2020; Intel 11th-gen and NVIDIA Turing/Ampere encode support added 8/24/2021). 4:4:4 at H.265 "requires an NVIDIA or Intel GPU with hardware encoding support … the host must be a Windows machine" ([support: Hardware and Software Compatibility](https://support.parsec.app/hc/en-us/articles/32381568346644-Hardware-and-Software-Compatibility), [changelog](https://s3.amazonaws.com/parseccloud/changelog.txt)). The SDK's `ParsecColorFormat` enum shows the internal surface formats: NV12/I420 (4:2:0), NV16/I422 (4:2:2), BGRA/RGBA ([parsec.h](https://github.com/MalfoyJW/parsec-sdk/blob/master/sdk/parsec.h)).
- **Client frame pacing / vsync**: V-sync enabled by default; DirectX **flip-sequential swap effect** presentation; when the host FPS exceeds the client refresh rate, accumulated frames are **dropped** rather than queued (latest-frame-wins, no buffering) ([tech blog](https://parsec.app/blog/description-of-parsec-technology-b2738dcc3842)).
- **Virtual displays**: Parsec ships a signed **Virtual Display Driver (VDD)** (IddCx-based) — introduced 12/17/2020, up to **3 virtual monitors** since 8/24/2021, bundled into the main installer 4/25/2022. It's proprietary but famously repurposed standalone by the reverse-engineered [nomi-san/parsec-vdd](https://github.com/nomi-san/parsec-vdd) project ([changelog](https://s3.amazonaws.com/parseccloud/changelog.txt)).

## 5. Input Handling

- **Client capture**: native clients read raw OS input (via libmatoya's input layer); the web client uses browser `mousemove`/`keydown` listeners, the **Gamepad API (polled)**, Pointer Lock for relative-mouse games, and fullscreen to unlock Pointer Lock restrictions. The host tracks cursor state ("sends cursor messages to the client whenever there is a cursor state change") so the client knows when to switch between absolute and relative (captured) mouse modes ([browser tech blog](https://parsec.app/blog/game-streaming-tech-in-the-browser-with-parsec-5b70d0f359bc)).
- **Wire format**: the SDK message types are `MESSAGE_KEYBOARD`, `MESSAGE_MOUSE_BUTTON`, `MESSAGE_MOUSE_WHEEL`, `MESSAGE_MOUSE_MOTION` (absolute or relative), `MESSAGE_GAMEPAD_BUTTON` (15 buttons), `MESSAGE_GAMEPAD_AXIS` (6 axes), `MESSAGE_GAMEPAD_UNPLUG` — tiny messages sent over the same low-latency BUD channel ([parsec.h](https://github.com/MalfoyJW/parsec-sdk/blob/master/sdk/parsec.h)).
- **Host injection — gamepads**: history runs **ScpVBus (10/2016) → ViGEmBus → Parsec's own kernel driver**. Today the host uses the proprietary **Parsec Virtual USB Driver (PVUD / "VUSB")**, a kernel-mode driver creating a **virtual USB host controller** (`Root\Parsec\VUSBA`, Windows 10+) into which the host "plugs" emulated USB devices so they appear as real hardware. Reverse-engineered docs ([nomi-san/parsec-vusb](https://github.com/nomi-san/parsec-vusb)) show 8 ports: **Xbox 360 (XInput)**, **DualSense/PS5** (isochronous endpoints), **virtual microphone** (USB audio), **dummy HID mouse** (keeps cursor visible), **Wacom Intuos Pro M digitizer** (pen/tablet support), **DualShock 4**, and **YubiKey USB passthrough** (real device captured client-side via LibUSB, full descriptor forwarded). Control is via `DeviceIoControl` IOCTLs (version handshake `0x2A6404`, device-create-with-descriptor `0x2AE804`, plug/unplug, 13-byte-header read/write transfers), with hardcoded VIDs (Microsoft `045E`, Sony `054C`, Wacom `056A`). When PVUD is absent, Parsec **falls back to ViGEmBus** (Xbox 360/DS4 only; DualSense degrades to DS4).
  - Note: Parsec's gamepad driver is **not** open source on github.com/parsec-cloud — the org's public repos are only libmatoya, go-stun, the (archived) cloud Preparation Tool, GPU updater, and an SNES script; the original `parsec-cloud/parsec-sdk` repo now 404s (removed post-Unity; community forks like [MalfoyJW/parsec-sdk](https://github.com/MalfoyJW/parsec-sdk) preserve it). The VUSB knowledge comes from third-party reverse engineering.
- **DualSense support** shipped 12/17/2020 (Windows & macOS clients); rumble/haptics pass back through the same virtual device ([changelog](https://s3.amazonaws.com/parseccloud/changelog.txt)).
- **Latency**: input rides the unbuffered UDP channel; Parsec measured their **protocol adding ~7 ms** click-to-photon on LAN (see §9).

## 6. Audio

- **Codec: Opus**, encoded on the host and shipped as "raw encoded Opus" in **20 ms frames at 48 kHz**; SDK audio callbacks deliver "16-bit signed, two channel, 48KHz PCM" ([browser tech blog](https://parsec.app/blog/game-streaming-tech-in-the-browser-with-parsec-5b70d0f359bc), [parsec.h](https://github.com/MalfoyJW/parsec-sdk/blob/master/sdk/parsec.h)).
- **Sync/buffering strategy**: no A/V mux and no timestamp-based lipsync buffer — audio is played out as it arrives "with care taken to ensure proper timing and prevent overbuffering" (web client: WASM-compiled Opus decoder → Web Audio API). Video is always latest-frame-wins, so both streams independently run at minimal delay ([browser tech blog](https://parsec.app/blog/game-streaming-tech-in-the-browser-with-parsec-5b70d0f359bc)).
- Client→host **microphone** forwarding exists via the VUSB virtual USB audio device ([nomi-san/parsec-vusb](https://github.com/nomi-san/parsec-vusb)); microphone passthrough shipped Oct 2023 (Windows hosts only).

## 7. Networking: NAT Traversal, Ports, Relays

- **Hole punching**: classic STUN-based UDP hole punching ("the peer-to-peer connection … boils down to a STUN ping/pong as part of the UDP hole punching procedure"), plus "a few more native tricks … more aggressive hole punching, optional client side UPnP" in BUD; UPnP is on by default (`upnp: 1` in `ParsecConfig`). Claimed **97% NAT traversal success**; "95% of our users successfully co-play together" ([browser tech blog](https://parsec.app/blog/game-streaming-tech-in-the-browser-with-parsec-5b70d0f359bc), [parsec.h](https://github.com/MalfoyJW/parsec-sdk/blob/master/sdk/parsec.h), [technology page](https://parsec.app/technology)).
- **Ports**: TCP **443** for all backend traffic; UDP **3478** for STUN; P2P media on configurable UDP ranges — defaults start at **UDP 8000**, and the guidance is "allow UDP ports 8000–8011 outbound"; a host with start port 8000 needs **8000–8002 forwarded** (up to ~3 sequential ports per host; the SDK tries successive ports up to 50 times). SSL inspection must be disabled for `*.parsec.app` domains ([Connectivity Requirements](https://support.parsec.app/hc/en-us/articles/32381460716180-Parsec-Connectivity-Requirements), [port forward guide](https://support.parsec.app/hc/en-us/articles/32381279119252-How-to-port-forward-Parsec), [parsec.h](https://github.com/MalfoyJW/parsec-sdk/blob/master/sdk/parsec.h)).
- **Relays**: Parsec runs **no TURN-style media relay** for consumers — if hole punching fails (symmetric NAT + blocked UDP), the connection errors out (error 6013 "UDP blocked by your network," 6023/6024 negotiation failures). Teams Enterprise offers the **High Performance Relay (HPR)** — a lightweight, *customer-hosted* relay that funnels "many concurrent Parsec sessions through a single IP address/port," removing dependence on UPnP/firewall rules for LAN or WAN deployments; it stays "under [the customer's] control" ([HPR docs](https://support.parsec.app/hc/en-us/sections/32361195067028-High-Performance-Relay-HPR-Server), [error 6013](https://support.parsec.app/hc/en-us/articles/32381914838804-Error-Codes-6013-UDP-Blocked-By-Your-Network)).
- **Web client**: WebRTC data channels (DTLS/SCTP) with ICE, interoperating with the same host because BUD's traversal was made ICE-compatible ([browser tech blog](https://parsec.app/blog/game-streaming-tech-in-the-browser-with-parsec-5b70d0f359bc)).

## 8. The Parsec SDK

Originally at `github.com/parsec-cloud/parsec-sdk` (now removed; forks and the [npm package](https://www.npmjs.com/package/parsec-sdk) survive). "Low latency, peer-to-peer, interactive game streaming" — a **single header (`parsec.h`) + shared library <5 MB** ([fork README](https://github.com/MalfoyJW/parsec-sdk)).

- **ParsecClient**: connect to a host, send keyboard/mouse/gamepad input, receive video/audio; `ParsecClientGLRender` renders decoded frames straight from the decoder; config selects `PROTO_MODE_BUD` vs `PROTO_MODE_SCTP` and `CONTAINER_PARSEC` (native) vs `CONTAINER_MP4` (for browser MSE) — direct confirmation that the host can package the same H.264 stream two ways.
- **ParsecHost, two modes**: **game mode** (app submits frames/audio via `ParsecHostSubmitFrame`/`SubmitAudio` and polls input via `ParsecHostPollInput`; sandboxed — "Parsec can only interact with your game and has no access to the OS"; can run headless) and **desktop mode** (full desktop capture with approval flow; Windows-only). Host config exposes `encoderFPS`, `encoderMaxBitrate` (default **10 Mbps**, split between guests), `encoderH265`, `maxGuests` (default 20), `exclusiveInput`, `adminMute`.
- Also shipped: **ParsecUnity** module (pre-acquisition Unity integration), a **Web Client SDK** (wraps everything around a `<video>` element), and examples including a NES emulator, mobile (iOS/Android) clients, and a cross-platform desktop client.
- Auth uses `sessionID`/`peerID` from the Parsec API; the personal `/v1/auth` flow was prohibited for redistribution (OAuth-style delegation for third parties, separate enterprise path).
- The header leaks pipeline internals via error namespaces: D3D/OpenGL renderer errors, encoder session errors (`ENCODE_ERR_*` −15000s), decoder errors, `SERVER_ERR_DISPLAY/RESOLUTION/MAX_RESOLUTION`, STUN/DTLS/SCTP/AES-GCM transport errors ([parsec.h](https://github.com/MalfoyJW/parsec-sdk/blob/master/sdk/parsec.h)).

## 9. Performance Numbers

- **Protocol overhead**: Parsec's own DIY test (Sony RX100 IV at 1000 fps + Makey Makey with LED synced to mouse input): local click-to-photon 16 ms, through Parsec on LAN 23 ms → **~7 ms added by the whole capture-encode-transmit-decode-render loop**; the [technology page](https://parsec.app/technology) repeats "on a LAN ethernet connection, Parsec adds only 7 milliseconds" ([DIY latency blog](https://parsec.app/blog/testing-game-streaming-input-latency-on-parsec-with-diy-instructions-49ae838f45a7)).
- **Codec latency**: "total encode/decode latencies lower than 10 ms" via direct vendor hardware APIs ([tech blog](https://parsec.app/blog/description-of-parsec-technology-b2738dcc3842)).
- **Targets**: 60 FPS standard (client `refreshRate` default 60; higher refresh supported later); design point "20 ms total latency vs. 40 ms … the difference between awesome and unplayable"; network sweet spot <20 ms ping, ≥10 Mb/s; BUD tuned for <50 ms ping / 30 Mb/s; default host bitrate cap 10 Mbps (configurable) ([tech blog](https://parsec.app/blog/description-of-parsec-technology-b2738dcc3842), [BUD blog](https://parsec.app/blog/a-networking-protocol-built-for-the-lowest-latency-interactive-game-streaming-1fd5a03a6007), [parsec.h](https://github.com/MalfoyJW/parsec-sdk/blob/master/sdk/parsec.h)).
- **How "sub-frame" is achieved**: zero buffering anywhere — no jitter buffer, latest-frame-wins with frame dropping, hardware encode/decode <10 ms combined, GPU-resident frames, predictive congestion control that avoids queue buildup, and unbuffered input on the same channel. At 60 fps (16.7 ms/frame), the 7 ms added LAN latency is genuinely sub-frame.

## 11. Notable Cross-Cutting Observations

- Parsec's core bet was **vertical integration**: custom transport + direct vendor encoder APIs + zero-copy GPU path + kernel input drivers, versus assembling WebRTC/FFmpeg/RTP components. Every layer (BUD ↔ encoder feedback, VUSB device realism, MSE low-delay hack) reflects that.
- The native client binary was **under 6 MB** partly from *not* bundling WebRTC ([browser tech blog](https://parsec.app/blog/game-streaming-tech-in-the-browser-with-parsec-5b70d0f359bc)).
- Post-Unity, public engineering artifacts contracted (SDK repo removed, repos archived); the richest current documentation of internals is the reverse-engineering work (parsec-vdd, parsec-vusb) and preserved SDK forks.
