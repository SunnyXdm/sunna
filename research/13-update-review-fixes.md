# 13 · Self-update: review findings to fix before the first release

Status: work brief, 2026-11-18. An independent review of the install and self-update work (design in `12-install-and-update.md`, implementer's account in `docs/update-verification.md`) found the signature and hash checks sound and in the right order, and found the problems below. Everything here is to be fixed, with a test that fails before the fix and passes after, unless marked otherwise. Severity is the reviewer's; the order within each section is the order to work in.

## A. A host must never be left down (the reason this system exists)

1. **High. A new version that hangs before listening, or exits 0 early, is never rolled back.** `crates/update/src/bin/sunna-update.rs:56` waits forever on a hung child; if the child exits 0 the supervisor exits 0 and `Restart=on-failure` (`scripts/sunna-host:172`) leaves the host down. Reproduced by the reviewer with shell-script children: `early-success` gave exit 0 with `current` still on the new version; `hang` was still waiting. Fix: the child signals readiness (listening, on the version the supervisor selected); a start deadline; any exit before readiness, with any status, counts as a failed start. The unit should also restart on any exit.
2. **High. An interrupted switch can stop even the old version from starting.** The unpacked version directory and the rename into `versions/` aren't synced before the activation journal is committed (`crates/update/src/lib.rs:527`, `:558`). After power loss the journal can name a version that isn't on disk, and recovery exits without trying the old one although `current` still points at it. A corrupt or truncated state file aborts startup too (`:368`). Both reproduced (`missing-stage`, `corrupt-state`). Fix: fsync files, the version tree and the containing directories before journaling; validate the journal against versions that actually run; fall back to the last known good pointer; version the state format; treat an unreadable or newer-format state file as "no state" (keep a copy aside), never as fatal.
3. **High. A failed commit can strand a running host on the wrong side of `current`.** If the flip succeeds and saving state fails (disk full), the old daemon keeps running while `current` names the candidate; remote management then refuses it (`crates/host/src/lib.rs:524`) and later attempts act on stale state (`crates/update/src/lib.rs:568`, `crates/update/src/host.rs:49`). Fix: reconcile any outstanding transaction before another prepare or switch; on a failed commit restore the old pointer or hand recovery to the supervisor at once.
4. **High. The desktop app's restart depends on the new version's launcher.** Pre-flight checks only the app executable (`crates/update/src/lib.rs:502`); `apps/sunna/src/update.rs:107` flips `current` and then relies on the candidate's helper. An archive with a working app and a missing or broken helper leaves the app unable to start. Fix: pre-flight the whole launch path of the candidate; have the already-running supervisor restart the child.
5. **Medium. Health is marked for a release that can't share a screen, and missed for one that can.** Ten seconds of answering probes says nothing about capture or input (`crates/update/src/host.rs:11`, `crates/host/src/lib.rs:601`); and an overlapping `--check` holding `update.lock` makes the one-shot health write fail silently, so later restarts roll back a good build (`apps/sunna/src/update.rs:143` has the same shape). Fix: tie health to the child and the selected version; before marking a host healthy, bring up the configured capture and input backends once (without a viewer) and require that to succeed; retry transient failures of the health write.
6. **Medium. Update requests can be lost or outlive what they asked for.** The worker deletes `requested` before a long download (`crates/update/src/host.rs:27`); a crash after a committed rollback leaves `rollback-requested` behind, which then fails every later tick (`crates/update/src/lib.rs:589`). Fix: persist request and result with the transaction; consume requests idempotently.
7. **Medium. Migrating an old install leaves the old daemon running.** The installer reports success while the September-era process still serves; it can't be updated remotely. Fix: detect a running old service, restart it through the migrated entry point when the installer is told to (and say exactly what to run when it isn't), and verify the old unit starts through the new layout before claiming remote updates work.
8. Also from the earlier hand review: **a host's background download or verification error must be reported back** to a viewer that asks for status (today the app can only say "Still waiting…"); and the desktop app's `auto` policy must differ from `notify` (auto: a staged update is switched to at the next launch without asking; notify: wait for "Restart to update"). The app's UI currently offers only Daily / Never because the two behaved alike: once they differ, the UI choice becomes Automatically / Ask first / Never.

## B. Only signed releases, the newest ones, from where we said

1. **High. The updater trusts files it has already verified.** With `SUNNA_UPDATE_ROOT` or `XDG_DATA_HOME` somewhere another account can write, the cached archive can be swapped between hashing and unpacking, staged files replaced before pre-flight, installed files changed before launch; predictable `.part` and `.new` names follow symlinks (`crates/update/src/lib.rs:70`, `:238`, `:483`). Fix: refuse a root (or any ancestor) writable by another user; private 0700 staging; exclusive, no-follow opens; unpack from the same file handle that was hashed.
2. **Medium. Plain HTTP is accepted in production.** `SUNNA_UPDATE_URL` may be `http://`, and the HTTPS check is on the signed URL string, before redirects are followed (`crates/update/src/lib.rs:84`, `:126`; `scripts/release/install.sh.in:15`). Fix: HTTPS only, including every redirect hop, in production builds and in the bootstrap's curl (`--proto '=https' --proto-redir '=https'`); loopback HTTP only with the test feature.
3. **Medium. Replay after a rollback.** Having run 1.3.0 and rolled back to 1.1.0, a stale mirror can serve a validly signed 1.2.0 as an upgrade; fresh installs have no floor; migrated binaries are all `0.0.0+legacy` (`crates/update/src/lib.rs:465`, `:589`, `:701`). Fix: persist the highest version ever accepted, separately from `current`; an explicit rollback is the only way below it; seed migration from the old binary's real version when it can report one.
4. **Medium. Unpacking has gaps.** No limit on the number of entries (inode exhaustion); tar long-name and PAX metadata are read before the per-entry accounting; the ZIP loop budgets declared sizes, not bytes written (`crates/update/src/lib.rs:252`). Fix: entry-count cap; bound the decompressed tar stream including metadata; count actual ZIP output.
5. **Medium. Android hands the APK to an implicit intent** (`apps/android/.../Updates.kt:61`): another app that handles APK `ACTION_VIEW` can receive it or imitate the installer. Fix: a `PackageInstaller` session with the system's own confirmation.
6. **Medium. Android can install a different release from the one shown.** The prompt shows one manifest; the download fetches `latest` again; the unknown-apps permission flow resumes from a fixed cache name and a Boolean, even after Cancel (`Updates.kt:23`, `crates/android/src/lib.rs:779`). Fix: bind consent to a manifest version and digest; a per-artifact file; clear pending consent on cancel.
7. **Publication checks.** `test-key` can be compiled into a release-profile build. Add to the release pipeline: the signing key matches `crates/update/release.pub`; every shipped updater binary rejects a manifest signed with the test key.

## C. The release pipeline

1. **High. Signing trusts mutable CI inputs and an unchecked set of files.** Actions are referenced by tag, not commit; the publish job signs whatever matches filename prefixes; `scripts/release/manifest.py:6` interpolates helper-derived filenames into the installer's `case` without validating them (`.github/workflows/release.yml:1`, `:59`). Fix: pin every action by full commit SHA; validate an exact per-job inventory (names, count) before signing or generating installers; validate target names against a fixed allow-list in `manifest.py`; the signing job (and Android signing) runs in a protected environment with required approval; least-privilege `permissions:` per job.
2. **Medium. Tag and versions can disagree.** Linux restamps its snapshot, macOS and Android build the checkout as is (`release.yml:8`, `scripts/release/build-linux.sh:13`, `scripts/release/version.py:5`). Fix: fail before building unless the tag, the workspace version, the Tauri version, and Android `versionName`/`versionCode` agree.
3. **Medium. `minimum_protocol` does nothing** (`crates/update/src/lib.rs:31`, `:558`; `crates/host/src/lib.rs:557`). Define it as the lowest peer protocol the release can talk to, and enforce it: a host asked to update by a viewer whose protocol is below it refuses with "update the app first"; the app warns before sending the request.

## D. Smaller things

1. **Medium. The probe can misread a current host as pre-updater.** `ProbeAck.busy` and the viewer record are sampled separately, so `UpdateInfo` can arrive where the client expects `InUse`; optional reads reuse a framed receiver after a timeout though its receive is documented cancellation-unsafe (`crates/host/src/lib.rs:485`, `crates/client/src/lib.rs:335`, `crates/transport/src/lib.rs:343`). Fix: one bounded read loop for the optional tail, dispatch by variant, never reuse the stream after a timed-out read. Old hosts and old apps must still work both ways (protocol 8, positional postcard).
2. **Medium. Bootstrap from a `noexec` /tmp fails** after verifying (`scripts/release/install.sh.in:13`): use a private directory under the install filesystem, or diagnose and offer a way to choose. Print the full path of what was installed when `~/.local/bin` isn't on `PATH` (`crates/update/src/bin/sunna-update.rs:28`).
3. **Medium. Bootstrap and helper can pick different releases.** The script is pinned to the release that served it; the helper then asks `latest` (`install.sh.in:14`, `install.ps1.in:4`, `crates/update/src/lib.rs:84`). Pass the pinned feed for the install only.
4. **Low.** A saved check time in the future suppresses daily checks until the clock catches up (host, desktop, Android): treat it as due; use monotonic time within a process. `curl … | sh` succeeds on an empty download: document a download-then-run form joined by `&&` for automation. The PowerShell entry point must state the same first-install trust as the shell one; the Android guide must say that the first sideload fixes the signer the device will trust.
5. **Docs.** `docs/update-verification.md` and `docs/app-mac.md` still say the desktop update controls are separate work; they exist (`apps/sunna/ui/updates.js`). Qualify the rollback and HTTPS claims to what is now true.

## Not in this work (recorded so nobody thinks it was missed)

- **A viewer does not verify a host's identity** (self-signed certificates, `docs/security.md`). The review rates this high for remote management: on a network with someone in the middle, the reusable host key can be captured during a probe, and with it a session, an update request or a policy change. Release signature checks still hold, so it can't install anything unsigned. This predates updating and needs its own design (pin each host's certificate, carried in the `sunna://` link and QR code so even the first connection is verified). It is the next piece of work after this one, and public downloads should not be recommended before it.

## Proving it

- Every High and Medium item gets an automated test (unit, or a fixture run of the real `sunna-update` binary) that demonstrates the fault on the code as it is now and passes after the fix. Keep the reviewer's five fixtures (`nonzero`, `early-success`, `hang`, `corrupt-state`, `missing-stage`) as permanent tests, and add: disk-full during commit, power-loss ordering (simulate by replaying the filesystem states between each step), symlinked `.part`, world-writable root, HTTP redirect, replay after rollback, entry-count bomb, probe race, future clock.
- Then run the whole existing proof again from scratch (`scripts/release/prove-update.py`, `scripts/release/prove-linux.sh` on the five distributions, the old/new compatibility run, the Android build and tests), plus a real systemd user service in a container that has one (systemd-in-Docker is fine), including killing the daemon and the supervisor at each stage of a switch.
- The desktop app's checks in `apps/sunna/dev/verify-updates*.mjs` must still pass, updated for the Automatically / Ask first / Never choice.
- Update `docs/update-verification.md` to the new truth: what each test showed, with commands, and what is still unverified.
