## Findings that change the comparison

1. Sunshine's media sender has packet pacing, but its pacing target is approximately **800 Mbit/s**, not a measured bottleneck capacity. The examined loss-statistics callback only logs. Its normal video FEC is a configured **20% parity/data ratio**, not a network-adaptive controller. This is a concrete opportunity on variable internet paths, not evidence that QUIC alone is faster. [Sunshine/src/stream.cpp:1177–1191,1598–1628,1657–1674,1770–1821](/home/sunny/research-repos/Sunshine/src/stream.cpp:1177); [Sunshine/src/config.cpp:814–823](/home/sunny/research-repos/Sunshine/src/config.cpp:814).
2. Sunshine's macOS capture here is **AVCaptureScreenInput**, not ScreenCaptureKit. It nevertheless has a retained CVPixelBuffer → FFmpeg VideoToolbox surface path; calling all Sunshine Mac capture a CPU-copy pipeline would be wrong. [Sunshine/src/platform/macos/av_video.m:10–41,59–90](/home/sunny/research-repos/Sunshine/src/platform/macos/av_video.m:10); [Sunshine/src/platform/macos/nv12_zero_device.cpp:38–68](/home/sunny/research-repos/Sunshine/src/platform/macos/nv12_zero_device.cpp:38).
3. “Moonlight uses Metal on Mac” is version/build dependent. This checkout prefers **libplacebo over MoltenVK** when compiled in, while retaining direct Metal and AVSampleBufferDisplayLayer choices. [moonlight-qt/app/streaming/video/ffmpeg.cpp:1008–1022](/home/sunny/research-repos/moonlight-qt/app/streaming/video/ffmpeg.cpp:1008). Presentation, not simply decode duration, is decisive.
4. **Reference invalidation is not equivalent to an acknowledged long-term reference protocol.** Sunshine's direct NVENC path retains a larger DPB, uses one L0 reference per picture, and invalidates a lost range only while an older usable reference survives. The common-C client now has LTR acknowledgments, but that does not establish that every compatible server implements them. [Sunshine/src/nvenc/nvenc_base.cpp:286–300,795–829](/home/sunny/research-repos/Sunshine/src/nvenc/nvenc_base.cpp:286); [moonlight-common-c/src/Video.h:72–86](/home/sunny/research-repos/moonlight-common-c/src/Video.h:72).
5. Wolf and Moonshine demonstrate that **owning a compositor** changes isolation, resolution control, capture timing, and input routing together. Neither is a general replacement for capturing an already running macOS/Windows desktop. Wolf defaults are NV12/SDR and explicitly disable HDR; Moonshine has a separate HDR-capable Vulkan pipeline. [wolf/src/moonlight-server/state/configTOML.cpp:191,301–322](/home/sunny/research-repos/wolf/src/moonlight-server/state/configTOML.cpp:191); [wolf/src/moonlight-server/state/default/config.include.toml:335–370](/home/sunny/research-repos/wolf/src/moonlight-server/state/default/config.include.toml:335); [moonshine/README.md:9–25](/home/sunny/research-repos/moonshine/README.md:9).

## 1. Sunshine

### 1.1 End-to-end pipeline and latency-bearing boundaries

Logical flow:

```text
paired HTTPS launch → RTSP/SDP negotiation → per-client stream session
  shared display capture → latest-image event → client encoder → encoded packet queue
  → video broadcast worker → frame/header construction → RS blocks → optional AES-GCM → UDP
  audio capture → PCM queue → Opus worker → audio broadcast worker → UDP
  ENet control receive → decrypt → input queue/task pool → OS input devices
```

The shared asynchronous capture object owns a `jthread`, pending capture contexts, and the display reference; each client has an encode session. An alternate synchronous multi-client path does capture/convert/encode on the capture thread for backends that cannot run concurrently. The `PARALLEL_ENCODING` flag determines this architectural split; “async encoder” and “async capture” are separate properties. [Sunshine/src/video.cpp:413–423,627–710,1553–1583,1697–1725,2685–2865,2875–2990](/home/sunny/research-repos/Sunshine/src/video.cpp:413).

Captured images are delivered through an event that replaces the previous value under a mutex, rather than an unlimited raw-frame FIFO. This is the right place to shed stale work: before encoding and therefore before a new reference dependency exists. By contrast the generic packet queue defaults to 32 elements; on overflow its default policy clears the queue and accepts the new item. This caps memory, **not necessarily frame age**, and dropping already encoded pictures invokes downstream recovery. Capture runs at critical priority, encode/sender at high priority. [Sunshine/src/video.cpp:1708–1714,2438–2506,2882–2893,2904–2905](/home/sunny/research-repos/Sunshine/src/video.cpp:1708); [Sunshine/src/thread_safe.h:24–49,391–440](/home/sunny/research-repos/Sunshine/src/thread_safe.h:24); [Sunshine/src/video.h:118–120](/home/sunny/research-repos/Sunshine/src/video.h:118).

The encoder loop drains reference-invalidation events, services an IDR request, waits for an image, converts, encodes, then resets normal-frame state. Static scenes are not silent: default minimum FPS is half the requested FPS, unless configured otherwise, explicitly to refine static image quality. Thus at 60 FPS the normal minimum target is approximately 30 FPS; a timeout re-encodes the previous surface without a fresh capture timestamp. This helps a lossy interframe codec converge but is not pixel-exact build-to-lossless. [Sunshine/src/video.cpp:2434–2506](/home/sunny/research-repos/Sunshine/src/video.cpp:2434).

Network, audio and control are separate workers, but the video broadcast worker is shared and processes packet work serially across sessions. Encoder output is a completed access unit before packetization/FEC; configured slices do **not** establish slice-by-slice capture-to-wire transmission. Latency accumulates at compositor/capture availability, GPU conversion, encode completion, encoded-queue residence, FEC generation, pacing/OS send, client reassembly/decode and presentation. [Sunshine/src/stream.cpp:471–498,1523–1548,1555–1603,1679–1704](/home/sunny/research-repos/Sunshine/src/stream.cpp:471); [Sunshine/src/video.cpp:1826–1945](/home/sunny/research-repos/Sunshine/src/video.cpp:1826).

Host processing latency is measured from the optional capture timestamp to construction of the short video frame header, in 0.1 ms units, saturated to 16 bits. It excludes subsequent FEC/send/network/client work. When capture has no timestamp, the field is zero and not a measurement. [Sunshine/src/stream.cpp:1575–1596](/home/sunny/research-repos/Sunshine/src/stream.cpp:1575). A generic “host latency” comparison must respect this boundary.

### 1.4 Wire, FEC, pacing, adaptation and encryption

GameStream compatibility has several planes: HTTP discovery/pairing and HTTPS authenticated app control, RTSP over TCP with SDP-like negotiated attributes, ENet UDP control/input, and distinct video/audio UDP sockets. New encrypted RTSP is an AES-GCM message envelope, not ordinary RTSPS. Supported/requested media encryption is negotiated in RTSP. [Sunshine/src/nvhttp.cpp:64–136,476–517](/home/sunny/research-repos/Sunshine/src/nvhttp.cpp:64); [Sunshine/src/rtsp.cpp:206–264,823–856,930–949,1132–1206](/home/sunny/research-repos/Sunshine/src/rtsp.cpp:206); [Sunshine/src/stream.cpp:1958–1964](/home/sunny/research-repos/Sunshine/src/stream.cpp:1958).

Video is RTP-like, not ordinary standards-compliant RTP/H.264 packetization. There is the 12-byte RTP header plus extension space (maximum 16 total), a packed 16-byte NVIDIA video header, then parts of a short per-frame header/access unit. NV header fields: stream packet index (32-bit), frame index (32-bit), flags, extra flags, multi-FEC flags/block descriptor, and FEC info (32-bit). RTP sequence/timestamp are network-endian; NV fields use the protocol's little-endian layout. Flags are picture data=1, EOF=2, SOF=4. [moonlight-common-c/src/Video.h:10–48](/home/sunny/research-repos/moonlight-common-c/src/Video.h:10); [Sunshine/src/stream.cpp:137–164,1575–1603,1682–1746](/home/sunny/research-repos/Sunshine/src/stream.cpp:137).

`fecInfo = (shard_index << 12) | (data_shards << 22) | (percentage << 4)`. Multi-FEC block index is bits 4–5, last block index bits 6–7; maximum four blocks/frame. Video RTP clock is **90 kHz**, sourced from capture time when available. Short frame types distinguish normal P (1), IDR (2), and post-RFI (5); final payload length removes padded ambiguity. [Sunshine/src/stream.cpp:1575–1583,1685–1697,1722–1746](/home/sunny/research-repos/Sunshine/src/stream.cpp:1575).

RS is systematic data+parity over equal padded shards. Parity is `ceil(data_shards * F / 100)`; negotiated minimum parity can increase effective F for small frames. At F=20 this is ~20 parity per 100 data, i.e. parity is ~16.7% of transmitted packets, **not** a guarantee against arbitrary 20% total loss. Maximum total shards/block is 255; sender computes maximum data as `floor(25500/(100+F))`. If a frame requires >4 blocks, this implementation disables FEC for that enormous frame. This failure mode is particularly relevant to oversized IDRs. [Sunshine/src/stream.cpp:845–913,1607–1628](/home/sunny/research-repos/Sunshine/src/stream.cpp:845).

Adaptation is limited to frame geometry/minimum parity, not measured path conditions. The normal FEC percentage is configuration. `IDX_LOSS_STATS` logs only. No video packet retransmission cache/NACK repair or live encoder bitrate feedback loop was found in the examined sender/control/encode paths. This negative claim is scoped to these implementations, not all GameStream-compatible forks. [Sunshine/src/stream.cpp:1177–1209,1546–1840](/home/sunny/research-repos/Sunshine/src/stream.cpp:1177); [Sunshine/src/video.cpp:2438–2506](/home/sunny/research-repos/Sunshine/src/video.cpp:2438).

Packet pacing uses an ~800 Mbit/s budget in 1 ms units; batches are under 64 KiB and no more than 64 packets (Linux GSO limit). It carries debt into the next frame; each FEC block is computed before its shards are sent. It prevents instantaneous line-rate megabursts but does not pace a 50 Mbit/s stream evenly at 50 Mbit/s or infer a 20 Mbit/s internet bottleneck. A common global video sender also means a slow send/pacing interval can affect other sessions. [Sunshine/src/stream.cpp:1657–1674,1701–1704,1769–1821](/home/sunny/research-repos/Sunshine/src/stream.cpp:1657).

RTSP initially budgets below the client-selected bitrate: for F≤80 it scales by `(100−F)/100`, subtracts an audio allowance (capped at 20%), and additional overhead. This is static budgeting, not congestion control. [Sunshine/src/rtsp.cpp:1253–1276](/home/sunny/research-repos/Sunshine/src/rtsp.cpp:1253). Encoder CBR also is not congestion control: it constrains output against a target, not the bottleneck's changing capacity.

Encryption: control v2 is requested whenever supported; encrypted-control mode rejects plaintext controls. Video optionally AES-128-GCM encrypts **each FEC shard after FEC**, with a 32-byte prefix (12-byte IV, frame number, 16-byte tag). A 64-bit packet invocation counter and fixed video discriminator avoid nonce reuse within a session/key. Audio uses AES-CBC with padding and IV based on audio key ID+sequence, then audio FEC protects the encrypted bytes. Do not call CBC audio authenticated AEAD. Default policy here is LAN **never** for optional media encryption, WAN **opportunistic**, with mandatory available; control protection is distinct. [Sunshine/src/stream.cpp:352–359,583–617,732–734,1748–1767,1882–1889](/home/sunny/research-repos/Sunshine/src/stream.cpp:352); [Sunshine/src/config.cpp:819–823](/home/sunny/research-repos/Sunshine/src/config.cpp:819); [Sunshine/src/rtsp.cpp:930–949,1293–1297](/home/sunny/research-repos/Sunshine/src/rtsp.cpp:930).

### 1.6 Audio

Sunshine captures PCM separately from video, with high/critical worker priorities and a **30-buffer** PCM queue. A separate Opus thread sends to the audio sender. Opus uses **48 kHz**, multistream layouts, `OPUS_APPLICATION_RESTRICTED_LOWDELAY`, CBR (`OPUS_SET_VBR(0)`), negotiated packet duration. Presets: stereo 96/512 kbit/s; 5.1 256/1536 kbit/s; 7.1 450/2048 kbit/s (normal/high quality). High-quality surround uses uncoupled channels. [Sunshine/src/audio.cpp:44–150,222–272](/home/sunny/research-repos/Sunshine/src/audio.cpp:44).

Audio RTP data payload type 97; parity type is defined by common-C as 127. Four data packets then **two RS parity packets**, fixed 50% parity/data overhead, using the compatibility parity matrix `77 40 38 0e c7 a7 0d 6c`. Data transmits immediately; parity follows the fourth data packet. Recovery of an early missing packet therefore can wait for later audio packets even without an RTT. Audio timestamp increments by packet duration in **milliseconds**, unlike video 90 kHz. There is no Opus in-band FEC configuration in this encode loop; packet-level RS and decoder PLC are different mechanisms. [Sunshine/src/stream.cpp:1850–1944](/home/sunny/research-repos/Sunshine/src/stream.cpp:1850); [moonlight-common-c/src/RtpAudioQueue.h:7–24](/home/sunny/research-repos/moonlight-common-c/src/RtpAudioQueue.h:7); [moonlight-common-c/src/RtpAudioQueue.c:20–21](/home/sunny/research-repos/moonlight-common-c/src/RtpAudioQueue.c:20).

## 2. Moonlight common-C and Qt client

### 2.1 Reassembly and loss recovery

`moonlight-common-c` owns network/protocol, FEC queues and decoder callbacks; Qt/SDL/FFmpeg implement desktop decode, presentation, audio and input. Common-C's decode-unit queue is bounded at **15** and the Qt FFmpeg client requests the **pull renderer** model, with its own decoder thread. That bound is a failure ceiling, not an intended 15-frame jitter buffer. Overflow flushes/recovery can occur if decode/presentation stops draining. [moonlight-common-c/src/VideoDepacketizer.c:63–80,470–545](/home/sunny/research-repos/moonlight-common-c/src/VideoDepacketizer.c:63); [moonlight-qt/app/streaming/video/ffmpeg.cpp:150–153,732–737](/home/sunny/research-repos/moonlight-qt/app/streaming/video/ffmpeg.cpp:150).

Video receive → decrypt if negotiated → RTP/FEC queue → ordered frame depacketization → decode unit. It can complete as soon as sufficient shards are available, without waiting for all parity; packets for already completed frames are discarded. It tracks missing sequences and frame gaps, tolerates in-frame packet reordering, and reconstructs RS blocks before depacketization. This is neither “never buffers a packet” nor a large general-purpose playout jitter buffer. [moonlight-common-c/src/VideoStream.c:92–107,189–232](/home/sunny/research-repos/moonlight-common-c/src/VideoStream.c:92); [moonlight-common-c/src/RtpVideoQueue.c:194–245,281–334,619–711,743–778](/home/sunny/research-repos/moonlight-common-c/src/RtpVideoQueue.c:194).

When loss exceeds recoverability, the client requests reference invalidation if negotiated/decoder-compatible, otherwise IDR. Waiting states distinguish first IDR, subsequent IDR, and confirmed post-invalidation frames, and drop dependent data as needed. Queued invalidation ranges can be coalesced; overflow falls back to IDR. Speculative loss reporting is conditional on RFI support in this snapshot (the latest common-C commit explicitly tightens that). [moonlight-common-c/src/VideoDepacketizer.c:98–127,783–823,866–899,1078–1095](/home/sunny/research-repos/moonlight-common-c/src/VideoDepacketizer.c:98); [moonlight-common-c/src/ControlStream.c:390–416,1493–1634](/home/sunny/research-repos/moonlight-common-c/src/ControlStream.c:390); [moonlight-common-c/src/RtpVideoQueue.c:194–223](/home/sunny/research-repos/moonlight-common-c/src/RtpVideoQueue.c:194).

Do not silently reinterpret this as “the frame has been displayed,” nor assume Sunshine's current NVENC server uses the extension. Per-frame FEC-status reports (`0x5502` client→host) carry highest/contiguous sequence, missing/data/parity counts and block positions. ### 2.3 Frame pacing and what adds latency

Pacer has separate pacing/render queues, each capped at **3**, with a hardware-frame budget checked against `PACER_MAX_OUTSTANDING_FRAMES=5`. Depending on renderer, it has a vsync-source thread, render thread, or SDL event to main thread. It waits for renderer readiness **before** dequeuing a frame, preserving the ability to choose fresh queued work. [moonlight-qt/app/streaming/video/ffmpeg-renderers/pacer/pacer.cpp:16–30,84–100,104–169,179–195,316–322](/home/sunny/research-repos/moonlight-qt/app/streaming/video/ffmpeg-renderers/pacer/pacer.cpp:16).

On vsync it uses queue history over **500 ms** to choose a drop target, typically one frame but temporarily up to three when the source FPS meets/exceeds display FPS. It can wait until next vsync minus **3 ms slack** for a frame. Render queue catch-up similarly uses a rolling history and a 0/1/2-frame target. Frame pacing intentionally trades a little delay for smoother display under jitter; disabling it does not remove renderer/OS/display waiting. [moonlight-qt/app/streaming/video/ffmpeg-renderers/pacer/pacer.cpp:201–249,332–418](/home/sunny/research-repos/moonlight-qt/app/streaming/video/ffmpeg-renderers/pacer/pacer.cpp:201).

This generic vsync-source pacing is instantiated for **Windows and Wayland** in the examined code. Other platforms render immediately through this layer; their renderer/OS can still synchronize or buffer. In particular, do not assign the Windows/Wayland pacer waits automatically to macOS's Metal/display-link or display-layer behavior. [moonlight-qt/app/streaming/video/ffmpeg-renderers/pacer/pacer.cpp:262–309](/home/sunny/research-repos/moonlight-qt/app/streaming/video/ffmpeg-renderers/pacer/pacer.cpp:262).

Latency additions to look for: capture/display FPS mismatch, decode-unit backlog, GPU surface exhaustion, copyback fallback, main-thread event hop, pacing queue, FIFO/driver buffering, macOS display-layer buffering, display scanout and pixel response. Decoded frames can be dropped safely while retaining decoder reference state; encoded interframes cannot be dropped the same way. Renderer choice and actual presentation mode deserve telemetry, not just “hardware decode: yes.”

Moonlight receives local input through SDL/platform helpers. Mouse drains pending SDL motion, sums relative deltas and retains the latest absolute position, mapping the latter through the video rectangle. Reliability is event-specific. **Relative and absolute mouse, buttons, keys, UTF-8 text and ordinary gamepad state use reliable ENet flags** in this snapshot, on category/controller channels. **Steal:** hardware-path probing with decode test samples, pull decode thread, zero-copy frontend/backend separation, explicit renderer readiness, post-decode catch-up, detailed operational overlay, reference-aware recovery and mature input mappings. **Avoid:** treating low decode time as proof of low display latency; a single “network latency” number without its definition; assuming three queues of small bounded depth cannot add several refresh intervals; hard-coding yesterday's Mac renderer preference.

### 3.2 SudoVDA, resolution, refresh and HDR

Apollo creates a Windows indirect display through **SudoVDA**, an IddCx driver. In launch preparation it selects a rendering adapter, decides whether a virtual display is needed (explicit request/configuration/headless case), and derives an identity from client UUID, app UUID, or both. Client dimensions and refresh are passed to `AddVirtualDisplay`; refresh is in **millihertz**, with values below 1000 multiplied by 1000 and an optional double-refresh policy. It then resolves the new display name, selects it as capture output and applies display configuration. ### 4.3 Wire, FEC, recovery, pacing and encryption

Wolf implements Moonlight's HTTPS/PIN, RTSP, ENet control and UDP video/audio framing using its own protocol/GStreamer code. RTSP negotiation uses **20% FEC** (a TODO/configuration constant), minimum parity **2**, and Sunshine-like initial bitrate deductions. No closed-loop video bitrate controller was identified. [wolf/src/moonlight-server/rtsp/commands.hpp:194–253](/home/sunny/research-repos/wolf/src/moonlight-server/rtsp/commands.hpp:194).

Video RS parity is `ceil(data * percent / 100)`, raised to minimum parity with an adjusted advertised percentage. Wolf's implementation splits sufficiently large frames into **three FEC blocks** when data shards exceed 90, rather than Sunshine's up-to-four adaptive-size strategy. Individual RS blocks must fit 255 shards; oversize blocks can bypass FEC. The implementation and exact header math are in [wolf/src/moonlight-server/gst-plugin/video.hpp:143–182,192–265,269–344](/home/sunny/research-repos/wolf/src/moonlight-server/gst-plugin/video.hpp:143); default properties in [wolf/src/moonlight-server/gst-plugin/gstrtpmoonlightpay_video.cpp:119–149](/home/sunny/research-repos/wolf/src/moonlight-server/gst-plugin/gstrtpmoonlightpay_video.cpp:119). This is packet erasure repair, not temporal coding; burst loss spanning more parity than a block can cover still needs recovery.

Sender can batch UDP datagrams. Optional pacing, enabled with `WOLF_ENABLE_VIDEO_PACING=TRUE`, uses roughly **800 Mb/s**, **1 ms** windows, a batch cap of 16 and approximately 64 KiB. Its default is disabled. This is a burst limiter, not path congestion control. No video retransmit cache/NACK-driven RTX or effective RFI handler was established in the traced control-to-encoder path; IDR requests are handled. [wolf/src/moonlight-server/streaming/streaming.cpp:198–208,227–300,400–409](/home/sunny/research-repos/wolf/src/moonlight-server/streaming/streaming.cpp:198); [wolf/src/moonlight-server/control/control.cpp:211–220](/home/sunny/research-repos/wolf/src/moonlight-server/control/control.cpp:211).

**Static crypto finding, not a reproduced exploit:** outbound feedback calls `encrypt_packet(aes_key, 0, payload)` for each packet. The helper constructs a zero-filled GCM IV, writes the sequence into its first byte, and encrypts with that IV. Repeated messages under a session key therefore have a visibly repeated nonce on this path. The sequence-byte assignment would also truncate a larger counter if one were supplied unchanged. This deserves upstream/security-owner review before copying the code. [wolf/src/moonlight-server/control/control.cpp:85–90](/home/sunny/research-repos/wolf/src/moonlight-server/control/control.cpp:85); [wolf/src/moonlight-protocol/moonlight/control.hpp:410–425](/home/sunny/research-repos/wolf/src/moonlight-protocol/moonlight/control.hpp:410). PIN pairing is not sufficient evidence of sound media/control encryption. Audio CBC is negotiated; the traced video payloader does not implement Sunshine's per-shard video GCM wrapper. Do not assume that a private-network deployment encrypts every media payload.

## 5. Moonshine (Rust): Smithay → DMA-BUF → Vulkan Video

### 5.1 Scope and execution model

This is **hgaiser/moonshine v0.16.1**, not similarly named projects. It is a Linux host with an in-process headless Smithay compositor, a Vulkan Video encoder through **PixelForge v0.9.1**, a Moonlight-compatible protocol implementation, Inputtino gamepads and a built-in PulseAudio-protocol server. There is no native macOS/Windows host here. Merely being Rust does not make its capture backend portable to Apple's VideoToolbox. The compositor creates GBM/EGL/GLES rendering resources on a DRM render node; it does not need scanout ownership/DRM master. Frames are exported as DMA-BUFs with lifetime/consumption tracking, passed through a **two-frame synchronous channel**, imported to Vulkan and converted on GPU. An OS video thread submits encodes; a Tokio consumer awaits encode futures in order, reads completed bitstreams, inserts metadata, packetizes/FEC-encrypts, then queues batches to a UDP sender task. Input reaches the compositor through calloop channels. PixelForge supports asynchronous submit/completion. Moonshine does not deliberately wait for the next captured frame before consuming a completed encode. ### 5.2 Exact encoding, color and reference repair

Moonshine requests H.264, HEVC or AV1, 4:2:0 or 4:4:4, SDR 8-bit or HDR 10-bit according to negotiation and Vulkan capabilities. It uses `EncodeTuning::LowLatency` (not `UltraLowLatency`), CBR at negotiated target, no B frames, **GOP size 0 meaning infinite**, client-derived maximum references, **VBV duration `1000 / FPS` integer milliseconds**, initial VBV occupancy **0**. PixelForge's Vulkan quality-level control is **0**; its separately named config `quality_level` is a codec quantizer for modes that use it, not the Vulkan quality-tier index. [moonshine/moonshine-core/src/session/stream/video/pipeline/mod.rs:551–605,668–674](/home/sunny/research-repos/moonshine/moonshine-core/src/session/stream/video/pipeline/mod.rs:551); [pixelforge/src/encoder/mod.rs:189–202,310–331](/home/sunny/research-repos/pixelforge/src/encoder/mod.rs:189); [pixelforge/src/encoder/h264/record.rs:467–468,499–509](/home/sunny/research-repos/pixelforge/src/encoder/h264/record.rs:467).

There are **no NVENC, AMF, QSV, VAAPI or VideoToolbox preset strings** in this host's selected encoder path. Vulkan Video drivers translate the explicit encode structures. Hardware capability probing matters: device support for a codec does not imply 10-bit/4:4:4 encode support, and an NVIDIA/AMD/Intel brand name is not a guarantee. A one-frame VBV expressed in whole milliseconds is 16 ms at 60 FPS, 8 ms at 120, not an exact frame-duration rational.

Reference invalidation is implemented, rather than merely mapping every loss to an IDR. For H.264 it retains references older than the first lost picture and issues MMCO commands to remove tainted later pictures from the decoder's sliding-window DPB. HEVC rebuilds its explicit short-term reference-picture set from surviving references. AV1 removes tainted entries and repoints reference names to survivors. If none remain, an IDR/keyframe is necessary. These are **short-term history repair**, not an acknowledged long-term-reference scheme. H.264 initialization explicitly has `max_long_term_refs=0`; H.265 marks pictures non-long-term. [pixelforge/src/encoder/h264/mod.rs:160–182](/home/sunny/research-repos/pixelforge/src/encoder/h264/mod.rs:160); [pixelforge/src/encoder/h264/init.rs:91–97](/home/sunny/research-repos/pixelforge/src/encoder/h264/init.rs:91); [pixelforge/src/encoder/h265/mod.rs:135–150](/home/sunny/research-repos/pixelforge/src/encoder/h265/mod.rs:135); [pixelforge/src/encoder/h265/record.rs:189–197](/home/sunny/research-repos/pixelforge/src/encoder/h265/record.rs:189); [pixelforge/src/encoder/av1/mod.rs:132–143](/home/sunny/research-repos/pixelforge/src/encoder/av1/mod.rs:132).

HEVC records a single slice-segment entry in this implementation; the API does not establish Sunshine-style negotiated multi-slice streaming. The whole completed encoded frame is consumed before packetization. No periodic cyclic intra-refresh configuration was found in the Moonshine setup. [pixelforge/src/encoder/h265/record.rs:277–286](/home/sunny/research-repos/pixelforge/src/encoder/h265/record.rs:277); [moonshine/moonshine-core/src/session/stream/video/pipeline/mod.rs:237–341](/home/sunny/research-repos/moonshine/moonshine-core/src/session/stream/video/pipeline/mod.rs:237).

### 5.3 Protocol, FEC, security and a concrete interoperability concern

Moonshine implements Moonlight-style HTTPS pairing/launch, RTSP negotiation, ENet control and RTP-like video/audio UDP, with video FEC default **20%** and optional AES-GCM video encryption. It uses **quinn-udp**, not QUIC, for batched/GSO UDP transmission. There is no QUIC congestion controller hidden in that dependency. The GSO path caps segments by OS capability and 65,507-byte aggregate size, falls back to per-datagram sends, and waits for socket writability. No per-path media rate controller or network-aware pacer was found in that sender. [moonshine/moonshine-core/src/session/stream/video/mod.rs:26–31,82–83,379–429](/home/sunny/research-repos/moonshine/moonshine-core/src/session/stream/video/mod.rs:26); [moonshine/moonshine-core/src/session/stream/video/gso_socket.rs:85–118](/home/sunny/research-repos/moonshine/moonshine-core/src/session/stream/video/gso_socket.rs:85).

The video packetizer uses 255-shard RS blocks, at most four block indices, optional minimum parity, a cache of RS encoders and the Moonlight FEC header bitfields. A large fourth block takes all remaining packets, with parity clamped by the 255-shard capacity. GCM uses per-shard counters and a video-domain discriminator with the Sunshine-style prefix. [moonshine/moonshine-core/src/session/stream/video/packetizer.rs:14,137–177,229–290,327,364–405](/home/sunny/research-repos/moonshine/moonshine-core/src/session/stream/video/packetizer.rs:14).

**Static, arithmetically reproducible interoperability concern:** parity count is `floor(data*percent/100)` (then minimum/cap), while the advertised integer percentage becomes `floor(parity*100/data)`. Common-C reconstructs count as `ceil(data*advertised_percent/100)`. At the packetizer's 20% maximum block, **213 data → 42 parity → advertised 19% → client expects 41 parity**. This changes RS dimensions and deserves an interoperability test under actual erasures; loss-free frames can obscure it. Source: [moonshine/moonshine-core/src/session/stream/video/packetizer.rs:235–236,274–287](/home/sunny/research-repos/moonshine/moonshine-core/src/session/stream/video/packetizer.rs:235); [moonlight-common-c/src/RtpVideoQueue.c:709–711](/home/sunny/research-repos/moonlight-common-c/src/RtpVideoQueue.c:709). This dossier establishes the arithmetic mismatch, not a hardware/network reproduction or an upstream issue status.

Control parses IDR and reference-invalidation messages; loss-statistics messages do not by themselves establish adaptation. Reconnect resets frame/sequence accounting and requests a fresh keyframe; encryption-key update logic is separate. [moonshine/moonshine-core/src/session/stream/control/mod.rs:57–105,163–192,556](/home/sunny/research-repos/moonshine/moonshine-core/src/session/stream/control/mod.rs:57); [moonshine/moonshine-core/src/session/stream/video/pipeline/mod.rs:719–785](/home/sunny/research-repos/moonshine/moonshine-core/src/session/stream/video/pipeline/mod.rs:719).

### 6.4 WebRTC wire, FEC, retransmission and actual adaptation

WebRTC uses SDP/ICE, DTLS-authenticated SRTP and SCTP data channels, not RTSP/ENet or Moonlight's video header. H.264 RTP payloads use NAL aggregation (STAP-A) and FU-A fragmentation with `PACKET_MAX=1200`; RTP timestamps use 90 kHz video and 48 kHz audio. Supported SRTP profiles include AES-256-GCM, AES-128-GCM and AES128-CM/SHA1-80, negotiated against compiled support. Browser DTLS fingerprints authenticate the negotiated transport relative to trusted signaling; they are not the same user-managed persistent host pin as Moonlight pairing. [selkies/src/selkies/webrtc/codecs/h264.py:52–60,148–158,189–196,252–265](/home/sunny/research-repos/selkies/src/selkies/webrtc/codecs/h264.py:52); [selkies/src/selkies/webrtc/rtcdtlstransport.py:92–152](/home/sunny/research-repos/selkies/src/selkies/webrtc/rtcdtlstransport.py:92); [selkies/src/selkies/webrtc_media_pipeline.py:24–30](/home/sunny/research-repos/selkies/src/selkies/webrtc_media_pipeline.py:24).

NACK retransmits from a **1-second / 9,600-packet** bounded history. A second NACK for a retained packet emits `lost_frame` to the native reference-invalidation callback; packets outside history trigger PLI/keyframe. RTX gets fresh transport-wide sequence numbers. PLI/FIR also request an actual native encoder keyframe, not just an unused software encoder flag. SDP advertises `rtx-time=125 ms`; that is **not the sender history length**. [selkies/src/selkies/webrtc/rtp.py:45–51,978–989](/home/sunny/research-repos/selkies/src/selkies/webrtc/rtp.py:45); [selkies/src/selkies/webrtc/rtcrtpsender.py:419–449,524–539](/home/sunny/research-repos/selkies/src/selkies/webrtc/rtcrtpsender.py:419); [selkies/src/selkies/webrtc_engine.py:1126–1174,2073–2080](/home/sunny/research-repos/selkies/src/selkies/webrtc_engine.py:1126); [selkies/src/selkies/webrtc_mode.py:2657–2662](/home/sunny/research-repos/selkies/src/selkies/webrtc_mode.py:2657).

Video FEC is **FlexFEC XOR with interleaved masks**, not Reed–Solomon. When negotiated, groups end at a frame marker or **10 packets**. It sends 1, 2 or 3 repairs according to smoothed loss: EWMA coefficient **0.3**, thresholds **2%** and **8%**. Repairs cover interleaved subsets; this does not recover every arbitrary three-packet erasure as an RS(10,3) code would. Negotiation/browser support determines whether it runs. FEC steering occurs in the periodic feedback loop **before** the `congestion_control` gate, so disabling encoder bitrate adaptation does not itself disable this loss-based FEC policy. [selkies/src/selkies/webrtc/rtcrtpsender.py:469–475,674–695](/home/sunny/research-repos/selkies/src/selkies/webrtc/rtcrtpsender.py:469); [selkies/src/selkies/webrtc_mode.py:2707–2739](/home/sunny/research-repos/selkies/src/selkies/webrtc_mode.py:2707).

The strict-priority pacer is **enabled by default**, while encoder congestion adaptation is a **separate option, disabled by default**. Audio/RTCP bypass the token bucket; data-channel traffic precedes video/RTX/FEC. Normal pacing ceiling is **2.5× encoder target**, minimum burst 2048 bytes. Video queue budget is max(**120 ms** of wire time, **2.2×** largest of last four IDRs). Overflow abandons the GOP and requests a new keyframe, rather than clipping arbitrary packet tails. Optional stale-GOP deadlines are off by default because a gap can stall browser receive buffers. [selkies/src/selkies/settings.py:192–195,1049–1052](/home/sunny/research-repos/selkies/src/selkies/settings.py:192); [selkies/src/selkies/webrtc/pacer.py:5–42,52–105,127–151](/home/sunny/research-repos/selkies/src/selkies/webrtc/pacer.py:5).

Pacer braking uses fresh delivery evidence; it distinguishes a burst outage from repeated loss runs. It reserves 500 kb/s for other classes, has a target-relative floor and +25%/s recovery. This complexity is useful evidence of how a superficially reasonable “lower rate when our queue overflows” loop can feed back on its own chosen pace. It is **custom control**, not a claim that stock aiortc/libwebrtc GCC is doing all the work. [selkies/src/selkies/webrtc/pacer.py:31–42,63–105,132–138](/home/sunny/research-repos/selkies/src/selkies/webrtc/pacer.py:31).

When congestion control is enabled in CBR mode, a **1-second** loop aggregates TWCC evidence per display, accounts for its slowest peers, uses the user's chosen rate as ceiling and changes the native encoder target. Shared `CongestionSteer` backs off to **0.7×** after two consecutive loss strikes above **10%**, holds **2 seconds**, then grows **1.15×** per step or follows **85%** of higher measured goodput. Application-limited idle-screen throughput is not treated as capacity. One slow viewer may therefore reduce quality for viewers of the **same encoded display**, not unrelated displays. [selkies/src/selkies/webrtc_mode.py:2676–2740](/home/sunny/research-repos/selkies/src/selkies/webrtc_mode.py:2676); [selkies/src/selkies/stream_server.py:255–292](/home/sunny/research-repos/selkies/src/selkies/stream_server.py:255).

### 6.5 WebSockets: a materially different loss/latency tradeoff

Default WebSockets carries custom video/JPEG/audio/control framing over reliable TCP. Video message type `0x04` identifies encoded full frames/stripes with codec/frame/reference/geometry information; H.264/JPEG can use independent stripe paths, other codecs generally full-frame. WebCodecs or browser video paths consume these rather than Moonlight decoders. [selkies/src/selkies/websockets_mode.py:18–36](/home/sunny/research-repos/selkies/src/selkies/websockets_mode.py:18); [selkies/src/selkies/webrtc_media_pipeline.py:84–85](/home/sunny/research-repos/selkies/src/selkies/webrtc_media_pipeline.py:84); [selkies/addons/selkies-web-core/selkies-ws-core.js:52,1592–1614,1800–1826](/home/sunny/research-repos/selkies/addons/selkies-web-core/selkies-ws-core.js:52).

TCP repairs bytes but imposes head-of-line waiting. A canceled or stale media frame cannot be removed from the kernel, a proxy, or the receiver's TCP reassembly queue. Selkies therefore measures both asyncio/kernel queue pressure, bounds per-client delivery, pauses capture delivery based on **client frame ACKs**, and paces bulk file/clipboard traffic with an end-to-end ping gauge. It explicitly closes partially canceled sends. [selkies/src/selkies/websockets_mode.py:319–420](/home/sunny/research-repos/selkies/src/selkies/websockets_mode.py:319).

Optional CBR adaptation uses frame round-trip growth above a rolling **10-minute minimum**, plus backpressure state, as congestion evidence; the same backoff/hold controller changes video rate once per second. Client consumption rate is estimated separately so a stalled sender does not teach the controller a permanently low decoder FPS. This is more robust than an unbounded TCP video queue, but cannot erase TCP loss recovery delay. [selkies/src/selkies/websockets_mode.py:2590–2670](/home/sunny/research-repos/selkies/src/selkies/websockets_mode.py:2590).

## 7. Rust transport reality check: quinn and str0m

### 7.1 Quinn: secure congestion-controlled transport, not a media engine

Quinn supplies QUIC connections/streams/datagrams, encryption, loss detection, congestion control, pacing, path-MTU behavior and runtime I/O integration. It supplies **none** of capture, encoder tuning, video reference tracking, packet FEC, client decoding/presentation, audio capture/mixing, input injection, app launch or user pairing. Those twelve engine concerns cannot be delegated to `Connection`.

`send_datagram()` is unreliable/unordered and each application datagram must fit **one QUIC packet** and the peer's limit. On a full send buffer it can discard **oldest unsent datagrams** to admit newer ones. `send_datagram_wait()` instead waits for space, preserving older queued work and potentially increasing latency. Neither knows whether one dropped datagram contains an IDR header, an audio frame or the final fragment of a reference picture. The API exposes available send-buffer space and dynamic maximum datagram size; Sunna has to use them at a **frame/dependency** level. [quinn/quinn/src/connection.rs:497–571](/home/sunny/research-repos/quinn/quinn/src/connection.rs:497).

The default outgoing datagram capacity is **1 MiB**; the default controller is **CUBIC**, not BBR. NewReno/BBR and custom controller factories exist. Datagram payloads are not retransmitted as stream data, but their QUIC packets still participate in congestion/loss accounting. Adding application FEC does not exempt that traffic from congestion control. Reliable input/control and video datagrams on one connection still share a path congestion window and socket scheduling even though streams eliminate cross-stream ordered-delivery blocking. [quinn/quinn-proto/src/config/transport.rs:307–316,330–345,400–409](/home/sunny/research-repos/quinn/quinn-proto/src/config/transport.rs:307); [quinn/quinn-proto/src/congestion.rs:8–12](/home/sunny/research-repos/quinn/quinn-proto/src/congestion.rs:8); [quinn/quinn-proto/src/connection/mod.rs:3434–3447,4198](/home/sunny/research-repos/quinn/quinn-proto/src/connection/mod.rs:3434).

Analytical scale: 1 MiB at 20 Mb/s is approximately **419 ms of payload**, before FEC/headers. That is a capacity example, not a measurement of Quinn's normal queue. Likewise, a congestion controller that bounds bytes in flight does not automatically bound capture-to-display age. App-level bitrate targets should account for media+FEC+audio+input and queue age, not merely copy a socket throughput estimate.

Quinn encrypts transport packets; **authenticating the intended user/device remains application work**. Accepting any self-signed certificate without a pairing/pinning/trust decision makes encryption alone insufficient. QUIC migration/MTU features do not implement rendezvous, NAT traversal policy, relay discovery or a Tailscale replacement. Those concerns belong to the other researchers; they are prerequisites at this integration boundary, not claims about what Quinn cannot ever be combined with.

**Steal/use:** audited transport crypto and congestion machinery, explicit datagram limits, stats and controller hooks. **Avoid:** replacing media-aware frame admission with `send_datagram_wait()`; accepting invisible local fragment loss as a network-loss signal; layering a second competing rate controller without defining which owns pacing, encoder target and FEC budget.

### 7.2 str0m: lower-level WebRTC with deliberate scheduling control

Str0m is **Sans I/O**: `Rtc` has no internal threads/async tasks/socket operations. The caller feeds network packets/timeouts and drains output, integrates sockets/timers, and supplies already-encoded media. Its documented invariant is **mutate → drain until Timeout → mutate**; sleeping or doing another mutation while output is queued can produce incorrect behavior. This is a strong fit for explicit scheduling but imposes a real integration contract. [str0m/src/lib.rs:3–6,123–141,427–443](/home/sunny/research-repos/str0m/src/lib.rs:3).

It implements SDP, ICE, DTLS/SRTP, data channels, codec-aware RTP packetization, RTCP, NACK/RTX, TWCC and bandwidth estimation. It does **not** encode/decode/capture/render media, provide a browser-style PeerConnection API, an adaptive jitter buffer, TURN client or interface enumeration. Applications can integrate external TURN/ICE infrastructure; the library's missing TURN item is not proof that a complete str0m-based product cannot relay. [str0m/src/lib.rs:561–583](/home/sunny/research-repos/str0m/src/lib.rs:561).

BWE is **off by default**. Enabling it with an initial bitrate and setting desired bitrate allows probing/estimates, but the app must allocate bitrate and actually reconfigure its encoders in response to `EgressBitrateEstimate`. `can_probe` requires negotiated TWCC/SRTP/sending media, and does not prove feedback is arriving. A leaky-bucket pacer adjusts send rate/queue drainage; do not interpret its internal `PACING=40 ms` timeout constant as an unconditional 40 ms delay on every packet. [str0m/src/config.rs:460–489,836](/home/sunny/research-repos/str0m/src/config.rs:460); [str0m/src/bwe/api.rs:10–27,42–61](/home/sunny/research-repos/str0m/src/bwe/api.rs:10); [str0m/src/pacer/leaky.rs:15–39,65–66](/home/sunny/research-repos/str0m/src/pacer/leaky.rs:15).

Defaults: audio reorder budget **15 packets**, video **30 packets**, video reorder timeout **None**; send/resend ring **50 audio / 1000 video packets**. These are packet counts/holding capacities, not milliseconds or decoded-frame counts. RTP mode can bypass frame reassembly and deliver packets directly to a custom client pipeline. NACK reports are spaced at least **33 ms**, TWCC at **50 ms**, and an individual missing packet is NACKed at most **five times**. On a 60-FPS local game stream, even one 33 ms repair scheduling interval is significant; a generic WebRTC default is not automatically an optimal interactive-desktop setting. [str0m/src/config.rs:492–600,610–660,830–844](/home/sunny/research-repos/str0m/src/config.rs:492); [str0m/src/session.rs:44–50](/home/sunny/research-repos/str0m/src/session.rs:44); [str0m/src/streams/register_nack.rs:8–31](/home/sunny/research-repos/str0m/src/streams/register_nack.rs:8).

Current str0m supports optional Opus **RED** (default Opus enabled without RED, default redundancy distance one when enabled). No implemented video RS/FlexFEC scheme was established in this skim; a parser fixture mentioning ULPFEC is not implementation evidence. [str0m/src/config.rs:238–258](/home/sunny/research-repos/str0m/src/config.rs:238). Keyframe request events and retransmit mechanics still need reference-aware encoder recovery policy upstream. WebRTC encryption and negotiation still need authenticated signaling and application permissions.

**Steal/use:** controllable event-driven scheduling, standards-compatible browser transport, integrated feedback/RTX and explicit codec packetization. **Avoid:** assuming media engines come with it; forgetting BWE defaults off; copying reorder/NACK defaults without a deadline budget; expecting a native Rust sender to control the browser's final display queue.

### 9.2 Numbers that must not be compared as though equivalent

- **Encode duration:** from encoder submission to completion, possibly including device queuing. Does not include the age of the captured surface.
- **Sunshine host-processing field:** optional source timestamp to short-header construction. Timestamp provenance differs by backend; a missing timestamp can produce zero. FEC/send and client display follow it.
- **Network RTT:** a round trip, not video's one-way transit. Halving RTT assumes symmetric paths and does not reveal queue residence inside either application.
- **Decode duration:** compressed input to decoded surface; excludes any later scheduled presentation, display-layer buffering and photons.
- **Frame interval / average FPS:** cadence/throughput, not age. A repeated 60 FPS image can be arbitrarily stale.
- **Display difference:** source display vs receiver display; may include different scanout phases but omit remote-input and application response.
- **Input-to-photon:** physical input to changed display light, including application/game response. For streaming overhead, compare with a controlled local baseline using the same application/input/display conditions.

These boundaries follow the inspected counters in §1.1/§2.4 and the external methods above. The [Moonlight FAQ's statistics explanation](https://github.com/moonlight-stream/moonlight-docs/wiki/Frequently-Asked-Questions) also cautions that platform capabilities determine which components can be measured. There is no honest universal sum of all overlay fields that yields click-to-photon.

### 9.3 Analytical scales, explicitly not benchmarks

At 60 Hz, one extra missed display opportunity costs **16.67 ms**; at 120 Hz, **8.33 ms**. Three independent one-frame waits can dwarf a 1 ms encoder improvement. A 100 kB compressed picture requires **40 ms** to serialize on a 20 Mb/s path before protocol/FEC overhead, even if submitted to UDP instantly. With 20% parity/data FEC its payload budget becomes about **48 ms**. These are arithmetic consequences of chosen units/rates, not measured application latencies.

A five-frame reference history at 60 FPS spans roughly **83 ms**, but usable recovery time is less once encoding has advanced beyond the loss and feedback must return. A feedback path with long RTT can exhaust short reference history before an RFI arrives. One XOR parity shard per eight data shards repairs at most **one** erasure in its group; two losses in that group fail even if overall loss percentage looks small. RS with `k` data and `r` parity can reconstruct from any `k` distinct valid shards, but waiting for repair still has a deadline cost. Loss percentage, burst length, packet ordering and time-to-repair all matter.

### 10.2 What is worth taking

**From Sunshine:** surface lifetime discipline; actual encoder capability probes; separate capture/encode/network workers; vendor-specific low-delay controls; real input-device lifecycle; narrow reference invalidation with an IDR fallback; frame timestamps and operational counters. This is a mature body of edge-case handling. A new Rust implementation must preserve those behaviors, not merely translate the happy-path packet loop.

**From Moonlight:** decode-path probing, retained hardware surfaces, renderer-specific presentation, pull decode, post-decode catch-up, per-category input channels and accumulated relative motion. Crucially, it separates decoding a reference from deciding to display that frame. A late frame may need decoding even when it should never be presented.

**From Apollo:** stable device/display identity, permission-scoped participation, display matching with restoration, and explicit distinction between launching, joining and controlling a session. These are engine/session requirements, not only UI polish. Driver discovery and display capture need a readiness handshake.

**From Wolf:** ownership of compositor timing, a real per-session device/seat model and per-session audio sinks. These are powerful for headless Linux. Existing desktop capture still needs its own backend; owning a compositor is not a universal substitute.

**From Moonshine:** direct Rust orchestration of DMA-BUF/Vulkan ownership and asynchronous encode completion; actual codec reference-state modeling rather than generic IDR requests. Also take its examples as evidence that memory safety does not eliminate protocol arithmetic, queue-age or driver-lifetime bugs.

**From Selkies:** coupled retransmit/reference repair, abandoned-GOP state, bounded fan-out, native/browser capability probes, loss feedback and queue diagnostics. A browser client can be valuable without forcing every native-client session through browser media buffering. WebSocket convenience and WebRTC capabilities must be evaluated as different transports.

**From quinn/str0m:** established encrypted transport machinery and explicit runtime contracts. Neither can decide which encoded picture is still useful, set VideoToolbox correctly, preserve keyboard layout semantics, or present a CVPixelBuffer at the right moment.

### 10.3 What to avoid inheriting

1. **A single latency number or “zero-copy” claim as the architecture.** Buffer ownership, GPU copies, queue waits, capture age, unique frames and final presentation each need evidence. Zero CPU readback is useful; it is not a zero-latency guarantee.
2. **Packet dropping without a codec state transition.** Raw-frame drop, encoder-declared skipped picture, unsent encoded picture, partial frame transmission, missing reference, decoder rejection and late decoded presentation are different events. They cannot share a silent “latest wins” rule.
3. **IDR storms.** An IDR may be much larger than a P-frame, precisely when a congested path has least spare capacity. Coalescing requests, bounding recovery traffic and using a safe surviving reference where the actual hardware supports it are essential. “LTR supported” needs a complete host/client acknowledgment and lifecycle contract.
4. **Fixed parity as universal reliability.** A clean LAN and a bursty Wi-Fi/tunnel path need different redundancy budgets. Repair must be evaluated in time to use the frame, not just eventual reconstruction percentage. FEC bytes, RTX bytes and keyframes must be charged to the same path budget.
5. **Two controllers fighting.** QUIC congestion control plus application AIMD plus a pacer plus FEC adaptation can oscillate if each treats another's deliberate limits as path capacity. Queue age, application-limited state, receiver bottleneck and path bottleneck need distinct signals.
6. **A reliable motion backlog or an unreliable key-release assumption.** Keys/buttons require robust state transitions and teardown reconciliation. Relative motion must accumulate displacement; absolute positions can replace stale positions. Touch/pen motion and device arrival have different reliability requirements. Gamepad feedback must have independent flow control.
7. **A universal encoder preset.** NVENC DPB tricks do not imply VideoToolbox equivalents. A one-frame VBV can harm quality or overshoot on some drivers. Multiple slices do not help transmission latency if the API only returns a whole completed access unit. Hardware support must be measured at the negotiated format/bit depth/chroma.
8. **Security inferred from pairing or a transport name.** Authenticated signaling, device trust, privileges, certificate revocation and unique AEAD nonces are separate properties. The Wolf static finding is a concrete reason to audit these boundaries. QUIC avoids designing packet crypto, but not designing who may connect/control.
9. **Broad feature tables that ignore runtime capability.** Current Sunshine's Mac backend is a particular example: common touch/gamepad interfaces exist while the pinned Mac backend rejects those devices. A product must report the actual selected path and its limitations.
10. **Historical issue numbers as current performance evidence.** Renderer defaults, native modules and platform APIs change quickly. Comparisons must name release/commit, configuration and hardware, including fallback paths.

### 10.4 What would be required to beat Sunshine+Moonlight

**On a clean LAN, the margin is mainly pipeline scheduling and presentation.** Sunshine/Moonlight already have low-delay encoding, GPU-resident paths, limited queues and mature native clients. A transport rewrite alone has no demonstrated multi-millisecond dividend when a packet is already arriving promptly. Sunna would need fresher capture, bounded work-in-progress, fast actual hardware encode/decode, and presentation that avoids extra display intervals. Improvements must survive sustained load and p95/p99 measurement, not just best-frame timing. The specialized ~12.5 ms published display-difference result is evidence that the incumbent can already be efficient under favorable conditions, not a target applicable to every Mac session.

**On variable internet paths, a clearer architectural opening exists.** The examined Sunshine/Apollo/Wolf senders do not close the loop from receiver congestion to encoder bitrate, and their pacing does not track path capacity. Sunna would need media-aware use of Quinn's congestion feedback and admission controls; a path-MTU-safe packet budget; frame deadlines; controlled IDR size; adaptive protection that distinguishes burst loss from overload; and recovery that chooses RTX/FEC/reference repair based on whether the result can still arrive usefully. RTT makes retransmission occasionally valuable and occasionally futile. Lowest median latency at zero loss is not enough: stalls, recovery time, quality during recovery and input latency under media congestion determine robustness.

**On the owner's M1/M2 Macs, native presentation and verified VideoToolbox behavior are the most immediate engine concerns.** Sunna already retains IOSurfaces into encode, but the checked-in decoder still copies BGRA to CPU and the viewer uses softbuffer. That is a concrete disadvantage relative to Moonlight's hardware-surface renderers, independent of transport. [Sunna/crates/codec/src/videotoolbox/mod.rs:1–11](../../crates/codec/src/videotoolbox/mod.rs:1); [Sunna/apps/sunna-cli/src/viewer.rs:1–7,95–128](../../apps/sunna-cli/src/viewer.rs:1). Here `Sunna/` resolves to the read-only `../../`. The platform researcher should determine the actual supported Apple low-latency/reference/presentation APIs; this dossier does not invent NVENC-equivalent RFI on VideoToolbox.

**Current Sunna is more careful than the old “silent drops” description suggests.** The read-only host code has a pre-encode backlog gate, whole-frame admission checks, immediate local bitrate cuts and a wire-frame ID that advances for an encoded frame dropped before send. Its client gates interframes until a keyframe after an unrecovered gap. [Sunna/crates/host/src/lib.rs:168–201,218–291](../../crates/host/src/lib.rs:168); [Sunna/crates/client/src/lib.rs:225–275](../../crates/client/src/lib.rs:225). Those mechanisms are a useful base; they do not eliminate the large recovery burst or guarantee a useful reference survives. The configured outgoing QUIC datagram budget remains 1 MiB ([Sunna/crates/transport/src/lib.rs:24–30,62–68](../../crates/transport/src/lib.rs:24)). Capacity, actual occupancy and frame age must be distinguished.

**Quality leadership requires more than AV1.** The engine needs a deliberate desktop/game content policy: correct color/range/transfer, crisp fine text, stable static regions, recovery without persistent corruption, and HDR where the entire chain supports it. 4:4:4 can materially preserve chroma detail but is constrained by encoder and decoder hardware; lossless text/static refinement may require a complementary image/update mode rather than turning a 4:2:0 game stream's bitrate indefinitely upward. That is an architectural inference from the capability tables, not a claim that the reviewed engines already provide exact desktop convergence. Quality comparisons must hold bandwidth, resolution, frame rate, chroma and latency constraints constant.

**Audio and input must meet the same standard as video.** A low video overlay does not compensate for 50–100 ms of audio backlog, drift, clipped output, key-layout errors or a lagging cursor. Native packetization and playback clocks need bounded queues, concealment and drift management; external devices and resampling add delays. Gamepad/touch/pen support entails device identity, arrival/removal, feedback and seat ownership, not just serializing button states. Permission revocation must release input state and stop capture/control consistently.

**Session correctness is part of robustness.** Sleep/wake, display disappearance, output resize, codec renegotiation, driver failure, authentication revocation, multi-viewer attachment and application exit must either recover or fail in a bounded, comprehensible way. Apollo and Wolf show different workable session models; their issues show where display and device lifecycles remain fragile. Sunna must choose semantics explicitly, but that choice belongs to the later architecture plan.

### 10.5 Evidence needed before claiming superiority

A defensible claim would report **incremental remote input-to-photon**, not just software stage times, against stock Sunshine+Moonlight and a documented tuned configuration on the same endpoints. It would include median and tail latency; unique-frame cadence and age; recovery time after burst loss; sustained visual quality at equal total wire bandwidth; audio skew/underruns; and input responsiveness while video is congested. Native resolution/refresh/HDR/codec/renderer selections and every fallback should accompany the result.

The necessary cases follow directly from the observed weaknesses: clean Ethernet; real Wi-Fi; reduced tunnel MTU; changing bottleneck capacity; random and burst loss; reorder/jitter; asymmetric delay; receiver decode overload; high-entropy scene/IDR bursts; static text and scrolling; display sleep/resize; and multiple viewers. These are criteria for interpreting a future implementation, **not a scheduled implementation or benchmark plan**. No result in this dossier proves Sunna already wins any of them.

## 11. Material uncertainties retained for the architecture phase

- **Apple reference repair:** whether the actual supported VideoToolbox APIs on M1/M2 and the desired codecs expose a usable acknowledged-reference mechanism with a sufficient horizon. No equivalent to NVENC invalidation is established by these engines' Mac code.
- **Full Mac-host HDR:** pixel type, capture fidelity, tone mapping, display metadata and client HDR output all need end-to-end validation. P010 allocation alone is insufficient.
- **Moonshine RS compatibility:** the floor/percentage/ceil mismatch described in §5 requires an actual loss/reconstruction interoperability test; healthy no-loss playback would not clear it.
- **Wolf crypto finding:** exact exploitable consequences and affected deployments were not tested. The repeated GCM nonce is visible on the traced outbound-feedback path; no external disclosure or exploit was attempted.
- **Actual queue age under overload:** source bounds identify possible residence, not typical residence. Moonshine's sender queue, GStreamer queue defaults, Quinn's datagram budget and browser playback all need real timestamps.
- **Selkies dependency reproducibility:** native modules are compatible-version dependencies, not locked to the inspected Git HEADs. Packaging may select different patches; the native SHA/version distinction below must be preserved.
- **Published latency gaps:** no apples-to-apples current Mac-to-Mac comparison was found. A numerical architecture promise must wait for measurement.
