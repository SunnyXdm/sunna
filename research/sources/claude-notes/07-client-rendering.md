# Client-side rendering for minimum latency and maximum sharpness (researched directly)

Astra's dossier (../dossier-astra.md §2.2-2.4) already covers moonlight-qt's decoder/renderer matrix and pacer. These notes add the platform-presentation facts and the sharpness side.

## macOS

### What moonlight-qt's Metal path actually does (for calibration)
- `vt_metal.mm:742` sets `m_MetalLayer.displaySyncEnabled = params->enableVsync`. With vsync ON on Apple silicon + macOS 14, it attaches a `CAMetalDisplayLink` with `preferredFrameLatency = 1.0` on the main run loop (`vt_metal.mm:811-821`); decoded frames are parked as "latest unrendered frame" (older one freed: latest-frame-wins, `vt_metal.mm:598-613`) and the display-link callback waits up to half a frame interval for a new frame (`vt_metal.mm:913-935`).
- With vsync OFF it renders immediately: `nextDrawable` then `presentDrawable` then `commit` then **`waitUntilCompleted`** (`vt_metal.mm:566-572, 617-624`). `waitUntilCompleted` blocks the render thread for the GPU time; `nextDrawable` blocks when all drawables are in flight (up to 1 s timeout by default).
- Shader samples with `filter::linear`, clamp-to-edge (`app/shaders/vt_renderer.metal:18`): bilinear for both luma and chroma, regardless of whether the stream is 1:1 with the drawable.
- Colour: `m_MetalLayer.colorspace` set per frame colourspace to `kCGColorSpaceITUR_709`, `ITUR_2100_PQ`, `ITUR_2020` or `SRGB` (`vt_metal.mm:230-254`); EDR enabled for 10-bit (`vt_metal.mm:739`).
- AVSampleBufferDisplayLayer path drives timing with a CVDisplayLink (`vt_avsamplelayer.mm:137-171`) and sets `opaque = YES` (`:359`).

### Presentation facts
- **Direct-to-display (compositor bypass) conditions, per Apple:** "your app needs to run in full-screen mode, displaying an opaque CAMetalLayer and RGB content, and run on a Mac with Apple silicon... You can enable the Metal HUD or use Instruments to verify" ([Managing your game window for Metal in macOS](https://developer.apple.com/documentation/metal/managing-your-game-window-for-metal-in-macos)). The drawable need not match the display size; the display hardware scales it "with a high-quality upscaling or downscaling algorithm" (same doc). So: native fullscreen Space (`toggleFullScreen:`), `layer.opaque = YES`, BGRA/RGB10 drawable (convert YUV to RGB in our own shader), no overlays drawn by other layers on top.
- **Measured windowed vs fullscreen cost** (independent, macOS 26, 2019 16" MBP Intel UHD 630, pointer-to-`presentedTime`): windowed ~42 ms when the compositor is in its "fast state" but 80-122 ms in a "slow state" (bimodal, trigger not identified); fullscreen Space 29-55 ms in both states; "Direct scan-out is chosen by macOS, not guaranteed by the app" ([systemless #1050](https://github.com/benletchford/systemless/issues/1050), [PR #994](https://github.com/benletchford/systemless/pull/994)). Intel machine; Apple silicon numbers will differ, but the lesson (windowed = extra compositor frames, sometimes many) is consistent with Apple's doc.
- **Community low-latency recipe** (Daniel Hooper): `displaySyncEnabled = window_is_fullscreen; maximumDrawableCount = 2; presentsWithTransaction = YES; opaque = YES; mach_wait_until the last possible moment` to sample input ([x.com/DanielcHooper/status/2067320915545686158](https://x.com/DanielcHooper/status/2067320915545686158)). Counterpoint from Apple forums: with 2 drawables "basically impossible to make work with the macOS and iOS compositor"; an M1 Max test at 120 Hz with 2 drawables achieved ~80 Hz; Apple DTS recommends `CAMetalDisplayLink` (macOS 14+) for pacing ([forums thread 763426](https://developer.apple.com/forums/thread/763426)). `displaySyncEnabled = NO` has a measured cost: load on kernel_task's InterruptEventSourceBridge thread ([forums thread 761635](https://developer.apple.com/forums/thread/761635), [SDL #10475](https://github.com/libsdl-org/SDL/issues/10475)).
- Implication for Sunna: make the presenter mode a measured choice, not a belief. Two modes to A/B with `presentedTime` telemetry: (a) "arrival" — present on decode completion, `displaySyncEnabled=NO` (tears; only sensible in fullscreen direct-to-display), (b) "display-link" — `CAMetalDisplayLink` with `preferredFrameLatency=1`, latest-frame-wins, render as late as possible before the deadline. Start with `maximumDrawableCount=3` and measure 2. Never `waitUntilCompleted` on the present thread; use `addCompletedHandler` to release CVMetalTextures.
- `MTLDrawable.addPresentedHandler` / `presentedTime` gives the actual on-glass time (0 if dropped) — the only honest "present" timestamp on macOS ([Apple docs: presentedTime](https://developer.apple.com/documentation/metal/mtldrawable/presentedtime)).
- CAMetalLayer can be driven off the main thread (`nextDrawable`/present from a render thread) as long as `presentsWithTransaction = NO`; with `presentsWithTransaction = YES` presentation is tied to a CATransaction commit (use only for synchronized resize).
- Decode: `VTDecompressionSession` defaults to real-time priority (`kVTDecompressionPropertyKey_RealTime` default true; [docs](https://developer.apple.com/documentation/videotoolbox/kvtdecompressionpropertykey_realtime)); do not set `kVTDecodeFrame_EnableTemporalProcessing` (it allows the decoder to delay output for reordering); keep the stream free of B-frames and signal `max_num_reorder_frames=0`/`max_dec_frame_buffering=1` in VUI (moonlight patches SPS for exactly this on macOS, Astra §2.2 citing `ffmpeg.cpp:1761-1810`). Output IOSurface-backed `420v`/`420f` (or `x420` for 10-bit) with `kCVPixelBufferMetalCompatibilityKey`, import planes via `CVMetalTextureCacheCreateTextureFromImage` (zero copy).

### Sharpness
- The single most important sharpness rule: **no resampling**. Size the host virtual display so stream pixels == client drawable pixels (`convertSizeToBacking`, i.e. points x backingScaleFactor). Then set `drawableSize` to the stream size and ensure texel centres align (full-screen triangle with exact UVs, or `MTLSamplerMinMagFilter.nearest` when 1:1) — a half-pixel misalignment with a linear sampler blurs every glyph.
- When scaling is unavoidable (window being resized, mismatched aspect): downscale with a proper filter (Lanczos/bicubic in shader, or let direct-to-display hardware scale in fullscreen); debounce and ask the host to resize the virtual display, then return to 1:1.
- 4:2:0 destroys coloured/subpixel-free text edges (chroma at half resolution: red text on white shows fringes). Mitigation order: (1) chroma-aware upsampling in the shader (bilinear with correct chroma siting — H.264 default siting is left/centre, "type 0"; nearest makes it worse), (2) 4:4:4 (HEVC Main 4:4:4 where decodable, or AVC444-style dual stream recombined in the shader: sample main-view Y + aux-view chroma planes, see FreeRDP notes), (3) lossless static tiles overlay.
- Colour management: tag the layer `colorspace` to match the host's encode tagging (sRGB/Display P3; macOS displays are P3 — if the host captures in P3 but the stream is tagged BT.709 and the client layer untagged, colours shift). Use `bgra8Unorm` with correct colorspace (not `_srgb` unless the shader outputs linear).

### Input capture on macOS client (latency-relevant)
- `NSEvent.isMouseCoalescingEnabled = NO` to get every mouse sample instead of one per frame ([docs](https://developer.apple.com/documentation/appkit/nsevent/1535456-ismousecoalescingenabled)).
- Relative/pointer-lock: `CGAssociateMouseAndMouseCursorPosition(false)` + hide cursor; deltas from NSEvent `deltaX/deltaY` (post-acceleration) — raw HID deltas need IOHIDManager.
- System shortcuts (Cmd-Tab, Cmd-Space, Mission Control, Ctrl-arrows) are consumed before the app sees them; forwarding them requires an active `CGEventTap` (Accessibility permission on the *client*) while the stream window is focused — Parsec/Jump/Screens pattern. Make it opt-in with an escape chord (see research/05).
- Local hardware cursor: render the host-provided cursor image as an `NSCursor` (set via `NSTrackingArea`/`cursorRect`) so pointer motion is at local refresh with zero network latency; the host sends only shape changes + hotspot; host position is only needed when the host moves the pointer itself (warp) or in relative mode.

## Linux
- Wayland frame timing protocols: `presentation-time` (stable) gives presentation feedback timestamps; `tearing-control-v1` (staging, wayland-protocols 1.30) lets fullscreen clients request async flips; `fifo-v1` and `commit-timing-v1` merged in wayland-protocols 1.38 (Oct 2024) ([Phoronix](https://www.phoronix.com/news/Wayland-Protocols-1.38), [fifo-v1](https://wayland.app/protocols/fifo-v1), [commit-timing-v1](https://wayland.app/protocols/commit-timing-v1)); Mesa's Vulkan WSI uses fifo-v1 for proper FIFO without blocking (SDL only prefers Wayland when fifo-v1 is available: [SDL #11640](https://github.com/libsdl-org/SDL/pull/11640)). Compositor support varies (KWin supports tearing-control since 5.27; Mutter support for tearing-control UNVERIFIED as of 2026).
- Zero-copy: VAAPI/Vulkan decode -> dmabuf -> either import into EGL/Vulkan and draw, or attach the dmabuf directly to a `wl_subsurface` via `linux-dmabuf-v1` (v4 feedback tells the client which formats/modifiers are scanout-capable) so the compositor can put the video on an overlay plane without a composition pass.
- Lowest possible: DRM/KMS atomic commit of the decoded frame to a plane (moonlight `drm.cpp`, Astra §2.2) — only for kiosk/handheld sessions without a compositor.
- X11: unredirect fullscreen (`_NET_WM_BYPASS_COMPOSITOR`) and swap interval 0.

## Windows (brief)
- D3D11VA decode -> flip-model swapchain (`DXGI_SWAP_EFFECT_FLIP_DISCARD`), `DXGI_SWAP_CHAIN_FLAG_FRAME_LATENCY_WAITABLE_OBJECT` + `SetMaximumFrameLatency(1)` and wait on the waitable before rendering, `DXGI_SWAP_CHAIN_FLAG_ALLOW_TEARING` + `Present(0, DXGI_PRESENT_ALLOW_TEARING)` for VRR/tearing; independent flip / MPO when fullscreen-borderless ([flip model](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/for-best-performance--use-dxgi-flip-model), [DXGI 1.3 waitable](https://learn.microsoft.com/en-us/windows/uwp/gaming/reduce-latency-with-dxgi-1-3-swap-chains), [variable refresh](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/variable-refresh-rate-displays)). Moonlight's d3d11va choices are in Astra §2.2.
- Frame statistics for present timing: `IDXGISwapChain::GetFrameStatistics` / `DXGI_FRAME_STATISTICS`, or PresentMon.

## wgpu viability
- wgpu 30 added `vulkan::Device::texture_from_dmabuf_fd()`; generic zero-copy import still goes through the HAL layer per backend (`create_texture_from_hal`); community crates wrap it: [wgpu-external-frame](https://github.com/water-rs/wgpu-external-frame) (DMA-BUF via VK_EXT_external_memory_dma_buf, IOSurface via `newTextureWithDescriptor:iosurface:plane:`, Windows shared handles). `TextureFormat::NV12` exists but adapters may report the feature unsupported on Metal ([wgpu #6921](https://github.com/gfx-rs/wgpu/issues/6921)); so import Y and CbCr planes as separate R8/RG8 textures.
- Present modes: wgpu exposes Fifo/FifoRelaxed/Immediate/Mailbox plus `desired_maximum_frame_latency` in `SurfaceConfiguration`; availability is per-backend/platform (on Metal, Immediate maps to `displaySyncEnabled=false`; UNVERIFIED in wgpu-hal source). wgpu does not expose `presentedTime`, `CAMetalDisplayLink`, DXGI waitable objects or Wayland presentation feedback — latency-critical presentation needs the raw layer anyway. Conclusion consistent with 07-v1-plan: raw CAMetalLayer on macOS; wgpu (or raw Vulkan/D3D11) elsewhere behind a presenter trait that exposes a true present timestamp.
