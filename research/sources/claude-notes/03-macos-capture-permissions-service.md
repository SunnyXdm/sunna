# 03 — macOS capture, permissions (TCC), service model, input, audio, clipboard

Research date: 2026-09-25. Scope: Sunna macOS host (current: CGDisplayStream -> IOSurface -> VT H.264, CGEventPost, runs from terminal; planned: SCK, SMAppService LaunchAgent, CGVirtualDisplay).
Legend: (UNVERIFIED) = not confirmed against a primary source in this pass. Local repo cites are FILE:LINE.

## 1. ScreenCaptureKit (SCK) and legacy capture APIs

### 1.0 Legacy API status (affects Sunna's current CGDisplayStream path)
- `CGDisplayStreamCreateWithDispatchQueue`/`CGDisplayStream*`: deprecated macOS 14.0, **obsoleted (API_UNAVAILABLE) in the macOS 15.0 SDK** ("obsoleted in macOS 15.0 - Please use ScreenCaptureKit instead"). Same for `CGWindowListCreateImage`, `CGDisplayCreateImage(ForRect)`. Sources: MacPorts #71136 https://trac.macports.org/ticket/71136 ; aseprite/laf#108 ; JUCE#1414. Obsoletion is a *header* attribute: Rust FFI `extern "C"` declarations (Sunna, RustDesk scrap `libs/scrap/src/quartz/ffi.rs:166`) still link and run because the symbols remain in CoreGraphics at runtime on 15.x/26.x (runtime presence on 26: UNVERIFIED but RustDesk still ships it).
- Runtime regressions on 15:
  - **CGDisplayStream delivers no frames for virtual displays** (CGVirtualDisplay/BetterDisplay) on macOS 15.0+ (tested 15.7): `CGDisplayStreamStart` succeeds, callback never fires / returns nil. https://github.com/rophy/rustdesk/issues/26 -> **Sunna's planned CGVirtualDisplay path REQUIRES SCK.**
  - Two processes with the same executable name calling `CGDisplayStreamCreate` -> second hangs; log `SLSDisplayStreamCreateProxying:61 unable to complete due to timeout` (macOS 15, no Apple answer). https://developer.apple.com/forums/thread/759218 . The "Proxying" symbol suggests CGDisplayStream on 15 is re-implemented as a proxy over the SCK/replayd path (inference, UNVERIFIED) -> no latency advantage left for CGDisplayStream on 15+.
  - The legacy APIs are exactly the "deprecated content capture technologies" that get the monthly Sequoia re-prompt (Apple 15.1 beta note).
- `AVCaptureScreenInput` (Sunshine `av_video.m:31`) likewise deprecated; replaced by SCK.
- **Implication:** migrate to SCK now; keep CGDisplayStream only as <12.3/<14.4-login-window fallback (probably drop — target macOS 14.4+ minimum, arguably 15+).

### 1.1 SCStreamConfiguration (Apple docs JSON, fetched 2026-09-25: https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration)
Availability per property below is from Apple headers/WWDC as I know them; the doc JSON flattens everything to "12.3+", so per-property versions marked (UNVERIFIED) unless noted.
- Geometry: `width`, `height` (output pixels), `scalesToFit`, `sourceRect` (points, display space), `destinationRect`, `preservesAspectRatio` (14.0). For retina 1:1 set width/height = pointSize * backingScale; `captureResolution` (`SCCaptureResolutionType .automatic/.best/.nominal`, 14.0) — `.best` = native backing pixels, `.nominal` = points (1x). For Sunna: `.best` + width/height = pixel size, `scalesToFit=false`.
- `pixelFormat`: documented set is exactly **'BGRA'** (ARGB8888 LE), **'l10r'** (ARGB2101010 LE packed), **'420v'**, **'420f'** (two-plane 4:2:0 video/full) — https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration/pixelformat . Undocumented but used in the wild: `kCVPixelFormatType_64RGBAHalf` ('RGhA') on 15+ (OBS `mac-sck-video-capture.m:214-215`), **'xf44'** (444YpCbCr10BiPlanarFullRange) reported to work (UNVERIFIED; would be the route to 4:4:4 10-bit text-perfect encode via VT HEVC RExt). For Sunna's H.264/HEVC 4:2:0 path, request '420v'/'420f' so SCK's GPU does RGB->YUV and VT gets an IOSurface it can encode zero-copy; set `colorMatrix = kCGDisplayStreamYCbCrMatrix_ITU_R_709_2` and `colorSpaceName = kCGColorSpaceSRGB` or `DisplayP3` explicitly and signal the same VUI in the bitstream (color mismatch is the #1 "looks washed out" bug).
- `queueDepth`: "By default, the system sets the queue depth to its minimum value of three frames ... **Don't exceed a queue depth of eight frames.**" https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration/queuedepth . If the consumer holds all surfaces (e.g. VT still encoding), SCK stalls/drops. Sunna: 3-5, and release CMSampleBuffers as soon as VT has retained the IOSurface.
- `minimumFrameInterval` (CMTime): cap on delivered rate; `CMTime(1, 120)` for ProMotion. SCK is **damage-driven**: it delivers only when content changes (plus `.idle` status frames) — no repeat frames on a static screen; encoder must handle gaps (Sunna: send nothing / keepalive, re-encode last surface only for IDR/refresh).
- `showsCursor` (bake cursor in; Sunna wants false + client-side cursor), `showMouseClicks` (15.0, draws click circles — keep false), `backgroundColor`, `shouldBeOpaque` (14.0), `ignoreShadowsDisplay/SingleWindow`, `ignoreGlobalClipDisplay/SingleWindow`, `capturesShadowsOnly` (14.0), `includeChildWindows` (14.2; OBS `mac-sck-video-capture.m:159`), `streamName` (14.0), `presenterOverlayPrivacyAlertSetting` (`SCPresenterOverlayAlertSetting .system/.never/.always`, 14.0 — controls the alert when Presenter Overlay is active; irrelevant for Sunna).
- Audio: `capturesAudio`, `sampleRate` (48000 default), `channelCount` (2), `excludesCurrentProcessAudio` (13.0). Microphone: `captureMicrophone`, `microphoneCaptureDeviceID` (15.0; delivered as `SCStreamOutputType.microphone`).
- HDR: `captureDynamicRange` (`SCCaptureDynamicRange .SDR/.hdrLocalDisplay/.hdrCanonicalDisplay`) + `SCStreamConfiguration(preset:)` with `.captureHDRStreamLocalDisplay`, `.captureHDRStreamCanonicalDisplay`, `.captureHDRScreenshotLocalDisplay`, `.captureHDRScreenshotCanonicalDisplay` — **macOS 15.0** (WWDC24 session 10088 "Capture HDR content with ScreenCaptureKit" https://developer.apple.com/videos/play/wwdc2024/10088/). HDR presets use 10-bit 'l10r' + PQ/HLG-ish color spaces (exact values UNVERIFIED). macOS 26 adds preset `SCStreamConfigurationPresetCaptureHDRRecordingPreservedSDRHDR10` (Xcode 26 b1 diff https://github.com/dotnet/macios/wiki/ScreenCaptureKit-macOS-xcode26.0-b1).
- 15.0 also added `SCRecordingOutput` (direct-to-file recording) — not useful for streaming.

### 1.2 SCStreamFrameInfo attachments (per-CMSampleBuffer, `CMSampleBufferGetSampleAttachmentsArray()[0]`)
- `SCStreamFrameInfo.status` -> `SCFrameStatus`: `.complete` (new frame), **`.idle`** (no new content; *no image buffer attached* — must not be encoded/treated as error), `.blank` (blank frame), `.suspended` (stream suspended, e.g. lock/sleep/TCC), `.started`, `.stopped`. Always check status before `CMSampleBufferGetImageBuffer`.
- `displayTime` (mach absolute time of the display refresh -> use for capture->glass latency measurement), `scaleFactor` (backing scale), `contentScale`, `contentRect` (where the content sits within the buffer; OBS uses these three for window crop `mac-sck-common.m:224-247`), **`dirtyRects`** (array of CGRect dictionaries of changed regions — useful for ROI/QP hints or skipping encode), `screenRect` (14.0), `boundingRect` (14.0), `presenterOverlayContentRect` (14.0). (Version tags UNVERIFIED.)

### 1.3 Filters, picker, screenshots
- `SCShareableContent.getWithCompletionHandler` / `getExcludingDesktopWindows:onScreenWindowsOnly:` enumerate displays/apps/windows; `SCShareableContent.current` (async). Each call can trigger TCC. `SCShareableContentInfo` + `SCShareableContent.info(for: filter)` (14.0) gives contentRect/pointPixelScale for a filter.
- `SCContentFilter(display:excludingWindows:)`, `(display:including:exceptingWindows:)` (apps), `(desktopIndependentWindow:)` (single window, follows across Spaces), `includeMenuBar` (14.2, OBS `mac-sck-video-capture.m:185`). Excluding Sunna's own overlay windows is how to hide host-side UI from the stream.
- `SCContentSharingPicker` (14.0): system UI to pick content; picker-granted streams don't need the Screen Recording TCC grant and avoid the Sequoia re-prompt, but need a local user -> not for unattended hosts. `SCStream.updateContentFilter` / `updateConfiguration` allow live changes (resolution change without restart).
- `SCScreenshotManager.captureSampleBuffer/captureImage(contentFilter:configuration:)` (14.0); macOS 26 adds `captureScreenshot(rect:configuration:)` / `SCScreenshotConfiguration` / `SCScreenshotOutput{sdrImage,hdrImage}` / `SCScreenshotDynamicRange` (dotnet/macios diff above). Useful for thumbnails/"preview" only.

### 1.4 Latency / behavior notes (vs CGDisplayStream)
- Both are compositor-fed IOSurfaces (WindowServer); on 15+ CGDisplayStream appears to be proxied (see 1.0). Apple claims SCK is GPU-accelerated, frame delivery at up to display refresh (WWDC22 "Meet ScreenCaptureKit" 10156 / "Take ScreenCaptureKit to the next level" 10155). Practical capture latency is ~1 refresh; queueDepth and holding buffers dominate (UNVERIFIED numbers; measure with `displayTime` vs `mach_absolute_time()` at callback).
- Cursor: with `showsCursor=false` SCK gives no cursor image/position -> Sunna must source cursor separately (section 4.9).
- Resolution/display changes: stream keeps old config; listen for `CGDisplayRegisterReconfigurationCallback` and call `updateConfiguration`. Display removed -> `didStopWithError` `SCStreamErrorNoCaptureSource` (OBS `mac-sck-common.m:36`).
- Stopped by user (menu-bar indicator "Stop sharing") -> `SCStreamErrorUserStopped` (-3817) (OBS `mac-sck-common.m:33`). Permission revoked mid-stream: stream stops with an error (commonly -3801 `userDeclined`) (UNVERIFIED code).
- Lock screen / FUS / login window: at lock (same session) SCK keeps delivering the lock-screen shield for display capture (UNVERIFIED — reports vary; some see `.blank`/`.suspended` when the screen locks). On fast user switch the agent's session goes off-console and its streams stop/suspend; the new console session's agent must capture. Login window capture: needs a LoginWindow-session agent and macOS 14.4+ (section 3.1).
- Known bugs: pre-14.4 SCK unusable in pre-login context (r.121253782); SCK+CGVirtualDisplay works while CGDisplayStream does not (15+); memory leaks in early 12.x/13.x SCK when repeatedly creating streams (UNVERIFIED); SCShareableContent calls can be slow (100s of ms) — cache and refresh on change.


## 2. TCC permissions

### 2.1 Sequoia "bypass the system private window picker" re-prompt
- Wording (15.0 betas): "\"<App>\" is requesting to bypass the system private window picker and directly access your screen and audio." Buttons "Allow For One Month" / "Open System Settings" (button text per 9to5mac/mjtsai; the "Continue To Allow" variant noted by Gruber). Source: https://mjtsai.com/blog/2024/08/08/sequoia-screen-recording-prompts-and-the-persistent-content-capture-entitlement/ ; https://9to5mac.com/2024/08/06/macos-sequoia-screen-recording-privacy-prompt/
- Cadence history:
  - macOS 15.0 beta 1-5 (Jun-Jul 2024): weekly AND after every reboot (9to5mac 2024-08-06).
  - macOS 15.0 beta 6 (Aug 2024) -> 15.0 release (2024-09-16): monthly (30 days), reboot no longer re-prompts (9to5mac 2024-08-14 https://9to5mac.com/2024/08/14/macos-sequoia-screen-recording-prompt-monthly/).
  - macOS 15.1 (beta 6, Oct 2024; release 2024-10-28): "Applications using our deprecated content capture technologies now have enhanced user awareness policies" and users see fewer dialogs for apps they "regularly use" (idownloadblog 2024-10-09 https://www.idownloadblog.com/2024/10/09/macos-sequoia-15-1-macos-screen-recording-prompts-frequency-reduced/ ; MacRumors). Exact heuristic undocumented (UNVERIFIED: widely reported as "no prompt if the app was used in the last ~30 days").
  - macOS 26 Tahoe: no documented change found in this pass; the mechanism (ScreenCaptureApprovals.plist) still exists (UNVERIFIED).
- State: per-app approval timestamps in `~/Library/Group Containers/group.com.apple.replayd/ScreenCaptureApprovals.plist` (TCC/FDA protected; editing to a far-future date was the community workaround) (mjtsai, Jeff Johnson 2024-09-23).
- Trigger: using *non-picker* capture (SCShareableContent/SCStream with a filter the app built itself, and the deprecated CG APIs) after the approval expires. Apps that use `SCContentSharingPicker` (macOS 14+) get consent through the picker each time and are not subject to the "bypass" prompt — but a picker requires a local human, so useless for unattended remote desktop.
- **`com.apple.developer.persistent-content-capture`** (Boolean entitlement, managed capability): documented as "required for a Virtual Network Computing (VNC) app to have persistent access to screen capture" — i.e. suppresses the periodic re-authorization for unattended remote-access products. Request via form https://developer.apple.com/contact/request/persistent-content-capture/ (Apple doc updated ~2024-08-21). Requires a provisioning profile -> Developer ID app with embedded profile; a bare CLI binary cannot carry a managed entitlement without an app bundle + profile. Forum report: app with this entitlement crashing on 10.13.6 (thread 765774) -> profile-carrying binaries must still launch on old OSes; watch min-OS. Known recipients: remote-support vendors (Jump Desktop, TeamViewer, AnyDesk, Splashtop, RustDesk?) are commonly reported to have it (UNVERIFIED individually). Doc: https://developer.apple.com/documentation/bundleresources/entitlements/com_apple_developer_persistent-content-capture ; forum https://developer.apple.com/forums/thread/761641
- MDM: `forceBypassScreenCaptureAlert` (com.apple.applicationaccess Restrictions payload, supervised, macOS 15.1+) suppresses the alert for managed Macs (UNVERIFIED version: reported with 15.1).
- **15.1+ semantics (refined):** ScreenCaptureApprovals.plist moved to a multi-keyed dict; "upon each invocation of an app that requests ScreenCapture permission, the timestamp in the plist is overwritten with the current date/time" -> the nag re-appears only after **~30 days of non-use** (luckman212/screencapture-nag-remover https://github.com/luckman212/screencapture-nag-remover ; https://tinyapps.org/blog/202409180700_disable_sequoia_nag.html). So a daily-used host rarely sees it; a Mac reached remotely once a quarter WILL show it at the moment capture starts, with nobody there to click (unattended deadlock). Workarounds: nag-remover (needs FDA, edits TCC-protected file — not shippable), MDM, or the entitlement.
- MDM: **`forceBypassScreenCaptureAlert`** (Restrictions payload `com.apple.applicationaccess`, macOS **15.1+**; some report it works in `com.apple.TCC` domain) — "allows owners of managed devices to opt out of user notifications for content capture technologies". MDM-only (ScreenCapture TCC profiles can't be self-installed). https://derflounder.wordpress.com/2024/10/31/managing-user-notifications-for-apps-which-request-screen-access-on-macos-sequoia-15-1/ ; Jamf thread https://community.jamf.com/t5/jamf-pro/monthly-tccc-prompts-macos-v15/m-p/328405
- **Implication for Sunna:** the base TCC grant is permanent-ish, but on 15.x without the entitlement the user at the host must click "Allow" roughly monthly — fatal for "unattended remote Mac". Apply for the entitlement early (needs a real app bundle, Developer ID, provisioning profile); fallback: document the prompt and detect it (capture stalls / SCStream error) and surface a notification on the client.

### 2.3 Responsible-process attribution, code identity, revocation
- TCC attributes a request to the **responsible process**: a CLI launched from Terminal/iTerm/VS Code inherits the *terminal app's* grants (Sunna today: the terminal needs Screen Recording + Accessibility, and a prompt names "Terminal"). Launched by launchd (LaunchAgent/Daemon) there is no responsible parent GUI app -> the binary itself is the TCC client, identified by its code signature designated requirement (bundle ID + Team ID for Developer ID signed; **by path/cdhash for ad-hoc/unsigned**, so every rebuild of an unsigned binary invalidates the grant). https://github.com/myn/deskhopplus/issues/41 ("TCC identifies unsigned binaries by path"); rainforestqa TCC deep dive.
- A helper inside an app bundle launched via SMAppService/LaunchAgent with `AssociatedBundleIdentifiers` (RustDesk `agent.plist:8`) is shown under the app's name in Login Items; TCC for a bundled helper executable: if it is a bare Mach-O in Contents/MacOS it is attributed by its own signing identifier (set `-i com.example.sunna` when codesigning; UNVERIFIED whether TCC attributes it to the containing bundle). Safest: make the agent itself a (LSUIElement/LSBackgroundOnly) .app bundle, e.g. `Sunna.app/Contents/Library/LoginItems/SunnaAgent.app`, with stable bundle ID + Team ID; grants survive updates as long as the designated requirement is unchanged (same bundle ID + Team ID). Changing Team ID, bundle ID, or going ad-hoc -> grants lost; stale rows can be reset with `tccutil reset ScreenCapture <bundle-id>` (RustDesk comment `macos.rs:121`).
- Root processes are NOT exempt from TCC for ScreenCapture/PostEvent (a root pre-login agent is a separate TCC client, but at the LoginWindow screen capture of loginwindow is generally permitted for the pre-login agent context; exact TCC rules at login window UNVERIFIED — RustDesk/Jump Desktop do it with the same binary that holds the user grants).
- Revocation mid-capture: toggling Screen Recording off in System Settings stops active SCStreams with an error in `stream:didStopWithError:` (OBS handles generically `mac-sck-common.m:29-49`); CGDisplayStream streams stop delivering. Toggling Accessibility off -> CGEventPost silently no-ops from then on (poll `CGPreflightPostEventAccess()` periodically and report to client). System Settings commonly offers "Quit & Reopen" after enabling Screen Recording — Sunna agent must handle relaunch (KeepAlive in plist).
- MDM PPPC: ScreenCapture (and ListenEvent) **cannot be pre-granted (Allow) by MDM** — only `Deny` or `AllowStandardUserToSetSystemService` (lets a non-admin user approve it; macOS 11+). Accessibility/PostEvent *can* be pre-granted via PPPC for managed devices. (Apple PPPC payload docs; UNVERIFIED this pass.)


## 3. Service realities

### 3.1 Process model (Apple DTS guidance)
- Apple's recommended screen-sharing architecture: a **LaunchDaemon** for global stuff (network, supervision) + a **LaunchAgent** per GUI session that records the screen and posts events; IPC via XPC. "Daemons should not be messing around with GUI stuff, and that includes ScreenCaptureKit." "You should not be doing this from a launchd daemon ever. It has no business connecting to the window server." (Quinn/DTS) https://developer.apple.com/forums/thread/814152 ; https://developer.apple.com/forums/thread/768146
- For daemons `LimitLoadToSessionType` is ignored ("daemons are always loaded into the global session"). For pre-login support set the agent's `LimitLoadToSessionType` to `[Aqua, LoginWindow]` — exactly what RustDesk does (`rustdesk/src/platform/privileges_scripts/agent.plist:11-14`). Pre-login agents run **as root** in the LoginWindow session (Apple PreLoginAgents sample); keep that agent small, don't run the whole GUI app as root.
- **SCK at the login window works on macOS 14.4+** ("In macOS 14.4 we fixed a bug that prevents you from using ScreenCaptureKit in the pre-login context (r. 121253782)"; DTS prototyped it). Before 14.4 you needed CGDisplayStream there. (thread 814152). A different poster (thread 768146, macOS 15) reported none of CGDisplayCreateImage/CGDisplayStream/AVCaptureScreenInput/SCK worked pre-login from their *daemon*/root GUI app — consistent with wrong context, not an API limit.
- **Implication for Sunna:** ship host as app bundle containing (a) root LaunchDaemon (network/QUIC listener, session broker), (b) LaunchAgent with LimitLoadToSessionType [Aqua, LoginWindow] doing SCK+CGEventPost, one instance per GUI session, XPC/UDS to the daemon; handoff on login/logout/fast-user-switch by the daemon routing the stream to the console-owning session's agent (RustDesk tracks console UID via /dev/console owner, `macos.rs:702`). Minimum OS for login-window capture via SCK: 14.4.

## 5. Audio capture
- **SCK audio** (macOS 13.0+): `capturesAudio=true`, 48 kHz float, per-filter (display filter = all system audio; app filter = those apps' audio), `excludesCurrentProcessAudio`. Covered by the *Screen Recording* grant and thus by the Sequoia re-prompt; delivered on the same SCStream as video (OBS `mac-sck-video-capture.m:220-224`, `mac-sck-common.m:21`). Microphone via SCK 15.0+ (`captureMicrophone`).
- **Core Audio process taps** (macOS 14.2 API; permission flow reliable from 14.4 — insidegui/AudioCap targets "macOS 14.4+" https://github.com/insidegui/AudioCap): `CATapDescription` (e.g. `initStereoGlobalTapButExcludeProcesses:`), `AudioHardwareCreateProcessTap`, then a (private) aggregate device whose `kAudioAggregateDeviceTapListKey` contains the tap; read via IOProc. Sunshine does exactly this: `Sunshine/src/platform/macos/av_audio.mm:629,660,486` and aggregate dict ~`:694-699`.
  - Permission: separate TCC service **kTCCServiceAudioCapture**, shown as "System Audio Recording Only" under Privacy & Security > Screen & System Audio Recording; Info.plist `NSAudioCaptureUsageDescription` required (not in Xcode dropdown). Prompt appears on first `AudioHardwareCreateProcessTap` for a properly signed binary. **Without permission the tap is created and AudioDeviceStart returns noErr but the IOProc delivers zeros** (silent failure). No public preflight API (AudioCap uses private TCC SPI `TCCAccessPreflight`; cached per process). Sources: https://developer.apple.com/documentation/coreaudio/audiohardwarecreateprocesstap(_:_:) ; https://github.com/moona3k/macparakeet/issues/924 ; https://dgrlabs.co/blog/2026-04-25-capturing-system-audio-on-macos-in-2026.html
  - Not subject to the Sequoia screen-recording monthly re-prompt (it is a different service) (inference; UNVERIFIED).
  - **Muting local output:** `tapDescription.muteBehavior = CATapMuted` (audio only to tap) / `CATapUnmuted` / `CATapMutedWhenTapped`; Sunshine `av_audio.mm:~649-653`. This is the clean way to implement "mute host speakers while streaming" — no virtual driver needed.
- **Virtual drivers (historical):** Soundflower, BlackHole, Loopback (Rogue Amoeba ACE), Background Music — AudioServerPlugIn HAL drivers installed in /Library/Audio/Plug-Ins/HAL, require admin install + coreaudiod restart, change the user's default output device. Obsolete for Sunna on 14.4+.
- **Implication:** Sunna should use Core Audio taps (independent permission, no monthly prompt, local mute) on 14.4+, with SCK audio as fallback (13.0-14.3). Detect silent-zero failure by RMS==0 for N seconds after start + permission hint.


## 6. Clipboard
- Change detection: `NSPasteboard.general.changeCount` polling (e.g. every 250-500 ms) is the only public mechanism (no notification API). Reading `changeCount` did not trigger the privacy alert in developer testing (deskhopplus #41 https://github.com/myn/deskhopplus/issues/41).
- **Pasteboard privacy (macOS 15.4 developer preview):** macOS 15.4 added `NSPasteboard.accessBehavior` (`NSPasteboard.AccessBehavior`: `.default`, `.ask`, `.alwaysAllow`, `.alwaysDeny`) — header: default for the general pasteboard is "to ask upon programmatic access", exempt only if "user originated and paste related" (Cmd-V / Edit>Paste). New `detect` APIs (`detectPatterns(for:)`, `detectMetadata(for:)`, `detectValues(for:)` on NSPasteboard and NSPasteboardItem) let an app inspect *kinds* of data without triggering the alert. Opt-in test: `defaults write <bundle-id> EnablePasteboardPrivacyDeveloperPreview -bool yes` (side effect: app main menu moves to TrustedUIService). Apple said enforcement would come "in a future release". https://mjtsai.com/blog/2025/05/12/pasteboard-privacy-preview-in-macos-15-4/ ; https://lapcatsoftware.com/articles/2025/5/3.html ; https://developer.apple.com/documentation/appkit/nspasteboard/accessbehavior-swift.enum ; FB17587626 (no API to programmatically request full access) https://github.com/feedback-assistant/reports/issues/655
- macOS 26 status: as of mid-2026 **announced but not enforced by default** (per 2026 third-party reporting, e.g. dev.to Tahoe clipboard-history article; UNVERIFIED against Apple release notes). Users will get an Allow/Deny per app in Privacy & Security when enabled.
- Whether a CLI/unbundled binary gets the alert is untested (deskhopplus #41 saw no alert for unsigned CLI, flagged as possibly different for .app bundles).
- **Implications for Sunna clipboard sync:** (1) poll `changeCount` only; (2) on change, use `detectPatterns`/`types` (types list reading: whether it alerts is UNVERIFIED) and only *read* contents lazily — ideally when the client actually pastes (promise-based / on-demand fetch over the control channel, like RDP's CLIPRDR format-list-then-data model); (3) writing to the pasteboard is not gated; (4) design for a one-time "Allow" in Privacy & Security, with a UX explaining it; (5) respect `org.nspasteboard.ConcealedType` / `TransientType` markers (password managers) and never sync those.
