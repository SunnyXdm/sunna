# DeskPad (CGVirtualDisplay) and SudoVDA (IddCx) notes (researched directly)

## DeskPad (/home/sunny/research-repos/DeskPad, HEAD c3349f0, 2026-02-28)
- Private header `DeskPad/CGVirtualDisplayPrivate.h:15-70` (originally by Khaos Tian, 2021-02-17) declares four ObjC classes from CoreGraphics: `CGVirtualDisplayMode` (width, height, refreshRate; `initWithWidth:height:refreshRate:`), `CGVirtualDisplaySettings` (`modes` array, `hiDPI` uint), `CGVirtualDisplay` (`initWithDescriptor:`, `applySettings:` -> BOOL, readonly `displayID`, `modes`, `hiDPI`, `maxPixelsWide/High`, `sizeInMillimeters`, `name`, `serialNum`, `productID`, `vendorID`, `terminationHandler`, `queue`), `CGVirtualDisplayDescriptor` (settable `queue`/`setDispatchQueue:`, `name`, `maxPixelsWide/High`, `sizeInMillimeters`, `serialNum`, `productID`, `vendorID`, `terminationHandler` block `(id, CGVirtualDisplay*)`).
- Usage `DeskPad/Frontend/Screen/ScreenViewController.swift:24-61`: descriptor queue = main; name "DeskPad Display"; `maxPixelsWide=5120`, `maxPixelsHigh=2160`; `sizeInMillimeters=1600x1000` (physical size drives macOS's default "looks like" scaling/DPI); fake `productID=0x1234`, `vendorID=0x3456`, `serialNum=1` (macOS persists per-display arrangement/resolution keyed by vendor/product/serial, so a stable triple = remembered layout; a unique serial per client would give per-client memory). `settings.hiDPI = 1` and 15 modes, all 60 Hz, 1280x720 .. 5120x2160 (lines 40-60). With hiDPI=1 macOS offers each mode as a 2x "looks like" mode (so a 2560x1600 mode yields a 1280x800-points HiDPI option) (behaviour inferred from DeskPad UI; UNVERIFIED exact rule).
- The display exists only while the `CGVirtualDisplay` object is alive in the creating process (DeskPad keeps it in a property, line 15/36); when the process exits the display disappears ("Launching the app is equivalent to plugging in a monitor", README). Implication: Sunna's host process (the per-user LaunchAgent) must own it; a crash unplugs the display and macOS re-arranges windows back.
- Capture of the virtual display in DeskPad uses deprecated `CGDisplayStream(dispatchQueueDisplay:outputWidth:outputHeight:pixelFormat: 'BGRA' (1111970369) ...)` with `showCursor: true` and sets the IOSurface directly as `layer.contents` (lines 86-102): zero-copy display of an IOSurface in a CALayer. DeskPad needs Screen Recording permission for this (README troubleshooting), but creating the virtual display itself does not require a TCC permission or entitlement (no .entitlements file in repo).
- Resolution change detection: `NSApplication.didChangeScreenParametersNotification` then read `NSScreen.frame.size` and `backingScaleFactor` for the virtual display's `displayID` (`Backend/ScreenConfiguration/ScreenConfigurationSideEffect.swift:14-28`). The stream is recreated at `points * scaleFactor` pixels on every change (ScreenViewController.swift:75-103).
- Mode switching is done by the user in System Settings; programmatic switching would use `CGDisplayCopyAllDisplayModes`/`CGConfigureDisplayWithDisplayMode` (public) on the virtual displayID (not shown in DeskPad).
- Critical: private API, no ABI promise; property names come from class-dump. `applySettings:` can be called again to replace the mode list (e.g., add an exact client-sized mode on the fly), which is how resolution-follow can be built (UNVERIFIED that re-apply works without re-creating the display on all macOS versions; the VideoToolbox/virtual-display agent notes cover version breakage).

## SudoVDA (/home/sunny/research-repos/SudoVDA, last commit 2025-04-15)
- Rewrite of Microsoft's IddCx Indirect Display sample (README). User-mode driver (UMDF), MIT/CC0. Modes 640x480..7680x4320, refresh up to 500 Hz; HDR only fully on Windows 11 24H2 (README "Notice").
- Registry config `HKLM\SOFTWARE\SudoMaker\SudoVDA`: `gpuName`, `maxMonitors` (default 10), `watchdog` (default 3 s), `sdrBits` (8/10), `hdrBits` (10/12) (README; read at `Driver.cpp:323-356`).
- Control plane = device IOCTLs on interface GUID `{e5bcc234-1e0c-418a-a0d4-ef8b7501414d}`: `IOCTL_ADD_VIRTUAL_DISPLAY (0x800)` with `{Width, Height, RefreshRate, MonitorGuid, DeviceName[14], SerialNumber[14]}` returning `{AdapterLuid, TargetId}`; `IOCTL_REMOVE_VIRTUAL_DISPLAY (0x801)` by GUID; `IOCTL_SET_RENDER_ADAPTER (0x802)` (choose which GPU renders the IDD — critical on hybrid GPUs so the encoder GPU owns the surface); `IOCTL_GET_WATCHDOG (0x803)`; `IOCTL_DRIVER_PING (0x888)`; `IOCTL_GET_PROTOCOL_VERSION (0x8FF)` (`Common/Include/sudovda-ioctl.h:10-64`).
- Watchdog: every IOCTL except GET_WATCHDOG resets the countdown (`Driver.cpp:1488-1491`); a thread decrements once per second and calls `DisconnectAllMonitors()` at zero (`Driver.cpp:380-400`). Apollo pings every `timeout/3` seconds and gives up after 3 failed pings (`Apollo/src/platform/windows/virtual_display.cpp:601-618`). Pattern worth stealing on every OS: virtual displays are leased, not owned — if the host dies, the display unplugs itself within seconds instead of leaving the user's desktop stranded on an invisible monitor.
- Per-monitor EDID generated from a base EDID with the requested preferred mode spliced in (`Driver.cpp:845-900`, mode lists at `1068-1140`); monitor reported as `DISPLAYCONFIG_OUTPUT_TECHNOLOGY_HDMI`. HDR path uses IddCx 1.10 `*2` callbacks (`EvtIddCxAdapterQueryTargetInfo`, `ParseMonitorDescription2`, `MonitorQueryTargetModes2`, `AdapterCommitModes2`, `SetDefaultHdrMetadata`, `SetGammaRamp`) when available (`Driver.cpp:487-499`) and advertises `IDDCX_ADAPTER_FLAGS_CAN_PROCESS_FP16` (`Driver.cpp:795-796`).
- The swap-chain loop (`Driver.cpp:647-760`) acquires each frame and immediately releases it — SudoVDA does not capture or encode inside the driver; Apollo/Sunshine capture the virtual monitor with DDA/WGC like a real display. The sample comments note the driver could encode directly in `ReleaseAndAcquireBuffer` (lowest-latency path, Parsec-VDD-style designs) — not done here.
- Hardware cursor: `IddCxMonitorSetupHardwareCursor` with alpha + full XOR support, 64x64 max (`Driver.cpp:955-975`): the OS then does NOT composite the cursor into the IDD surface, so the streamer must fetch the cursor shape separately (DDA pointer shape / `IddCxMonitorQueryHardwareCursor`) — i.e., client-side cursor by construction.
- Apollo applies the requested mode via `ChangeDisplaySettingsEx` with a fallback of +/-1 Hz for fractional rates (`virtual_display.cpp:271-295`).
- Signing: IddCx drivers must be attestation-signed through the Microsoft Hardware Dev Center (EV cert) to load on consumer Windows with Secure Boot (general Windows driver policy; UNVERIFIED for SudoVDA's specific release signing).
