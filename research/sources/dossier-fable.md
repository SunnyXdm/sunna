## 0. Executive summary (read this first)

- **RustDesk (v1.5.0, HEAD e9ddbd8 of 2026-09-25)** is a TCP-framed protobuf protocol (length-prefixed `Message` oneofs) with a rendezvous server (hbbs) and a byte-copying relay (hbbr), NaCl (sodiumoxide) key exchange, and — new since ~1.4/1.5 — three optional direct UDP paths (KCP-over-UDP punch, IPv6 punch, and a full WebRTC/DTLS/SCTP path via webrtc-rs) raced against TCP punch and relay with a 2.5 s "relay fallback delay". Its video path is still **frame-paced by a sleep loop and back-pressured by TCP writes**: the capture thread sends a frame, then blocks up to 3 s until every connection's send completes (or the client acks), then sleeps the remainder of `1/fps`. Its QoS reacts to a `TestDelay` ping that rides *inside* the video stream, measuring queue depth rather than RTT, and adjusts FPS first, bitrate second, every 3 s. This is why it feels laggy and blurry under load compared with Parsec/Moonlight, despite hardware H.264/H.265 being available on all desktop OSes (hwcodec/ffmpeg; VideoToolbox on macOS) and a VRAM zero-copy path on Windows.
- **Ease of use**: RustDesk's "ID + one-time password" model needs zero accounts, but macOS onboarding is four sequential cards (Screen Recording → Accessibility → Input Monitoring → Install daemon via osascript admin prompt) each requiring a manual re-check, and the client shows nothing about *why* a connection is slow. Parsec's account-based "computers just appear" model plus one Hosting toggle remains the ease benchmark (detail in §4–5).
- **Tailscale/iroh** (§3): both use the same magicsock design — one UDP socket, encrypted "disco" pings to every candidate endpoint, a TCP/HTTPS relay (DERP) that also carries the first packets, and an upgrade to direct once a pong arrives. iroh's key contribution for Sunna: it implements quinn's `AsyncUdpSocket` so QUIC sees one stable fake address per peer while the real path switches underneath — no QUIC migration needed. This is the design Sunna should copy (or embed).
- **Security** (§6): none of the ID/password products are E2E against their own rendezvous server unless the peer key is pinned out-of-band; RustDesk's `secure` flag depends on the hbbs `-k` key; the scam problem is real and RustDesk's mitigation is mostly UI text (a scam banner on the Android host page, no equivalent on desktop) plus lockouts.

Detailed sections follow (§1B precedes §1A because it was written first; both are complete).

## 1B. RustDesk: media pipeline, QoS, input, platform integration (from source)

Repo: `/home/sunny/research-repos/rustdesk` (version `1.5.0`, `Cargo.toml:3`; HEAD `e9ddbd8f` dated 2026-09-25). Protos live in `libs/base/protos/message.proto` (moved from `libs/hbb_common/protos`).

### 1B.1 Wire messages that matter for media/input

- `VideoFrame { oneof union { EncodedVideoFrames vp9s=6; RGB rgb=7; YUV yuv=8; h264s=10; h265s=11; vp8s=12; av1s=13 }; int32 display=14 }` and `EncodedVideoFrame { bytes data=1; bool key=2; int64 pts=3 }` — `/home/sunny/research-repos/rustdesk/libs/base/protos/message.proto:4-36`. One protobuf message per encoded frame, on the same TCP stream as everything else (no sequence numbers, no FEC, no per-packet timestamps; reliability and ordering are TCP's).
- `TestDelay { int64 time; bool from_client; uint32 last_delay; uint32 target_bitrate }` — `message.proto:700-705`. The host sends one every `TEST_DELAY_TIMEOUT` tick and the client echoes it; the round trip is the *only* network signal the QoS uses (see 1B.3).
- `KeyEvent { bool down; bool press; oneof { ControlKey control_key; uint32 chr (position keycode: win scancode / linux keycode / mac keycode); uint32 unicode; string seq; uint32 win2win_hotkey }; repeated ControlKey modifiers; KeyboardMode mode }` — `message.proto:293-311`; `enum KeyboardMode { Legacy=0; Map=1; Translate=2; Auto=3 }` — `message.proto:199-204`.
- `MouseEvent { int32 mask; sint32 x; sint32 y; repeated ControlKey modifiers }` — `message.proto:192-197`. Mask layout from `src/common.rs:68-91`: low 3 bits = type (`MOVE=0, DOWN=1, UP=2, WHEEL=3, TRACKPAD=4, MOVE_RELATIVE=5`, `MOUSE_TYPE_MASK=0x7`), buttons in `mask >> 3` (`LEFT=0x01, RIGHT=0x02, WHEEL(middle)=0x04, BACK=0x08, FORWARD=0x10`). Coordinates are absolute in the virtual desktop coordinate space (multi-monitor offsets come from `DisplayInfo.x/y`).
- `CursorData { uint64 id; sint32 hotx, hoty; int32 width, height; bytes colors }` and `CursorPosition { sint32 x, y }` — `message.proto:312-327`. Cursor is **not** baked into the video on macOS (`CGDisplayStream` config `cursor: false`, `libs/scrap/src/quartz/config.rs:69`) nor Windows; only X11 may embed it (`libs/scrap/src/common/mod.rs:273-279`). Cursor shape is sent as a separate message with a 64-entry shape cache (`src/server/input_service.rs:436`), and cursor position is polled by a `mouse_cursor` service (`src/server/input_service.rs:300-386`).
- `DisplayInfo { sint32 x, y; int32 width, height; string name; bool online; bool cursor_embedded; Resolution original_resolution; double scale }` — `message.proto:38-49`; `SwitchDisplay`, `CaptureDisplays { repeated int32 add, sub, set }` (`message.proto:600-616`) support switching displays or capturing several at once (each display is its own `video_service` instance, `src/server/video_service.rs:296-320`).
- `LoginRequest { username (= target ID); bytes password; my_id; my_name; OptionMessage option; oneof { FileTransfer; PortForward; ViewCamera; Terminal }; bool video_ack_required; uint64 session_id; string version; OSLogin os_login; my_platform; bytes hwid; avatar }` — `message.proto:68-88`. `OptionMessage` (`message.proto:671-699`) carries per-session toggles: `image_quality`, `custom_image_quality`, `custom_fps`, `show_remote_cursor`, `privacy_mode`, `block_input`, `disable_audio/clipboard/keyboard`, `enable_file_transfer`, `supported_decoding`, `follow_remote_cursor/window`, `terminal_persistent`, `show_my_cursor`.
- `SupportedDecoding { PreferCodec prefer (Auto/VP9/H264/H265/VP8/AV1); ability_vp9/h264/h265/vp8/av1; CodecAbility i444; Chroma prefer_chroma }` — `message.proto:651-669`.

### 1B.2 Codecs and quality modes

**Negotiation** (`libs/scrap/src/common/codec.rs:171-260`): every connected client's `SupportedDecoding` is stored in `PEER_DECODINGS`; the host computes `h264_useable = all peers decode H264 && (VRAM encoder available || hwcodec encoder available)` (same for H265), `vp8_useable`, `av1_useable`; then takes the *most frequent* client preference among usable ones. If nobody expresses a usable preference, the format stays at the previous `ENCODE_CODEC_FORMAT` (default `VP9`). Any encoder creation failure falls back to VP9 (`codec.rs:162-166`, `src/server/video_service.rs:668-680`). So with one client on "Auto", **RustDesk uses VP9 software unless the client explicitly prefers H264/H265** — the client-side default preference is `Auto`, which maps to no preference, and that is a major reason for CPU load and softness on Macs (UNVERIFIED for the Flutter default of the `codec-preference` option; the Rust side treats `Auto` as "no vote").

**Encoder backends**: `EncoderCfg::{VPX (libvpx VP8/VP9), AOM (libaom AV1), HWRAM (ffmpeg-based `hwcodec` crate: NVENC/AMF/QSV/VAAPI/VideoToolbox/MediaCodec into system RAM), VRAM (Windows-only D3D11 texture path)}` — `codec.rs:134-168`, `libs/scrap/src/common/hwcodec.rs:61-110`. `support_changing_quality()` is false for VAAPI (`hwcodec.rs:193-195`), meaning a VAAPI host must *recreate the encoder* to change bitrate (`video_service.rs:1418-1440` bails `SWITCH`), and `latency_free()` is false for `mediacodec`/`videotoolbox` (`hwcodec.rs:198`), which makes the loop *re-encode the last frame up to 10 times* when capture returns WouldBlock so the decoder pipeline drains (`video_service.rs:726-727, 911-926`).

**libvpx settings** (`libs/scrap/src/common/vpxcodec.rs:52-160`): `g_timebase = 1/1000`, `rc_undershoot_pct = 95`, `rc_dropframe_thresh = 25`, `g_threads = codec_thread_num(64)` (a load-average-derived count, `codec.rs:975-1000`), `g_error_resilient = DEFAULT`, `rc_end_usage = VPX_CBR`, `kf_mode = VPX_KF_DISABLED` unless recording (then `kf_max_dist = 240`, `video_service.rs:1079`), `rc_min/max_quantizer` from `calc_q_values(quality)`, `g_profile = 1` for VP9 4:4:4; VP9 `VP8E_SET_CPUUSED = 7`, `VP9E_SET_ROW_MT = 1`, `VP9E_SET_TILE_COLUMNS = 4`; VP8 `CPUUSED = 12`. Encode is called with `VPX_DL_REALTIME` via `encode()`.

**hwcodec settings** (`hwcodec.rs:28-31, 61-110`): `AV_PIX_FMT_NV12`, `fps = 30` (fixed in the encoder context), `gop = i32::MAX` (infinite GOP unless recording), `quality = Quality_Default`, rate control default (`rate_control()`, `hwcodec.rs:243-249`), bitrate = `base_bitrate(w,h) * ratio`, H.264 vs H.265 factor in `calc_bitrate` (`hwcodec.rs:255-280`).

**Bitrate model** (`codec.rs:893-970`): `base_bitrate(w,h)` interpolates a preset table — 640×480→400 kbps, 1280×720→1000, 1920×1080→2073, 2560×1440→3000, 3840×2160→5000, 7680×4320→12000 — scaled linearly by pixel count. The user's quality mode is a multiplier: `Best = 1.5`, `Balanced = 0.67`, `Low ("Optimize reaction time") = 0.5`, `Custom(x)` where the slider value maps via `((q >> 8) & 0xFFF) * 2 / 100` clamped to `[0.2, 40.0]` (`src/server/video_qos.rs:435-455`). So a 2560×1664 Retina display at "Best" targets roughly 3.5×1.5 ≈ 5.2 Mbps, and at "Balanced" ≈ 2.3 Mbps — an order of magnitude below Apple HP mode's ~75 Mbps and Parsec's 10–50 Mbps defaults. This, not the codec, is the root of "blurry".

**4:4:4**: only for VP9 (profile 1) and AV1 via libaom, never for hardware H.264/H.265 (`codec.rs:403-419`); requires every client to set `prefer_chroma = I444` (toolbar option `i444`, `flutter/lib/common/widgets/toolbar.dart:1012`).

### 1B.3 QoS: fps-first, bitrate-second, driven by an in-band ping

`src/server/video_qos.rs` constants (`:51-67`): `FPS = 30`, `MIN_FPS = 1`, `MAX_FPS = 120`, `INIT_FPS = 15`, `MIN_AUTO_FPS = 5`, `BR_MAX = 40.0`, `BR_MIN = 0.2`, `BR_MIN_HIGH_RESOLUTION = 0.1`, `HISTORY_DELAY_LEN = 2`, `ADJUST_RATIO_INTERVAL = 3` s, `DYNAMIC_SCREEN_THRESHOLD = 2` encodes/s, `DELAY_THRESHOLD_150MS = 150`, `RESTORE_GUARD_SAMPLES = 5`.

- The design comment (`video_qos.rs:40-48`) is candid: *"TestDelay shares the video stream, so it measures the queue in front of it rather than the path RTT."* The host emits `TestDelay` on `test_delay_timer` (`src/server/connection.rs:699-700, 1174-1195`), records `network_delay` when the echo returns (`connection.rs:3086-3100`), and if a probe stays out > 2 s it halves fps for every extra second (`video_qos.rs:600-636`).
- `user_network_delay()` (`video_qos.rs:463-598`) decides a per-user fps target from delay history and then `adjust_fps()` takes the minimum across users, clamped to the user's `custom_fps` cap; every viewer's first second is pinned to `INIT_FPS = 15` (`video_qos.rs:818-841`). Bitrate ratio changes happen only in `adjust_ratio()` at most every 3 s: on confirmed congestion (three bad replies) multiply by a reduction factor; if delay < 50 ms and the screen is dynamic, ×1.15; < 100 ms ×1.10; otherwise ×1.05; increases are capped to +150 kbps per step (`video_qos.rs:731-816`). Floors: `Best` can drop to `1.5/2.5 = 0.6`, `Balanced` to `min(0.335, 0.4)`, all bounded by "about 1 Mbps" (`video_qos.rs:689-719`).
- Consequence: recovery from a congestion event is slow (+150 kbps every 3 s) and the controller cannot distinguish path RTT from its own queue. There is no receiver-side rate estimate, no loss signal (TCP hides it), and no pacing.

### 1B.4 Frame pipeline and where latency is spent

`video_service::run` (`src/server/video_service.rs:595-1000`) is a single thread per display:

1. `check_qos()` reads `spf = 1/fps` and re-applies bitrate if the ratio changed (`:1418-1440`).
2. `c.frame(spf)` — on macOS `CGDisplayStream` with `queue_length: 3`, `throttle: 0.0`, cursor off (`libs/scrap/src/quartz/config.rs:65-72`); frames arrive on a dispatch queue and the capture thread `try_lock`s the latest one, converting IOSurface → BGRA on the CPU (`surface_to_bgra`, `libs/scrap/src/common/quartz.rs:48-70`); an unchanged frame is detected by *comparing the raw pixel data* (`would_block_if_equal`) and returns WouldBlock. No dirty rects. No ScreenCaptureKit for video (SCK is only used as a cpal audio host, `src/server/audio_service.rs:176-206`).
3. `frame.to(encoder.yuvfmt(), ...)` converts BGRA→I420/NV12 on the CPU (libyuv), then `handle_one_frame` encodes and `sp.send_video_frame(msg)` fans the protobuf out to each connection's channel (`:1237-1300`).
4. **Back-pressure wait**: the loop then blocks up to `3_000` ms, polling in 300 ms slices, until `FRAME_FETCHED_NOTIFIERS` reports every subscribed connection has "fetched" the frame (`:975-987`, `VideoFrameController::try_wait_next` `:205-250`). "Fetched" means the connection task finished `conn.stream.send(...)` — i.e. the bytes were written into the TCP socket — unless the client set `video_ack_required`, in which case it means the client sent back `Misc::VideoReceived` (`connection.rs:1073-1080, 3879-3884`). The Flutter desktop client does not set `video_ack_required` (no setter found outside the host; UNVERIFIED for web client).
5. `std::thread::sleep(spf - elapsed)` (`:993-995`).

So the effective frame period is `max(1/fps, TCP write time)`, a fresh frame is never captured while the previous one is still being written, and when the socket buffer is full (Wi-Fi hiccup) the host simply stops capturing. On the client (`src/client.rs:4000-4110`) frames are pulled from an `ArrayQueue` of `VIDEO_QUEUE_SIZE = 120` (`client.rs:111`) by one decode thread; there is a `discard_queue` flag that drops queued frames on some events, but no deadline-based dropping, so a 120-frame backlog (4 s at 30 fps) can build up and play out late. Decoded output goes to `ImageRgb` (CPU) or, with `use-texture-render`, a platform texture (`client.rs:2662-2760`; Windows D3D path gated by `allow-d3d-render`). `custom-fps` defaults to 30 and values above 30 require the host to advertise support (`client.rs:3413-3419`).

### 1B.5 Audio

Host: Opus via `magnum_opus::Encoder::new(48000, Stereo, LowDelay)` (`src/server/audio_service.rs:102-106`; `PA_SAMPLE_RATE = 48000`, `src/platform/mod.rs:90`), 10 ms packets (`AUDIO_DATA_SIZE_U8 = 960*4`, `AUDIO_PACKETS_PER_SECOND = 100`, `audio_service.rs:24, 202`), no explicit bitrate set (Opus default ~64–128 kbps VBR; UNVERIFIED for the crate default). On macOS, loopback capture uses cpal's ScreenCaptureKit host when available (`audio_service.rs:176-206`). Client: a PCM ring buffer sized `AUDIO_BUFFER_MS = 3000` ms (`src/client.rs:133`) with capacity-discard on overflow (`client.rs:2294-2330`). Audio frames share the TCP stream with video and input (head-of-line blocking).

### 1B.6 Clipboard and file transfer

Clipboard: polled every `CLIPBOARD_INTERVAL = 333` ms (`src/clipboard.rs:15`) via `arboard`, formats Text/HTML/RTF/ImageRgba/ImagePng/ImageSvg/FileUrl/Excel-XML plus an owner marker `dyn.com.rustdesk.owner` to avoid echo (`clipboard.rs:29-71`); 3 retries at 33 ms when the clipboard is busy (`:45-47`). File copy-paste between machines uses a CLIPRDR-style protocol (`Cliprdr*` messages, `message.proto:514-587`) originally Windows-only, now behind `unix-file-copy-paste` (`connection.rs:716-733`). File transfer: job-based `FileTransferSendRequest`/`FileTransferBlock { id; file_num; data; compressed; blk_id }` (`message.proto:447-495`) with per-file digest for overwrite detection and resume (`libs/base/src/fs.rs:260, 401-420, 663-665`), files with already-compressed extensions skip compression (`fs.rs:457-460`).

### 1B.7 Keyboard modes and cross-OS handling

Client side (`src/keyboard.rs`): `get_keyboard_mode_enum` maps `"map" | "translate" | "legacy"`, default **Map** (`:758-765`). `event_to_key_events` (`:940-989`) dispatches per mode and then appends lock-state modifiers (CapsLock/NumLock) except in Translate mode.

- **Legacy** (`:1018-1245`): "Generate characters locally, look for keycode on other side" — sends `ControlKey` for specials and `chr`/`unicode` for characters plus a modifier snapshot captured from the *local* key state (`get_key_state`), with a Windows AltGr hack (`IS_ALT_GR`).
- **Map** (`:1247-1330`): sends the *physical position* code translated into the peer OS's keycode space: from Windows `position_code` via `rdev::win_scancode_to_macos_code` (or `_iso_` variant if the local layout is ISO, `LocalConfig::get_kb_layout_type()`), `win_scancode_to_linux_code`, `win_scancode_to_android_key_code`; from macOS `macos_code_to_win_scancode` etc. Scancodes > 255 without the 0xE0 prefix are dropped (`#1371`). Windows peers get `Pause` as a legacy control key (`windows_peer_special_key`).
- **Translate** (`:1459-1530`): dead keys are swallowed (`unicode_info.is_dead`), numpad keys fall back to Map, macOS right-Option is ignored, AltGr is ignored on Linux/Windows, Windows→Windows hotkeys are carried as `win2win_hotkey`, and printable characters are sent as `unicode` (`try_fill_unicode`) unless the left Option is down on macOS; anything else falls back to Map.
- Mode support matrix (`src/common.rs:1910-1927`): Legacy always; Map requires peer ≥ 1.2.0 and not Android; Translate/Auto require ≥ 1.2.0.

Host side (`src/server/input_service.rs`): `handle_key_` (`:2397-2456`) first builds a `LockModesHandler` that toggles CapsLock/NumLock on the host to match the client's lock flags (sleeping 10–50 ms to make sure the LED state settled, `:186-231`), then dispatches: Map → `sim_rdev_rawkey_position(chr)` (X11) or `wayland_send_raw_key` via uinput/portal (`:1633-1657`); Translate → unicode/seq injection with a Wayland clipboard-paste fallback for non-ASCII (`:2172-2300`); Legacy → `sync_modifiers` presses any modifier the client listed that isn't pressed on the host and releases extras (`:1701-1760`), then `process_control_key`/`process_chr`/`process_unicode`/`process_seq` (`:2118-2162`). On macOS all modifiers are expressed as CGEvent *flags* (`add_flags_to_enigo`, `:1661-1670`) rather than separate key events. Pressed keys are tracked in `KEYS_DOWN` and released by `fix_key_down_timeout_loop`/`_at_exit` (`:930-960, 1018-1034`) — a periodic sweep rather than an on-disconnect release. Modifier "swap Cmd/Ctrl" is a client-side option (`swap-control-command`, seen in toolbar). Relative mouse mode for games exists since 1.4/1.5: `MOUSE_TYPE_MOVE_RELATIVE` with a `MAX_RELATIVE_MOUSE_DELTA = 10000` clamp and an exit hotkey (Cmd+G on macOS, Ctrl+Alt elsewhere) (`input_service.rs:1257-1290`, `keyboard.rs:33-58`). Scroll: `MOUSE_TYPE_WHEEL` (steps) and `MOUSE_TYPE_TRACKPAD` (pixel-ish, `en.mouse_scroll_x/y(v, is_track_pad)`, `:1329-1377`) — no scroll phase/momentum forwarding. Pinch comes through `PointerDeviceEvent.TouchEvent.scale_update` and is turned into Ctrl+wheel (`:1389-1450`).

### 1B.8 Multi-monitor, virtual display, privacy mode

- Each physical display is a separate `video_service` (`video_service.rs:296-320`); `CaptureDisplays{add/sub/set}` lets a client subscribe to several, and the Flutter client can open them as individual windows (`OPTION_DISPLAYS_AS_INDIVIDUAL_WINDOWS`, `libs/base/src/config/keys.rs`). Display changes are checked once a second (`video_service.rs:790-797`).
- Virtual display is **Windows-only** (RustDesk IDD or Amyuni IDD, `src/virtual_display_manager.rs:6-12`, up to 5 virtual monitors, `:143`, "headless" plug-in when no monitor is attached, `src/server/display_service.rs:797-835`). No macOS or Linux virtual display.
- Privacy mode: Windows has three implementations (Magnifier API, `SetWindowDisplayAffinity` exclude-from-capture, and a virtual-display trick; `src/privacy_mode.rs:40-43`, `src/privacy_mode/win_*.rs`); macOS got one in 1.5 that **blacks out every display's gamma table and installs a CGEventTap to swallow local input** (`src/platform/macos.mm:715-847`, `src/privacy_mode/macos.rs`) — a fragile approach (gamma can be reset by the OS, and an event tap dies if the app is unresponsive).

### 1B.9 macOS permissions, daemon/agent model, login window

- Permission checks: Accessibility via `AXIsProcessTrustedWithOptions(kAXTrustedCheckOptionPrompt)` (`src/platform/macos.rs:95-105`); Input Monitoring via `IOHIDCheckAccess/IOHIDRequestAccess(kIOHIDRequestTypeListenEvent)` (`src/platform/macos.mm:48-64`); Screen Recording via `CGPreflightScreenCaptureAccess/CGRequestScreenCaptureAccess` on ≥ 11 (`macos.mm:32-34`), else the `CGWindowListCopyWindowInfo` window-name heuristic (`macos.rs:122-181`).
- Onboarding order in the Flutter home page (`flutter/lib/desktop/pages/desktop_home_page.dart:478-503`): one card at a time — Screen Recording → Accessibility → Input Monitoring → "Install daemon" — each "Configure" button triggers the OS prompt and a watcher re-polls until granted (`:722-740`). Input Monitoring is requested even for outgoing-only builds. There is no restart-required detection beyond re-polling.
- Service install (`macos.rs:189-251`): runs `osascript` with an embedded `install.scpt` that asks for admin credentials and writes **two plists**: a root LaunchDaemon `com.carriez.RustDesk_service` running `Contents/MacOS/service` (KeepAlive) and a LaunchAgent `com.carriez.RustDesk_server` with `LimitLoadToSessionType = [LoginWindow, Aqua]` running `RustDesk --server` (`src/platform/privileges_scripts/daemon.plist`, `agent.plist`). The login-window session type is what lets RustDesk show the macOS login screen; the daemon relays IPC and does silent auto-update as root (`macos.rs:794-802`, `updater.rs:72-80`: first check after 30 s, then daily). The active console user is found by parsing `ls -l /dev/console` (`macos.rs:646-664`), pre-login is "console owned by uid 0" (`:734-736`), lock state by scraping `ioreg -n Root -d1` for `CGSSessionScreenIsLocked` (`:749-768`) — all shell-outs.
- Signing: builds are signed with a Developer ID (`--options runtime`) and notarised with `rcodesign notary-submit ... --staple` (`build.py:1126-1144`, `.github/workflows/flutter-build.yml:782-812, 949-955`); entitlements are minimal (`app-sandbox=false`, `cs.allow-jit`, `device.audio-input`, `network.server`) — `flutter/macos/Runner/Release.entitlements`. No `persistent-content-capture` entitlement.

### 1B.10 Linux and Windows service model

- Linux (`src/platform/linux.rs:1068-1180`): a root `--service` (systemd unit) loops every `SERVICE_INTERVAL`, detects the seat0 desktop (`Desktop::refresh`), and spawns `--server` as root at the greeter (GDM/SDDM Wayland login screens are recognised, `:378-379, 1268-1300`) or as the logged-in user with `DISPLAY`/`XAUTHORITY`/`WAYLAND_DISPLAY` injected (`:884-903`). A uinput service handles input on Wayland (`:683-684`); the portal path uses `org.freedesktop.portal.RemoteDesktop` + `ScreenCast` with `restore_token` support so the picker dialog only appears once (`libs/scrap/src/wayland/pipewire.rs:52, 88-104`). An optional DRM/KMS capture producer runs in the root service (`linux.rs:1076-1097`).
- Windows (`src/platform/windows.rs:556-830, 3930`): a proper SCM service (`sc create RustDesk binpath= "... --import-config ..." start= auto`) that launches `--server` into the active console session via `LaunchProcessWin` with the winlogon token (`:820-850`), tracks session switches, and calls `selectInputDesktop()` before injecting so UAC/secure-desktop works (`:1036-1044`). Installers: NSIS-style self-install (`install_me`, `:1585`) and MSI (`update_me_msi`, `:3912`); Windows builds are signed with `signtool ... /f cert.pfx /t http://timestamp.digicert.com` (`build.py:1053`).

### 1B.11 Accounts, address book, self-hosting API

### 1B.14 Critical assessment (media/input/platform)

1. Media on a reliable in-order byte stream (TCP, or KCP/SCTP which are also reliable) with capture gated on write completion: any loss stalls *everything* including input; there is no way to drop a late frame on the wire.
2. Bitrate presets are tiny (≈2 Mbps at 1080p Balanced) and the controller measures its own queue; "Best" at 1.5× is still < 6 Mbps at Retina resolutions.
3. Codec defaults to software VP9 unless the client votes; VideoToolbox is treated as a non-latency-free encoder that must be primed with repeated frames.
4. CPU pixel path on macOS: IOSurface → BGRA copy → libyuv → encoder; unchanged-frame detection compares whole frames.
5. No dirty rects, no lossless/text refinement, 4:4:4 only in software codecs.
6. Client decode thread with a 120-frame queue and no deadline drop.
7. Input rides the same stream as video; modifiers are re-synthesised per event with sleeps; key release is a periodic sweep.
8. macOS onboarding is four serial permission cards plus an osascript admin prompt; status detection is by shelling out to `ls`, `ioreg`, `launchctl`.
9. What RustDesk gets right and Sunna should keep: separate cursor channel with shape cache; per-display services and `CaptureDisplays`; portal `restore_token` on Wayland; the LoginWindow LaunchAgent trick for the macOS login screen; the Windows service + winlogon-token launch pattern; the `TestDelay`-carries-`target_bitrate` idea (client can display it); approve modes and per-IP unauthenticated caps; ID whitelist and auto-disconnect timers.

## 1A. RustDesk: rendezvous, relay, punching, encryption, identity (from source)

Sources: `/home/sunny/research-repos/rustdesk` (client/host, v1.5.0), `/home/sunny/research-repos/rustdesk-server` (hbbs/hbbr, HEAD a7736be 2026-08-07), and the `hbb_common` submodule cloned separately at `/home/sunny/research-repos/hbb_common` (HEAD 94ec710, 2026-09-25) because the shallow clone did not include it.

### 1A.1 Framing and transports

- Every message (both `RendezvousMessage` and `Message`) is a protobuf blob with a variable-length little-endian length prefix: 1 byte if len ≤ 0x3F (`len << 2`), 2 bytes if ≤ 0x3FFF (`| 0x1`), 3 bytes if ≤ 0x3FFFFF (`| 0x2`), else 4 bytes; `MAX_FRAME_LENGTH = 0x3FFF_FFFF`, pre-allocation capped at 256 KiB — `/home/sunny/research-repos/hbb_common/src/bytes_codec.rs:6-8, 46-73, 123-134`.
- Transports the client can end up on (`src/client.rs:1387-1560`): raw TCP (direct punch or relay), **KCP over UDP** (`src/kcp_stream.rs`, `kcp-sys` fork on the `rustdesk-patches` branch, "turbo" profile with `nc=1`, optional congestion window via `allow-kcp-congestion-control`, `kcp_stream.rs:28-40`), **IPv6 UDP/KCP**, **WebRTC** (webrtc-rs; DTLS/SCTP data channel; `hbb_common` feature `webrtc`, `Cargo.toml:55`), and **WebSocket** to hbbs/hbbr on 21118/21119 for browser/proxy cases (`hbb_common/src/config.rs:122-123`). The RustDesk fork of webrtc-sctp is patched because "RFC 4960's 1s RTO floor makes a single loss cost 1-3s on a link whose RTT is 24-64ms" and its congestion window is disabled by default (`Cargo.toml:228-240`) — an explicit acknowledgment that a reliable in-order transport under loss is what makes RustDesk stall.
- Per-transport enable flags are local options: `enable-tcp-punch`, `enable-udp-punch`, `enable-ipv6-punch`, `enable-webrtc`, `relay-fallback-delay` (`libs/base/src/config/keys.rs:129-135`); TCP punch is always the backstop when everything else is off (`src/client.rs:346-357`). A WebRTC offer is only sent once the hbbs socket is key-exchanged so ICE candidates are never signalled in the clear (`src/client.rs:861-880`).

### 1A.2 Identity: ID, keys, passwords

- The 9–10 digit ID is derived from the MAC address: the low 4 bytes of the MAC packed into a u32 and masked with `0x1FFFFFFF` (`hbb_common/src/config.rs:1046-1069`); Android/iOS draw a random number in `1e9..2e9`. IDs can be changed by the user (`update_id`, `:1276`) and hbbs rejects IDs shorter than 6 chars.
- A sodiumoxide `sign::gen_keypair()` ed25519 pair is generated on first run and stored in the config file (`config.rs:1116-1134`); its public key is registered with hbbs along with a per-install `uuid` (`RegisterPk { id, uuid, pk, old_id, no_register_device }`, `hbb_common/protos/rendezvous.proto`). hbbs's rules (`rustdesk-server/src/rendezvous_server.rs:371-450`): first registration wins; same uuid may change IP unless the pk also changes; a different uuid for a registered ID → `UUID_MISMATCH`, which makes the client generate a *new* ID (`src/rendezvous_mediator.rs:1287-1300`, `Config::update_id()`); at most 3 `RegisterPk` per 6 s or `TOO_FREQUENT`; IP changes are tracked in `IP_CHANGES` over `IP_CHANGE_DUR = 180 s` (`peer.rs:21-24`) with a 60 s block.
- Passwords: a random temporary ("one-time") password of configurable length (`temporary-password-length`), a permanent password stored salted/hashed (`validate_password_storage`, `connection.rs:2477`), or both; plus optional TOTP. The client proves knowledge via the `Hash { salt, challenge }` exchange (`message.proto:328-331`; `handle_hash`, `src/client.rs:4632`).

### 1A.3 Rendezvous protocol (hbbs), step by step

Ports (`hbb_common/src/config.rs:120-123`): hbbs 21116 UDP (registration/heartbeat) + 21116 TCP (punch/relay requests, key exchange), 21115 TCP (NAT test), hbbr 21117 TCP (relay), 21118/21119 WebSocket variants. Public servers: `RENDEZVOUS_SERVERS = ["rs-ny.rustdesk.com"]` with `RS_PUB_KEY = "OeVuKk5nlHiXp+APNn0Y3pC1Iwpwn44JGqrQCsWqmBw="` baked in (`config.rs:117-118`). Timeouts: `CONNECT_TIMEOUT = READ_TIMEOUT = 18_000 ms`, `REG_INTERVAL = 15_000 ms` (`config.rs:45-51`).

1. **Host registration**: the host's `RendezvousMediator` sends `RegisterPeer { id, serial }` over UDP every 15 s (`rendezvous_mediator.rs:367-480`, `REG_INTERVAL`), backing off its own wait from 3 s to 30 s when replies are missing (`MIN/MAX_REG_TIMEOUT`, `:379-381`). hbbs answers `RegisterPeerResponse { request_pk }`; if the ID is unknown or the IP changed, `request_pk = true` and the host sends `RegisterPk` (`rendezvous_server.rs:593-635`). hbbs considers a peer online if `last_reg_time < REG_TIMEOUT = 30 s` (`:50, 731`).
2. **NAT type test**: the client opens two TCP connections from the *same local port* to hbbs:21116 and :21115 and sends `TestNatRequest`; if the two observed ports differ, `NatType::SYMMETRIC`, else `ASYMMETRIC` (`src/common.rs:705-760`).
3. **Connect**: the client TCP-connects to hbbs (falling back through `RENDEZVOUS_SERVERS`), measures the TCP connect RTT, runs a UDP NAT test in parallel (`UDP_NAT_TEST_GRACE = 400 ms`, `src/client.rs:637-660`), then sends `PunchHoleRequest { id, nat_type, licence_key, conn_type, token, version, udp_port, force_relay, socket_addr_v6, switch_code, webrtc_sdp_offer }` up to 3 times with deadlines of 3 s, 6 s, 9 s (`src/client.rs:944-1000`). A non-empty `licence_key` must equal the server's `-k` key or hbbs replies `LICENSE_MISMATCH` (`rendezvous_server.rs:711-720`).
4. **hbbs decision** (`rendezvous_server.rs:703-812`): if the target is offline → `OFFLINE`; if both parties present the same public IP (or both are "LAN" per the server's `mask`) → `FetchLocalAddr` to the host, who replies `LocalAddr { local_addr, relay_server }` and the client gets `PunchHoleResponse { is_local = true }` (`:671-700`). Otherwise hbbs forwards `PunchHole { socket_addr(A), nat_type, relay_server, ... }` to the host over the host's UDP registration path; if `ALWAYS_USE_RELAY` or exactly one side is LAN, `nat_type` is forced to `SYMMETRIC` to force relay. Relay selection is round-robin across `--relay-servers` (`:948-956`). Requests from the same IP to the same ID are de-duplicated for 60 s (`PUNCH_REQ_DEDUPE_SEC`). UDP `PunchHoleRequest`/`PunchHoleSent`/`LocalAddr` are deliberately ignored to avoid amplification (`:452-465`).
5. **Host reaction** (`rendezvous_mediator.rs:1053-1210`): decides `relay_v4 = peer SYMMETRIC || my NAT SYMMETRIC || proxy/ws || force_relay`; if not relayed it "punches" by connecting *from its listening port* to A's public address (`punch_tcp_until_connected`, `:1543-1600`, retry interval 0.15 s × 1.5 backoff up to 2 s, `PUNCH_INTERVAL/BACKOFF/MAX_INTERVAL`, `:1518-1520`, `PUNCH_GRACE = 3000 ms`) while also listening on that same reuse-port socket (`new_listener(local_addr, true)`, `hbb_common/src/tcp.rs:257-280` sets `SO_REUSEADDR`/`SO_REUSEPORT`), so either the host's SYN crosses the client's SYN (simultaneous open) or the client's connect lands on the listener. It then tells hbbs `PunchHoleSent { socket_addr, id, relay_server, nat_type, version, socket_addr_v6, webrtc_sdp_answer }`, which hbbs turns into `PunchHoleResponse { socket_addr(B), pk = sign(IdPk{id,pk}), relay_server, nat_type }` for A (`rendezvous_server.rs:637-669`). If relayed, the host instead opens a connection to hbbr with a fresh uuid and hbbs sends A a `RelayResponse { uuid, relay_server, pk }`.
6. **Client connect matrix** (`src/client.rs:1387-1470`): `is_local || peer SYMMETRIC → 1 s` direct attempt; both ASYMMETRIC → 18 s (or `punch_time_used × 6` after a previous failure); otherwise `punch_time_used × 6` (×3 after a failure), min 1 s. All enabled direct transports race (`select_ok`): TCP `connect_tcp_local(peer, local_addr)` from the *same* local port used toward hbbs, UDP/KCP, IPv6, WebRTC (`race_transports_prefer_webrtc`, `:220-330`, WebRTC preferred if it wins within the 2.5 s `RELAY_FALLBACK_DELAY_MS`, `:619-635`). On failure or `force-always-relay` → `request_relay` (`:1778-1840`): connect to hbbs, send `RequestRelay { id, uuid, relay_server, secure, licence_key, conn_type, token }`, then connect to hbbr and send the same uuid; hbbr pairs the two TCP sockets by uuid and copies bytes (`relay_server.rs:336-420`, `make_pair`).
7. **Keep-alive**: in-session the host closes after 30 s without any message (`connection.rs:1175-1177`, `SEC30`); the client answers `TestDelay` echoes which double as keep-alives.

### 1A.4 Relay server (hbbr)

`rustdesk-server/src/relay_server.rs`: two TCP listeners (raw 21117 and WebSocket 21119), a loopback console for commands, a per-IP blocklist file, and token-bucket limits: `LIMIT_SPEED = 32 Mbit/s` per connection, `SINGLE_BANDWIDTH = 128 Mbit/s`, `TOTAL_BANDWIDTH = 1 Gbit/s`, with an automatic *downgrade* to `LIMIT_SPEED` once a session has run `DOWNGRADE_START_CHECK = 1 800 000 ms` (30 min) and used > 66 % of its allowance (`DOWNGRADE_THRESHOLD_100 = 66`, `:40-44`). The relay never parses payloads; whether it can read them depends on the E2E key exchange below.

### 1A.5 Encryption: what is and isn't end-to-end

- **Peer identity comes from hbbs.** `PunchHoleResponse.pk` is `sign(IdPk { id, pk }, server_sk)` (`rendezvous_server.rs:1234-1256`); the client verifies it with the *server's* public key (`RS_PUB_KEY` or the configured `key`, `src/client.rs:1649-1670`). With a valid signed pk the client sends `PublicKey { asymmetric_value (ephemeral box pk), symmetric_value (session key sealed to the peer's pk), kx_version }` and both sides derive a `secretbox` (XSalsa20-Poly1305) key; nonces are 64-bit sequence counters (`hbb_common/src/tcp.rs:63, 248-255, 382-401`); kx v1 splits directional subkeys with a BLAKE2b-derived transcript (`tcp.rs:31-46, 366-380`). WebRTC additionally binds the DTLS fingerprint to the signed identity and *fails closed* on mismatch (`client.rs:1693-1712`).
- **Fallback is silent-ish plaintext.** If there is no signed pk (self-hosted server without `-k`, older server) or the signature fails to verify, the client logs "pk mismatch, fall back to non-secure", sends an empty `PublicKey`, and continues **unencrypted** (except on WebRTC, which is DTLS-encrypted but reported "insecure") — `client.rs:1676-1690, 1730-1745`. The UI shows a lock icon variant (`secure`/`insecure`, `flutter/lib/models/model.dart:274-288`). So: with the public servers or a `-k` server, traffic is E2E-encrypted with a key hbbs cannot compute (it only signs the peer's pk), **but** a malicious or compromised hbbs can substitute a pk it controls because the client trusts whatever hbbs signs — the trust root is the server key, not an out-of-band pairing. The relay (hbbr) is blind in the secure case and sees everything in the fallback case.
- Login credentials are hashed with the host's salt before transmission (`Hash` challenge) and travel inside the encrypted stream when one exists.

### 1A.6 LAN discovery and direct IP

- `src/lan.rs`: UDP broadcast of `PeerDiscovery { cmd: "ping", mac, id, username, hostname, platform }` to `255.255.255.255:<broadcast port>` (`:188-215`), hosts reply with their info if `enable-lan-discovery` is on; the MAC is also used for Wake-on-LAN (`send_wol`, `:86-100`).
- Direct IP access: if the ID looks like an IP the client connects straight to `<ip>:21118` (`RELAY_PORT + 1`, `src/client.rs:428-446`); the host must have `direct-server` enabled and may restrict by `whitelist` (`keys.rs:57-58`, `rendezvous_mediator.rs:1344-1420`).

### 1A.7 Self-hosting and configuration distribution

hbbs takes `-k <key>` (or generates `id_ed25519`/`id_ed25519.pub` on first run, `rustdesk-server/src/common.rs:205-237`), `--relay-servers`, `ALWAYS_USE_RELAY=Y`, `-M`/mask for LAN detection, and pushes `ConfigUpdate { serial, rendezvous_servers }` to clients whose `serial` is older (`rendezvous_server.rs:355-366`). Clients are configured via `custom-rendezvous-server`, `relay-server`, `api-server`, `key` options, a base64 "--config" import string, or by renaming the executable (`rustdesk-host=…,key=….exe`, custom_server.rs; UNVERIFIED details of the encoding). Pro server adds the HTTP API used for address books/OIDC (see 1B.11) and, per issue #902 of rustdesk-server-pro, phones home to a licence server whose outage took a Pro deployment down in Feb 2026 (https://github.com/rustdesk/rustdesk-server-pro/issues/902).

### 1A.8 Critical notes on the connectivity design

- The rendezvous protocol carries no candidate *lists*: one public address per side (plus optional v6 and a WebRTC SDP). Multi-interface hosts (VPN + LAN + Wi-Fi) get exactly one guess unless WebRTC is enabled.
- NAT typing is binary (symmetric vs not) via two TCP connects, not per-destination STUN, and "one side symmetric" simply forces relay; there is no port prediction or birthday probing.
- TCP simultaneous-open punching depends on `SO_REUSEPORT` and on the NAT treating a *TCP* outbound SYN as a mapping; many CGNATs and mobile networks don't — the KCP/UDP path was added for this (and is off by default in the private-server profile, `enable-udp-punch` default UNVERIFIED).
- Registration is UDP: many self-host failures are "clients never become ready" because UDP 21116 is blocked (rustdesk-server#647, rustdesk discussions #15014, #14189, doc.rustdesk.com#575).
- The relay is a plain TCP pipe with per-session rate limits (32 Mbit/s downgrade) that would throttle any high-bitrate stream after 30 minutes on a shared hbbr.

## 2. RustDesk weaknesses: what users hit, and why gamers don't use it

### 2.1 Latency, quality, and the TCP problem
- The oldest open request is "Low-latency streaming" (rustdesk/rustdesk#79, discussion #3979); a 2024 discussion measured "screen-to-screen latency up to 120 ms on a wired LAN" (#6888) and independent comparisons put RustDesk at 18–30 ms LAN vs Parsec 7–10 ms, and 50–70 ms vs 25–35 ms inter-city (quantvps.com comparison, https://www.quantvps.com/blog/parsec-vs-rdp-vs-rustdesk — vendor blog, UNVERIFIED methodology). The web client collapses to ~1.5 s latency when the LAN is busy (discussion #10938), consistent with §1B.4: a reliable stream plus write-gated capture turns queueing into latency instead of dropped frames.
- Mouse: "Mouse cursor lags and replays old movement with high polling-rate mouse" (#15842, 2026) — every motion event is a protobuf on the same stream as video; there is no coalescing on the wire.
- Bitrate ceilings (§1B.2) and default software VP9 are why "blurry" persists even with `Best`; H.264/H.265 hardware encode only engages when the client explicitly prefers it and every client can decode it.

### 2.2 macOS
- Screen Recording permission "granted but not detected" / black screen / "waiting for image": #3261 (v1.2.0), #11251 (2025), discussion #10699; PR #9941 tried to fix detection. The root cause is TCC identity: the permission is bound to the signed bundle, and RustDesk's checks are heuristic (`CGWindowListCopyWindowInfo` scan or the private-ish `CGPreflightScreenCaptureAccess`, §1B.9). On macOS 26.1 Tahoe, unbundled executables no longer appear in the Screen & System Audio Recording list at all (Apple dev forum thread 807898), which breaks any "run the binary" install.
- Sequoia's periodic re-authorisation of screen capture (monthly since 15.1; weekly in early betas — TechRadar, mjtsai.com 2024-08-08) hits unattended hosts; the escape hatch is the `com.apple.developer.persistent-content-capture` entitlement, which Jump Desktop obtained and documents (https://support.jumpdesktop.com/hc/en-us/articles/29070118000781); RustDesk's entitlements do not include it (§1B.9).
- The Configure buttons rely on the OS prompt firing; when it doesn't, users are told to `tccutil reset ScreenCapture com.carriez.rustdesk` (RustDesk docs, https://rustdesk.com/docs/en/client/mac/).

### 2.3 Wayland/Linux
- Login screen on Wayland is unsupported (`LOGIN_SCREEN_WAYLAND = "Wayland login screen is not supported"`, `src/client.rs:120`; GNOME Discourse thread 29880; PR #15420 in progress). The docs tell users to switch GDM to X11.
- Portal picker dialog every session on KDE (discussions #10016, #13468; issue #14839 for Debian 13 KDE where the picker never appears and multi-monitor is one combined surface) — mitigated only where the portal supports `restore_token` (§1B.10), which requires xdg-desktop-portal ≥ 1.16-era `persist_mode` and a backend that honours it.
- Flatpak/Snap: no system service possible, so unattended access after reboot needs the native deb/rpm; the home page shows "wayland_experiment_tip" and a SELinux warning card (`desktop_home_page.dart:520-545`).

### 2.4 Connection failures
- Self-hosting: "clients register but never become ready" (rustdesk-server#647, discussion #643), "stuck at Connecting to network" on Windows (#14189), LTE clients failing with no relay request reaching hbbr (#15014), "Not ready" with self-hosted vs public server (doc.rustdesk.com#575). Common causes: UDP 21116 blocked/NATed for the registration path, `-k` mismatch, relay host not reachable on 21117, or the server's "LAN mask" misclassifying peers.
- Public server: RustDesk now requires controllers to log in with a third-party identity provider to use rs-ny (RustDesk blog, "RustDesk and Remote Access Scams"), which broke "I can't reach my home PC until I log in" for some (same source, citing Reddit).
- Pro licence-server dependency: rustdesk-server-pro#902 (Feb 2026).

### 2.5 Why gamers don't use it
- No gamepad forwarding at all (issues #2525, #4057; "not designed for cloud gaming" per maintainers). Relative mouse mode only arrived in 1.4.5 (Jan 2026, ubuntuhandbook.org) and 1.4.6 hides the pointer in that mode (discussion #14609); some Windows games misinterpret its absolute `MOUSEEVENTF_ABSOLUTE` events (#12539).
- fps defaults to 30 and the QoS floors at 15 fps for the first second and 5 fps under stress (§1B.3); no frame pacing, no vsync control, no audio latency tuning, audio buffer up to 3 s.
- Everything on one reliable stream: a single lost packet on Wi-Fi stalls video *and* input.

### 2.6 Security incidents and trust
- CVE-2024-25140: RustDesk 1.2.3 installed a self-signed "WDKTestCert" (SHA-1/RSA-2048, valid 2023–2033) into the Windows Trusted Root store to load its virtual display driver; fixed by switching to the Microsoft-signed Amyuni `usbmmidd_v2` driver (discussion #6444; wiki "Remove RustDesk test certificate"; Hackaday 2024-03-01). Today's code path (`virtual_display_manager.rs:9-11`, `IDD_IMPL = amyuni_idd`, `windows.rs:1833-1847` `--uninstall-cert`) reflects that.
- Governance: Purslane Ltd (Singapore), AGPL-3.0; Chinese-origin concerns appear in HN/Reddit threads (UNVERIFIED as to any substantive finding).
- Scam abuse: RustDesk's countermeasures (blog above) are website/support-page warnings, an Android countdown warning before screen capture starts, temporary removal from Google Play (2023-09-03), and the public-server login requirement. There is no desktop-host-side warning in the current tree (§1B.12), no "installed minutes ago" heuristic, and unattended access with a permanent password remains one setting away.
- Pro pricing (rustdesk.com/pricing, 2026): Individual $9.90/mo (1 user, 20 devices), Basic $19.90/mo (10 users, 100 devices), Customized from $23.88/mo + $1.20/user + $0.12/device; Pro adds address book, OIDC/LDAP, audit logs, web console, custom client generator.

### 2.7 Onboarding/UX complaints
- The two-password model (one-time vs permanent) and the four server fields (ID/Relay/API/Key) confuse first-timers; the `--config` string and renamed executables exist to hide this for MSPs.
- Windows first launch offers "Install" vs run-portable; portable mode cannot host the UAC desktop and shows repeated elevation prompts (portable_service).
- Reviews consistently list "laggy compared to Parsec", "quality settings hidden in toolbar", and "confusing self-host docs" as cons (It's FOSS / XDA style reviews; UNVERIFIED exact quotes).

## 3. Tailscale's traversal stack (from `/home/sunny/research-repos/tailscale`, v1.103.0, HEAD d229a06 2026-09-24)

### 3.1 Design in one paragraph
Every node keeps one UDP socket per address family (`rebind`, `magicsock.go:3787-3800`), a WireGuard node key, and a separate "disco" key. Path discovery is done with tiny NaCl-boxed **disco** messages sent to every known candidate address of a peer; the peer's **Pong** carries the source address it saw, which tells the sender its own reflexive address for that path. Until a direct path is proven, *all* traffic goes through the peer's home **DERP** relay (TCP/HTTPS), and the first disco pings are accompanied by a **CallMeMaybe** through DERP that lists the sender's endpoints so the other side pings back (simultaneous open through both NATs). When a Pong arrives, the lowest-latency direct path becomes `bestAddr` and is trusted for `trustUDPAddrDuration = 6.5 s` since the last pong, refreshed by 3 s heartbeats while the session is active.

### 3.2 Constants that encode the policy (`wgengine/magicsock/magicsock.go:3989-4041`, `tsconst/ping.go:11`)
`sessionActiveTimeout = 45 s` (stop keeping a path alive after this idle), `upgradeUDPDirectInterval = 1 min` (retry to find a better direct path even if one works), `upgradeUDPRelayInterval = 1 min`, `discoverUDPRelayPathsInterval = 30 s`, `heartbeatInterval = 3 s`, `trustUDPAddrDuration = 6500 ms`, `goodEnoughLatency = 5 ms` (don't bother upgrading below this), `endpointsFreshEnoughDuration = 27 s` ("UDP NAT mappings typically expire at 30 seconds"), `discoPingInterval = wireguardPingInterval = tsconst.DefaultPingInterval`, `pingTimeoutDuration = 5 s`.

### 3.3 Path selection
- `addrForSendLocked` (`endpoint.go:632-648`): if `bestAddr` is valid and still trusted → send only there; if it expired → send to **both** the last best UDP address **and** DERP ("We had a bestAddr but it expired so send both"). This dual-send is how Tailscale avoids a stall when a path silently dies.
- `wantFullPingLocked` (`endpoint.go:995-1012`): a full ping round (every candidate) is due when there is no direct best address, when trust expired, or every `upgradeUDPDirectInterval` unless latency ≤ 5 ms.
- `sendDiscoPingsLocked` (`endpoint.go:1415-1450`): pings every endpoint not pinged within `discoPingInterval`; on the first ping of a round it also `enqueueCallMeMaybe` via DERP — but only after confirming its own STUN endpoints are fresh (< 27 s), otherwise it triggers a `ReSTUN("refresh-for-peering")` first (`magicsock.go:2618-2650`).
- `handlePongConnLocked` (`endpoint.go:1917-2010`): a non-DERP pong updates that endpoint's latency; if `betterAddr(thisPong, bestAddr)` or the current best is untrusted, it switches immediately and logs "now using"; `betterAddr` prefers direct over relay and lower latency, with IPv6 winning ties (`endpoint.go:2047`; the WireGuard-only path also prefers v6 on equal latency, `:680-686`). A debug knob `TS_DISCO_PONG_IPV4_DELAY` exists to bias toward v6 (`magicsock.go:1901-1905`).
- Probing UDP lifetime: `probeUDPLifetime` pings at "cliffs" of common NAT timeouts to learn how long a mapping survives idle (`endpoint.go:159-175`).

### 3.4 Disco wire format (`disco/disco.go`)
Header: magic `TS💬` (6 bytes) + 32-byte sender disco pubkey + 24-byte nonce, then a NaCl box whose plaintext is `type(1) | version(1) | payload`. Types: `Ping 0x01` (12-byte TxID, alleged node key, padding), `Pong 0x02` (TxID + observed `Src` ip:port), `CallMeMaybe 0x03` (list of endpoints `MyNumber`), and the peer-relay family `BindUDPRelayEndpoint 0x04/Challenge 0x05/Answer 0x06`, `CallMeMaybeVia 0x07`, `AllocateUDPRelayEndpointRequest/Response 0x08/0x09`. Disco keys are separate from node keys so that an unauthenticated third party can't learn node identities from the on-path pings, and so pings can be answered before WireGuard handshakes (`magicsock.go:2053-2070` distinguishes WireGuard vs STUN vs disco vs Geneve-encapsulated packets by header).

### 3.5 netcheck (`net/netcheck/netcheck.go`)
`Report` fields (`:91-131`): `UDP`, `IPv6`, `IPv4`, `IPv6CanSend`, `IPv4CanSend`, `OSHasIPv6`, `ICMPv4`, `MappingVariesByDestIP`, `UPnP`, `PMP`, `PCP`, `PreferredDERP`, `RegionLatency/V4/V6`, `GlobalV4/V6` (+ counters of how often each reflexive endpoint was observed, to survive NATs that hand out new mappings mid-session, `:137-165`), `CaptivePortal`. Timings: `ReportTimeout = 5 s`, `stunProbeTimeout = 3 s`, `icmpProbeTimeout = 1 s`, retransmits at 100 ms initially then 200 ms (`:58-87`); incremental reports probe `numIncrementalRegions = 3` regions (always including the home region) with up to 3 tries per node (`:441, 481-495, 569`); a full report every `fullReportInterval = 5 min` (`:1372`). **Hard NAT detection** = the reflexive `ip:port` differs between two STUN servers → `MappingVariesByDestIP = true` (`:660-675, 725-735`). Hairpin checks were removed ("We no longer send hairpin checks", `:334`).

### 3.6 Hard NAT: what Tailscale actually does
The code contains **no birthday-paradox port spraying**: grepping for "birthday"/"spray" finds only a comment about fixed-port peers behind hard NAT (`magicsock.go:1332`). The strategy is: (1) prefer IPv6; (2) request a port mapping (PCP → NAT-PMP → UPnP) so the hard NAT becomes an "easy" one; (3) otherwise, if one side is easy, the easy side's pings reach the hard side's *observed* mapping for that specific destination because the hard side pinged first (CallMeMaybe ordering); (4) if both are hard and no mapping is available → stay on DERP, or (since 2025) on a **peer relay**. The blog's 256-probe math (https://tailscale.com/blog/how-nat-traversal-works: 174 probes ≈ 50 %, 256 ≈ 64 %, 1024 ≈ 98 %, 2048 ≈ 99.9 % for one hard NAT with 256 open ports; ~170 000 probes / 28 min at 100 pps for two hard NATs) explains why they didn't bother.

### 3.7 Port mapping (`net/portmapper/portmapper.go`, `pcp.go`)
`portMapServiceTimeout = 250 ms` ("a single L3 hop away"), services re-verified every `trustServiceStillAvailableDuration = 10 min`, `pmpMapLifetimeSec = pcpMapLifetimeSec = 7200` (2 h), `createMapping` has a 5 s overall context; order: PCP if recently seen (or PMP disabled), else NAT-PMP, else UPnP as fallback (`:645-720`, `preferPCP` at `:+59`). Mappings are renewed at `renewAfter` and the external address is fed back to netcheck as a candidate endpoint.

### 3.8 DERP (`derp/derp.go`, `derp/derpserver/derpserver.go`, `derp/derphttp`)
- Frames: 1-byte type + 4-byte big-endian length; `ServerKey 0x01` (magic `DERP🔑` + 32-byte key), `ClientInfo 0x02` (naclbox(json)), `ServerInfo 0x03`, `SendPacket 0x04` (32-byte dest key + bytes), `RecvPacket 0x05` (v2: 32-byte src + bytes), `KeepAlive 0x06`, `NotePreferred 0x07`, `PeerGone 0x08`, `PeerPresent 0x09`, `ForwardPacket 0x0a` (mesh), `WatchConns 0x10`, `ClosePeer 0x11`, `Ping 0x12`/`Pong 0x13`; `ProtocolVersion = 2`; `MaxPacketSize = 64 KiB`; server keep-alive every `60 s` with jitter (`derp.go:34-140`).
- Transport: HTTP `Upgrade: DERP` on 443 (TLS) with fallback to port 80 where `CanPort80` (`tailcfg` DERPNode fields: `STUNPort`, `DERPPort`, `CanPort80`, `STUNOnly`, `InsecureForTests`, `CertName`, `IPv4/IPv6`), STUN co-hosted on UDP 3478, and a regional mesh where servers forward packets for clients connected elsewhere in the region (`FrameForwardPacket`, `WatchConns`). Rationale in the package doc: "DERP is a last resort… very aggressive NATs, firewalls, no IPv6, etc? Well, DERP." Using TCP/443 is what makes it reachable from every network; the price is head-of-line blocking under loss.
- Queueing: `defaultPerClientSendQueueDepth = 32` packets, `DefaultTCPWiteTimeout = 2 s` (30 s for mesh-key clients), overflow packets are *dropped*, not buffered (`derpserver.go:88-93`). For a 60 fps video stream at ~10 packets/frame this is ~50 ms of queue — DERP is sized for keepalives and handshakes, not media.
- Payload confidentiality: DERP carries WireGuard packets; it learns only node public keys and traffic shape.

### 3.9 Peer relays (`net/udprelay/server.go`, disco 0x04–0x09)
A tailnet member can run a UDP relay (`tailscale set --relay-server-port`, kb/1411); peers allocate an endpoint on it via disco (`AllocateUDPRelayEndpointRequest`), bind with a challenge/answer handshake, and traffic is Geneve-encapsulated with a per-session VNI (`server.go:97-110`, 24-bit VNIs). Tailscale's KB states relayed connections "use the peer relay first" when both sides have restrictive NATs, and that peer relays "usually offer better performance than DERP" (https://tailscale.com/kb/1257/connection-types). This is the UDP media relay DERP never was.

### 3.10 IPv6 and UDP-blocked networks
netcheck's `IPv6`/`IPv6CanSend` plus v6 tie-breaking mean v6 direct paths win when available; with `UDP = false` (probes never return) magicsock stays DERP-only. Required egress: UDP 41641 (source port default), UDP 3478, TCP 443 (control + DERP), TCP 80 preferred for control (https://tailscale.com/kb/1082/firewall-ports).

### 3.11 What the control plane must carry (for a home-grown rendezvous)
`tailcfg.Node`: node key, disco key, `Endpoints` (STUN-discovered + local + port-mapped ip:ports), home DERP region, addresses; `Hostinfo.NetInfo` (netcheck summary). Endpoints are re-reported on every netcheck/link change (`ipn/ipnlocal` `UpdateEndpoints`). `ipnstate.PeerStatus` exposes `CurAddr`, `Relay` (DERP region), `PeerRelay` (`ip:port:vni`), `LastHandshake` (`ipn/ipnstate/ipnstate.go:270-279`), which is what `tailscale status` prints and what `tailscale ping --until-direct` polls.

### 3.12 tsnet (`tsnet/tsnet.go`)
`tsnet.Server { Dir, Store, Hostname, UserLogf, Logf, Ephemeral, AuthKey, ClientSecret, ClientID, IDToken, ControlURL, … }` (`:223-330`), `Listen`, `ListenTLS`, `ListenFunnel`, `ListenSSH`, **`ListenPacket` (UDP is supported)** (`:1350-1365`), `Dial`, `LocalClient`. It embeds a gVisor userspace netstack; the process becomes a tailnet node needing a coordination server (Tailscale's or Headscale) and a login. License BSD-3. For a Rust program this means cgo/FFI via `libtailscale` or a sidecar; it gives you *all* of §3 for free (including peer relays) but binds Sunna's identity model to Tailscale accounts and adds a Go runtime (tens of MB) — appropriate as an *optional* transport, not as the core.

## 3b. iroh, libjuice, str0m: QUIC-native traversal options for Sunna

### 3b.1 iroh (`/home/sunny/research-repos/iroh`, v1.2.0, HEAD 3c91282 2026-09-24; MIT/Apache-2.0; MSRV 1.91)
Workspace: `iroh` (endpoint + "socket" a.k.a. magicsock), `iroh-relay` (relay server/client + QUIC address discovery), `iroh-base` (keys), `iroh-dns`/`iroh-dns-server` (pkarr-over-DNS address lookup) (`Cargo.toml:2-8`). 1.0 shipped 2026-06-15; n0 reports ~95 % of bytes flowing direct and "roughly 9 out of 10" hole punches succeeding on its public relays (https://www.iroh.computer/blog and https://docs.iroh.computer/about/faq; press coverage byteiota/techtimes 2026-06; these are n0's own numbers — UNVERIFIED independently).

**The mapped-address trick (why iroh matters for a quinn app).** iroh drives a QUIC stack ("Noq", their quinn fork `iroh-quinn`) whose "socket" is not a UDP socket but iroh's `Transports` multiplexer. Every remote endpoint is given a fake IPv6 ULA: `EndpointIdMappedAddr` in `fd15:70a:510b::/64`, relay paths in `fd15:70a:510b:1::/64`, custom transports (Tor, BLE…) in `fd15:70a:510b:3::/64`, all with dummy port 12345 (`iroh/src/socket/mapped_addrs.rs:16-55, 130-250`). QUIC addresses the *peer*, not a path; the socket layer resolves the mapped address to the currently selected real path (UDP ip:port, relay, or custom) on every send, and rewrites the source on receive (`socket/transports.rs:1046-1160`). Since 1.x iroh additionally uses **QUIC multipath** (`MAX_MULTIPATH_PATHS = 8`: "1 relay path, ~3 IP paths, 3 spare", `socket.rs:131-137`) so several real paths can be open on one connection, with per-path keep-alives (`HEARTBEAT_INTERVAL = 5 s`, `PATH_MAX_IDLE_TIMEOUT = 15 s`, `RELAY_PATH_MAX_IDLE_TIMEOUT = 30 s`, `socket.rs:109-129`) and a path selector (`biased_rtt_path_selector.rs`, `RTT_SWITCHING_MIN = 5 ms`). The relay path is opened first and stays open; direct paths are added when hole punching succeeds and the selector moves traffic over (`remote_map/remote_state.rs:150-175`).

**Hole punching** (`remote_state.rs:506-575`): triggered on the lowest-id client-side connection; candidates come from the QUIC "NAT traversal" extension (the peer's advertised addresses arrive *inside* the QUIC connection over the relay path, `conn.get_remote_nat_traversal_addresses()`, up to `MAX_QNT_ADDRESSES = 32`), local candidates from interface enumeration + QAD; a new attempt runs when candidates change or every `HOLEPUNCH_ATTEMPTS_INTERVAL = 5 s`; `GOOD_ENOUGH_LATENCY = 10 ms`, `UPGRADE_INTERVAL = 60 s` (`remote_state.rs:52-66`). Both sides open paths toward each other's candidates (QUIC PATH_CHALLENGE/RESPONSE act as the "disco" pings) — this is the draft-seemann-quic-nat-traversal design (`PUNCH_ME_NOW`-style frames), so there is no separate unauthenticated ping protocol at all.

**Address discovery:** STUN was replaced by **QAD** (QUIC Address Discovery: a QUIC connection to the relay with ALPN `/iroh-qad/0` that returns the observed address via a transport parameter/frame, `iroh-relay/src/quic.rs:9-10`); `net_report::Report { udp_v4, udp_v6, mapping_varies_by_dest_ipv4/v6, preferred_relay, relay_latency, global_v4, global_v6, captive_portal }` (`iroh/src/net_report/report.rs:18-55`) is the netcheck analogue. Port mapping lives in `iroh/src/portmapper.rs` (UPnP/NAT-PMP/PCP; defaults UNVERIFIED).

**Relay** (`iroh-relay`): WebSocket over HTTPS at `/relay` (`http.rs:7-13`); frames `ServerChallenge 0, ClientAuth 1, ServerConfirmsAuth 2, ServerDeniesAuth 3, ClientToRelayDatagram 4, …Batch 5, RelayToClientDatagram 6, …Batch 7, EndpointGone 8, Ping 9, Pong 10` (`protos/common.rs:18-45`) — a DERP descendant with challenge-response auth by node key. Public relays: `use1-1`, `usw1-1`, `euc1-1`, `aps1-1.relay.n0.iroh.link` (`iroh/src/defaults.rs:27-33`); `RelayMode::Custom` lets you run your own (`iroh-relay` binary), and address lookup can be your own DNS/pkarr server or mDNS, so iroh works with zero n0 infrastructure.

**Identity/E2E:** the `EndpointId` is an ed25519 public key used directly as the TLS identity via **RFC 7250 raw public keys** (`iroh/src/tls.rs:4-14`, `tls/resolver.rs`, `tls/verifier.rs`); the relay only sees ciphertext. Dialling by key means the rendezvous cannot substitute identities — exactly the property RustDesk lacks.

**Transport config:** iroh re-exports its quinn fork's `Connection` (streams + datagrams) so Sunna's quinn code would port with a crate rename, but Sunna would then depend on `iroh-quinn` rather than upstream quinn (fork tracked in `Cargo.toml`; API drift risk). Default idle timeout 30 s at the connection level (comment at `socket.rs:127`).

**Known issues** (search of tracker, UNVERIFIED numbers): reports of connections sticking on relay behind certain corporate NATs and of Windows firewall prompts for the UDP socket; the architecture doc admits QAD-derived endpoints are not yet aged ("TODO: Use this", `socket.rs:100-103`).

### 3b.3 str0m (`/home/sunny/research-repos/str0m`, HEAD b27ff8a 2026-09-25)

## 4. Parsec (closed source): connectivity, onboarding, host settings, gates, security

### 4.1 Connection sequence and failure modes
- Control plane: account login → Kessel API (TCP 443) → computer list with online state → "Connect" → STUN (UDP 3478) → UDP hole punch on host ports starting at a pseudo-random port unless `network_server_start_port` is set (the older docs' default 8000 and "forward 8000–8002 / allow 8000–8011 outbound" still appear in support articles) → DTLS 1.2 session with a 128-bit AES-GCM key (parsec.app/security: "Native application peer-to-peer traffic is encrypted end-to-end using a shared 128-bit AES key"; connectivity requirements article, `support.parsec.app/…/32381460716180`).
- **No consumer relay.** Errors 6023/6024 ("Unable To Negotiate A Successful Connection") are documented as "something is preventing Parsec from making a peer-to-peer network connection"; listed causes: NAT, firewall, missing port forwarding, ISP blocking UDP, carrier-grade NAT, double NAT, disabled UPnP, guest Wi-Fi; fixes in order: restart, firewall allow, remove double router, **grant macOS Sequoia local-network permission**, check CGNAT, port-forward, pfSense/OPNsense hybrid NAT, VPN exceptions; and: "Teams can instead look to port forward the involved machines, or set up a Parsec High-Performance Relay if your team uses Parsec for Teams Enterprise"; last resort "ZeroTier … not a guaranteed fix" (https://support.parsec.app/hc/en-us/articles/32381913636244). Community summary: works if only one side is symmetric/CGNAT and the other can forward or UPnP; fails if both are (bleepingcomputer forum 747399; natchecker.com/blog/parsec-error-6023).
- Other documented codes (https://support.parsec.app/hc/en-us/articles/32381281333012, page not fetchable here — list per earlier research and community mirrors, UNVERIFIED individually): 6013 "UDP blocked by your network"; 6101/6105/6107/6111/6112 host-side capture/encoder/display errors; 15000 series encoder init; -3/-1 auth; 22006 "host offline"; 800 "server error".
- HPR (Enterprise only): a customer-hosted relay "efficiently relays many simultaneous Parsec connections through a single IP address/port", removes "reliance on UPnP or complex firewall rules", private listener 4900 / public 5000, configured via `app_stun_address=IP@PORT,…` and `app_client_stun_address`, `app_force_relay=2` forces relay for WAN+LAN, `network_fast_relay_ping=true` picks by latency; recommended in a DMZ close to hosts (HPR Overview/Prerequisites and Configure Relay articles; advanced config page). Free $0 (core 60 fps streaming, 1 monitor); **Warp** $9.99/mo or $8.33/mo annual (multi-monitor up to 3, 4:4:4, privacy mode, Wacom); **Teams** $35/user/mo ($30 annual; admin panel, SSO, team computers, guest access at $25/invite, 7-day audit logs); **Enterprise** $45/user/mo annual (Teams API, **High-performance relay**, RBAC, SCIM). ### 4.5 Security/privacy model (https://parsec.app/security)
"All connections traveling through Parsec are peer-to-peer. They never transit Parsec's infrastructure"; sessions "encrypted using 128-bit AES-GCM"; web client via DTLS; MFA on accounts; SAML SSO (Teams); SOC 2 Type 2; regular pen tests. Parsec's servers therefore see account identity, device list, online state, and IP endpoints (needed for STUN/brokering) but not media. The BUD key exchange is not documented; the session key is presumably brokered via the authenticated API channel (UNVERIFIED), which — like RustDesk — makes the account server the trust root.

### 4.6 What makes Parsec feel easy (analysis)
1. **Account = identity = device list.** Both machines log in once; the host appears by name with an online dot; no IDs, PINs, IPs, or ports are ever typed for your own machines.
2. **One toggle to host** (`Hosting Enabled`) with defaults that stream 60 fps at 10 Mbps H.265 immediately.
3. **Permission wizard lives where the user is looking** (Host tab, yellow banner) and re-checks state; the only weak point is the required app restart on macOS.
4. **Latest-frame-wins everywhere** so the picture is never behind the input even when quality drops; an overlay with a red icon explains "network is bad" instead of freezing silently.
5. **Guest model designed for co-play**: gamepad-only by default, Accept dialog, per-guest upgrades, Approved Apps.
6. **Installers do the right thing**: signed installers, silent self-update, Windows service for unattended access, virtual display fallback when headless.
Weaknesses that leave room: no relay for consumers (hard-NAT users are simply told to port-forward), macOS host is second-class (no virtual display, no gamepad, mic permission asked even when unnecessary), no Linux host, changelog frozen since 04/2022 (https://s3.amazonaws.com/parseccloud/changelog.txt has no 2023–2026 entries; post-Unity releases are only in-app), Warp paywalls privacy mode and 4:4:4.

### 5.8 What "as easy as Parsec" concretely requires
1. Identity that makes machines *appear*: either an account (Parsec/CRD) or a device-link flow (scan a QR / open a link on the other machine) that binds keys once; never an ID+password to retype.
2. Zero network configuration: STUN/QAD + hole punching + an always-available relay (the thing Parsec charges $45/user/mo for) with automatic upgrade to direct.
3. LAN auto-discovery (mDNS/DNS-SD) so the same machine works at home without touching the internet.
4. One host toggle with good defaults, and a permission wizard that (a) lives on the host tab, (b) polls TCC state, (c) tells the user when a relaunch is needed, and (d) survives Sequoia's re-approval cycle (persistent-content-capture entitlement; re-approval detection that notifies the *client*).
5. Unattended access as a first-class, explicit choice with a visible "this machine can be reached by X" indicator, not a hidden password.
6. Connection state that explains itself: direct/relay, RTT, loss, bitrate, and a plain-language reason when quality drops (Parsec's overlay, Tailscale's `tailscale ping`).
7. Signed, notarised installers with silent updates and a service/agent split so the host survives reboots and the login window.

## 6. Security and identity: pairing models, E2E guarantees, unattended access, abuse

### 6.1 Pairing models compared

| Model | What the user does | Crypto | MITM at rendezvous? | Unattended | Examples |
|---|---|---|---|---|---|
| ID + one-time password | reads 9-digit ID and a password off the host, types both | password hashed with host salt inside a session whose peer key came *from the rendezvous* | yes unless server key pinned (§1A.5) | only with permanent password | RustDesk, AnyDesk, TeamViewer |
| Account + device list | logs in on both machines | server-brokered session keys (Parsec, CRD) or server-distributed node keys (Tailscale) | the account server is the trust root; Tailscale mitigates with tailnet lock (https://tailscale.com/kb/1226/tailnet-lock: node keys must be signed by trusted signing nodes, so a compromised control plane can't add peers) | yes | Parsec, CRD, Tailscale |
| Account + PIN (PAKE) | logs in, sets a 6+ digit PIN on the host, types it on the client | Chrome Remote Desktop runs SPAKE2 so "the PIN and one-time codes are verified client-side and never sent to Google's servers" (Chromium implemented SPAKE2 for this, https://seb.dbzteam.org/blog/2013/12/05/spake2_in_chrome.html; CRD wiki) | the server brokers identity but cannot learn the PIN | yes | CRD |
| Local PIN pairing + cert pinning | 4-digit PIN shown by client, typed into host UI | Sunshine: `key = SHA-256(salt(16 B) ‖ PIN)[0..16]` → AES-128-ECB challenge/response, then exchange of X.509 certs and signatures; the client cert is pinned for TLS afterwards (`/home/sunny/research-repos/Sunshine/src/nvhttp.cpp:736-877`, `src/crypto.cpp:330-347`) | 4 digits are brute-forceable off-line if the exchange is observed on an untrusted network; fine on a LAN, weak over the internet | yes after pairing | Sunshine/Moonlight |
| QR / link pairing | scan a QR or open a link containing pubkey + ephemeral secret | key exchange bound to an out-of-band secret; no server trust needed | no | yes | WhatsApp Web, Signal linked devices |
| PAKE codes | speak a short code ("7-crossover-clockwork") | SPAKE2/CPace (RFC 9382; CPace draft) gives full-strength keys from a low-entropy code with one guess per attempt | no | yes | Magic Wormhole |
| TOFU fingerprint | compare a fingerprint once | SSH-style | first connection only | yes | SSH |

Guidance for Sunna: device-link pairing with a PAKE code or QR (short code shown on the host UI, typed/scanned on the client; both derive the long-term peer key, which is then pinned) gives account-free E2E that a rendezvous cannot subvert; an optional account can *carry* the same device keys for convenience (list of machines) without becoming the trust root — this is what neither RustDesk nor Parsec does. QUIC/rustls support this directly: self-signed or RFC 7250 raw-public-key certificates verified by a custom `ServerCertVerifier`/client-cert verifier that checks the pinned key (iroh's `tls/verifier.rs` is a working template); mutual TLS gives host↔client authentication in the handshake, and the relay sees only ciphertext.

### 6.2 E2E guarantees through relays and rendezvous
- E2E through a relay is only meaningful if the peer key is *not* obtained from the party that runs the relay. RustDesk: hbbs signs the peer's key → E2E against hbbr but not against hbbs (§1A.5). Tailscale: control distributes node keys → E2E against DERP but not against control unless tailnet lock. iroh: dial-by-key → E2E against both relay and discovery. Parsec: undocumented key brokering (UNVERIFIED) → assume E2E against nobody but a passive network attacker.
- WireGuard/Noise IK and QUIC TLS 1.3 both give forward secrecy per session; the difference for Sunna is that QUIC TLS with pinned RPKs needs no extra handshake layer.
- Relay authentication: DERP and iroh relays require the client to prove its node key (challenge-response) so relays can be rate-limited per identity; a Sunna relay should do the same (prevents becoming an open reflector).

### 6.3 Unattended access, lock screen, curtain
- Windows: TeamViewer/AnyDesk/RustDesk/Parsec (Shared install) run a SYSTEM service that spawns a capture/input agent in the console session with the winlogon token so the login screen and UAC secure desktop can be driven (`rustdesk/src/platform/windows.rs:820-850, 1036-1044`); Sunshine without its service cannot type into UAC prompts.
- macOS: Apple Screen Sharing shows the login window; RustDesk does it with a LaunchAgent limited to `LoginWindow` + `Aqua` session types (§1B.9); Parsec needs "a custom installer for login screen access"; Jump Desktop Connect and Screens Connect install daemon+agent pairs. A LaunchDaemon alone cannot capture the screen (no window server access); the agent must live in the login-window or user GUI session (Claude's dossier covers the platform detail).
- Wake-on-LAN: RustDesk broadcasts WoL from a LAN peer using the MAC learned in discovery (`src/lan.rs:86-100`); Moonlight has WoL; Tailscale/Parsec cannot wake a machine without a LAN helper.
- Curtain/privacy: Apple Remote Desktop curtain mode; Parsec privacy mode (Warp, Windows); RustDesk Windows via magnifier/exclude-from-capture/virtual display and macOS via gamma blackout + event tap (§1B.8); AnyDesk privacy mode (Windows). None of these is robust on macOS; a virtual display + physical display sleep (`CGDisplay` power management) is the only clean way (Claude's lane).

### 6.4 2FA and consent UX
TOTP on the host (RustDesk `Auth2FA`, AnyDesk/TeamViewer account 2FA), **2FA for connections** (TeamViewer: push approval on a phone for every session), new-device approval e-mails (TeamViewer Trusted Devices; Parsec device confirmation), and Accept dialogs with auto-timeout. Lesson: the consent dialog must show *who* is connecting (verified name/avatar from the pairing), and unattended access should be visibly "armed" in the host UI.

### 6.5 Abuse and scams — what happened, what vendors did
- Remote-access tools are the standard vehicle for tech-support scams; RustDesk's own blog ("RustDesk and Remote Access Scams") lists its mitigations: support-page warning, GitHub misuse disclaimer, Android warning + countdown before capture, temporary Google Play removal (2023-09-03), and mandatory third-party login for controllers on the public server ("because of ongoing scamming and botnet abuse"), while conceding "none removes the central social-engineering risk".
- Microsoft Quick Assist was used by Storm-1811 (Black Basta) in vishing campaigns from April 2024; Microsoft responded with in-app scam warnings and guidance to block Quick Assist where unused (https://www.microsoft.com/en-us/security/blog/2024/05/15/threat-actors-misusing-quick-assist-in-social-engineering-attacks-leading-to-ransomware/).
- AnyDesk's production breach (disclosed 2024-02-02) leaked source and the code-signing key; all certificates were rotated and older builds invalidated (BleepingComputer; Akamai). TeamViewer's corporate network was hit by APT29 in June 2024. Lesson: signing keys belong in an HSM/cloud signer, and the client must be able to revoke/rotate trust roots.
- CVE-2024-25140 (RustDesk test root cert) and CVE-2024-1709 (ScreenConnect auth bypass) show that installers and management planes are attack surface too.

Design lessons for Sunna: (1) no unattended access by default; enabling it is a deliberate host-side action with a persistent banner; (2) pairing must be initiated from the host UI (the victim's machine) with a short-lived code, never by typing a stranger-supplied ID into the host; (3) show a scam interstitial when a *first* inbound connection arrives within N hours of install or from a never-seen peer; (4) always-visible "controlled by <name>" overlay and a panic key that ends the session; (5) no silent/hidden mode, no config import from the command line without an admin prompt; (6) signed builds only, with key rotation baked into the updater; (7) rate-limit unauthenticated connections per IP as RustDesk does (64 total / 16 per IP / 128 KiB pre-auth).

## 7. Distribution: signing, packaging, services, auto-update

### 7.1 macOS
- Developer ID signing with hardened runtime + notarisation (notarytool or rcodesign; RustDesk uses `rcodesign notary-submit --staple`, `build.py:1126-1144`), stapled DMG/pkg. Unsigned or ad-hoc-signed builds hit Gatekeeper ("damaged / can't be opened", needing `xattr -d com.apple.quarantine`) and — critically — **TCC permissions are keyed to the code-signing identity**: every rebuild of an ad-hoc-signed dev binary loses Screen Recording/Accessibility (reason the Sunna repo already notes granting to the *terminal* for dev builds).
- Entitlements needed: none for TCC-gated capture/input; `com.apple.security.device.audio-input` for mic; `com.apple.developer.persistent-content-capture` (macOS 15+) to stop the periodic screen-capture re-approval — a restricted entitlement requested from Apple; Jump Desktop has it (https://support.jumpdesktop.com/hc/en-us/articles/29070118000781); Apple's doc page exists (https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.persistent-content-capture) but its text could not be fetched here (UNVERIFIED wording). Sequoia re-prompts monthly (weekly in 15.0 betas; TechRadar; mjtsai.com 2024-08-08).
- Services: `SMAppService` (macOS 13+) registers LaunchAgents/LaunchDaemons from inside the app bundle without osascript; RustDesk still writes plists via AppleScript with an admin prompt (§1B.9). A daemon (root, pre-login) cannot capture; the agent must run in the GUI session, and a `LimitLoadToSessionType = LoginWindow` agent covers the login screen.
- Tahoe 26.1 no longer lists plain executables under Screen & System Audio Recording (Apple forum 807898) — ship a real `.app` bundle, even for the daemon's helper.
- Mac App Store: sandbox forbids CGEventPost-style injection and LaunchDaemons; hosts are direct-distribution only (clients can be MAS). Homebrew cask is a fine secondary channel (Gatekeeper still applies).
- Updater: Sparkle (EdDSA-signed appcast, delta updates) is the standard; RustDesk does a root-daemon silent DMG update (`macos.rs:894-1050`, daily check after a 30 s initial delay, `updater.rs:72-80`).

### 7.2 Windows
- Authenticode: OV certs must live on hardware tokens/HSM since June 2023; EV gives instant SmartScreen reputation; **Azure Trusted/Artifact Signing** is $9.99/mo Basic (5 000 signatures) with identity validation included and no token (https://azure.microsoft.com/en-in/pricing/details/trusted-signing/; textslashplain.com 2025-03-12), not EV, but SmartScreen reputation accrues normally; SignPath.io offers free signing for OSS. RustDesk signs with `signtool … /f cert.pfx` (`build.py:1053`).
- Service model: an SCM service running as LocalSystem that launches the interactive agent with the winlogon/user token in the active session (`CreateProcessAsUser`, `SetThreadDesktop` for the secure desktop); `uiAccess=true` manifests (signed, installed under Program Files) for injecting into elevated windows. RustDesk: `sc create RustDesk binpath= "… --import-config …" start= auto` (`windows.rs:3930`).
- Packaging: MSI (RustDesk added `update_me_msi`), MSIX (auto-update built in, but sandboxed identity complicates services), NSIS/Inno; WinGet for discovery. Kernel drivers (virtual display, virtual gamepad) need WHQL/attestation signing — the reason RustDesk moved to Amyuni's signed IDD.

### 7.3 Linux
- Flatpak/Snap sandboxes cannot install a system service, cannot read X11 input without `--socket=x11`, and on Wayland must use the ScreenCast portal (PipeWire) for capture and the RemoteDesktop portal for input, ideally via **libei/EIS** (`ConnectToEIS`) rather than the older `Notify*` calls; `persist_mode`/`restore_token` avoids re-prompting after the first consent (https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.RemoteDesktop.html; KDE portal issue #12 for EIS support). GNOME ships `xdg-desktop-portal-gnome`, KDE `-kde`; wlroots compositors need `-wlr` (screencast only) or third-party backends (xdg-desktop-portal-generic). No portal can capture the greeter, so a native package with a root service (RustDesk's model, §1B.10) or a KMS/DRM capture path with `CAP_SYS_ADMIN` (Sunshine docs' `setcap`) is required for login-screen access; uinput needs a udev rule.
- Practical shipping matrix used by peers: deb/rpm + systemd unit (RustDesk, AnyDesk, Sunshine), AppImage (RustDesk, Sunshine), Flathub (RustDesk, Sunshine — host features reduced), snap (Sunshine, confinement issues).

### 7.4 Auto-update patterns
Parsec self-updates silently; RustDesk checks daily and updates via its root service on macOS/Windows; Sunshine only notifies; Tailscale offers `tailscale set --auto-update` with per-OS packaging. For a service + app pair, update the service binary atomically (rename-swap), restart the agent after the GUI session is idle, keep the previous version for rollback, and sign the update manifest with a key independent of the code-signing cert.

## 8. Steal / avoid, and what beating RustDesk and Parsec on connecting takes

### 8.1 Steal
- **iroh/Tailscale magicsock design**: one UDP socket; per-peer stable mapped address under quinn (`AsyncUdpSocket` shim) so the transport never migrates; direct-or-relay chosen by measured RTT; dual-send to old-best + relay when trust expires; 5 s path idle, 3–5 s heartbeats, 30 s relay idle; re-probe for a better path every 60 s unless ≤ 5–10 ms (§3.2, §3b.1).
- **QUIC as the ping protocol**: use PATH_CHALLENGE/RESPONSE (or the QUIC NAT-traversal draft's frames) for connectivity checks and QAD-style observed-address feedback instead of a separate STUN/disco layer (§3b.1).
- **Relay-first connect**: send the first packets through the relay so the session is up in one RTT and upgrade to direct in the background (Tailscale KB: "All connections start as relayed … then tries to upgrade").
- **Port mapping** (PCP → NAT-PMP → UPnP, 250 ms probes, 2 h leases) to turn hard NATs into easy ones (§3.7); Parsec's UPnP-by-default is part of its 97 % figure.
- **Dial-by-key identity** with RPK TLS and pairing-time pinning (iroh), plus optional account sync of device lists (Parsec's UX).
- **RustDesk's operational details**: LoginWindow LaunchAgent; Windows service + winlogon token; cursor-as-side-channel with shape cache; `restore_token` on Wayland; per-IP unauthenticated caps; approve modes; ID/IP whitelists; auto-disconnect; `TestDelay` echo carrying the target bitrate for the client UI.
- **Parsec's product decisions**: hosting toggle with working defaults; permission checklist on the host tab; guest permission ladder; Approved Apps; overlay that explains network state; latest-frame-wins.
- **neko's single-port UDP mux + link sharing** for browser guests later.

### 8.2 Avoid
- Reliable in-order transport for media (RustDesk TCP/KCP/SCTP): loss becomes latency, input stalls with video.
- Capture loop gated on socket writes and sleep pacing; fixed-fps encoder contexts; QoS driven by an in-band ping that measures your own queue; ×1.05–1.15 per 3 s bitrate recovery.
- Trusting the rendezvous for peer keys ("secure" that silently falls back to plaintext).
- Binary NAT typing via two TCP connects; one candidate address per side.
- TCP relays sized for keepalives (DERP: 32-packet queue, 2 s write timeout) as the only fallback for a 60 fps stream; Parsec's "no relay, go port-forward".
- Serial permission cards that require manual re-checks; shelling out to `ls /dev/console`, `ioreg`, `osascript` for state and install.
- Test root certificates, unsigned builds, hidden/silent install modes, unattended access as a default.
- Paywalling the relay (Parsec Enterprise) — for Sunna the relay is the reliability feature, not the upsell.

### 8.3 What it takes to beat RustDesk and Parsec on ease + reliability of connecting
1. **Connect success ≥ Tailscale-class**: direct on easy/easy and easy/hard NAT (port mapping + simultaneous open with QUIC path validation), IPv6-first, and a **UDP/QUIC relay** (self-hosted `sunna-relay`, plus community/public instances) so hard/hard and UDP-hostile networks still get a usable 30–60 fps stream. Target: direct ≥ 90 % of pairs (Tailscale/iroh figures), relay for the rest, never "error 6023".
2. **Time-to-first-frame < 1 s** via relay-first + parallel punching, and a visible upgrade to direct within ~5 s (disco/QAD timings above).
3. **Pairing in under a minute, no transcription of IDs**: host shows a short code/QR; client types/scans it; keys pinned; optional account to sync the device list; LAN discovery via DNS-SD (`_sunna._udp`) with the same keys.
4. **Host onboarding in three clicks on macOS**: one wizard page polling TCC, relaunch handled automatically, `SMAppService` for agent+daemon, persistent-content-capture entitlement applied for, re-approval detected and surfaced to the client.
5. **Explainable connections**: a status line with path type (LAN/direct/relay), RTT, loss, send/receive bitrate, and one-line reasons ("relay: both sides behind symmetric NAT; enable UPnP or IPv6").
6. **Safety by default**: attended mode until the owner enables unattended; scam interstitial on first inbound; controlled-by overlay; signed installers; auditable per-device keys with revocation.
7. **Media semantics that never stall**: datagrams, FEC/NACK with deadlines, latest-frame-wins, and input on its own datagram flow — already Sunna's direction (research/07), and the single biggest reason it can feel better than both RustDesk (reliable stream) and Parsec (no relay).
