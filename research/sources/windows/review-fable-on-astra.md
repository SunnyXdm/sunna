## 2. What the report missed that matters for "beat Parsec at gaming"

1. **Client-side input capture is absent from both reports.** Game streaming latency is as much the mouse path as the video path. Needed per client: macOS relative-mouse mode (`CGAssociateMouseAndMouseCursorPosition(false)` + `kCGEventMouseMoved` deltas, or IOHIDManager for raw reports; cursor hiding; 1000–8000 Hz mice deliver bursts that must be coalesced per host frame or sent as deltas with timestamps); Android pointer capture (`View.requestPointerCapture`, `AXIS_RELATIVE_X/Y`, API 26+; `MotionEvent` batching via `getHistorical*`; touch sampling at panel rate); Linux Wayland `zwp_relative_pointer_v1` + `zwp_locked_pointer_v1`, X11 XI2 raw motion. Also keyboard: scan-code-level capture so WASD and dead keys map exactly, and what happens to Cmd/Super/Alt-Tab. Parsec does all of this already.
2. **Input packet policy.** Nothing on how many input datagrams per second to send, whether to coalesce mouse deltas to one per host capture interval (Parsec's apparent behaviour) or forward every 1 kHz event, timestamping, and priority over media in the QUIC datagram queue (the report says "reserve timely capacity" but Sunna's single evicting send buffer has no priority classes).
3. **Controller forwarding latency**: XInput polls at 125 Hz on the host unless the virtual pad reports faster; ViGEm/libvirtualhid round-trip; rumble/feedback return path; client-side gamepad APIs (GameController.framework, Android `InputDevice`, SDL on Linux). Gamers notice stick latency more than mouse latency because there's no local cursor to hide it.
4. **Host frame-pacing interaction** (see 1.6): windowed vs independent-flip, DWM composition latency, the virtual display's refresh rate setting the sampling rate, V-Sync/Reflex/frame-cap advice (capping the game slightly below the virtual display's refresh gives a stable 1-frame capture age; uncapped gives jitter), and that Windows "Optimizations for windowed games" (DXGI flip model for DX10/11 windowed) changes the DDA path on 24H2+. None of this is in §2.3 beyond "test it".
5. **Tailscale as the network layer has three concrete latency consequences the report doesn't name.** (a) DERP relays run over **TCP+TLS with an HTTP Upgrade** (`tailscale/derp/derphttp/derphttp_client.go:356,511-512,677`), so when a direct path fails every "unreliable" QUIC datagram becomes reliable, ordered and TCP-retransmitted: loss turns into head-of-line stalls of ≥1 RTT, and the XOR-FEC/resend design becomes dead weight. Sunna must detect relay mode (`tailscale status --json`, `CurAddr` empty) and either warn or switch to a lower-bitrate, larger-jitter-buffer profile. (b) Tunnel MTU is 1280 (`net/tstun/mtu.go:79`), hence Sunna's 1200-byte datagrams: a 104 kB frame is ~90 packets, ~90 AEAD operations per side per frame, and per-packet syscall cost unless GSO/`sendmmsg` is used. (c) On Windows Tailscale is **userspace wireguard-go over Wintun** (`wgengine/userspace.go:22-23`), not a kernel path: extra context switches and scheduling jitter on a 4-core host like Valkyris while a game is running. "Measure Tailscale" (§5.4) should become these three measurable items.
6. **Bitrate adaptation mechanism.** QUIC datagrams don't give the application loss/delay feedback; Sunna needs a receiver-side bandwidth estimator (arrival-time deltas, like GCC/Parsec) feeding the encoder, plus how it interacts with quinn's own congestion controller, which will throttle datagrams under loss regardless of what the app wants. The report says "adapt encoded bitrate before it fills" without saying how.
7. **Client decode specifics that gate the whole budget:** VideoToolbox needs `kVTDecompressionPropertyKey_RealTime` and async decode with a small pool; low-latency HEVC on M1/M2 is fine but HEVC 4:4:4 and AV1 are not hardware-decoded there (M3+ for AV1); MediaCodec needs `KEY_LOW_LATENCY` (API 30) and `Surface` output with `releaseOutputBuffer(ts)`; Linux decode via VA-API/NVDEC with DMA-BUF import into wgpu to kill the readback the report found. Named only as "equivalent native work".
8. **Encoder session contention on the host**: NVIDIA consumer cards allow a limited number of concurrent NVENC sessions (8 since driver 550-era; was 3/5 before), and ShadowPlay/Instant Replay plus Parsec already hold sessions on Valkyris (the report observed one active session). A Sunna install on a typical gamer's PC must handle "encoder busy" and ShadowPlay-induced throughput sharing.
9. **DDA's four-process limit** (row 4) — relevant for the same reason.
10. **Multi-monitor and monitor selection** (which output to stream, follow the game's monitor, cursor clipping across monitors) — Parsec supports monitor switching from the client.
11. **Keyframe/IDR size handling on a VBV of one frame**: the report notes IDR bursts; it doesn't say how the first second (handshake, IDR, FEC) behaves on a 30 ms WAN or how to pace an IDR across several datagram batches without eviction (row 35).

## 3. Contradictions and tensions with `fable-platform-drivers.md` (my report)

1. **Headless NVIDIA "phantom 1024×768 output".** My report says NVIDIA "keeps a phantom output alive… that is what you would capture with no driver". The Astra probe shows `nvidia-smi` reporting `Display Attached: No` / `Display Active: Disabled` for the RTX 4060 while WMI `Win32_VideoController` reports 1024×768@60. Those are compatible only if the WMI value is a default/stale mode, not an attached DXGI output. **My claim is UNVERIFIED and probably overstated**; it needs a `IDXGIAdapter::EnumOutputs` + `GetDesc().AttachedToDesktop` probe (and `QueryDisplayConfig`) from the interactive session, which the read-only rule didn't let either of us run. Astra's wording ("may leave no active output for DDA") is the safer one; treat "stock NVIDIA headless = DDA fails" as the planning assumption until tested.
2. **Virtual audio device signing.** Astra correctly says Sunna needs a signed virtual audio endpoint for mic passthrough and for headless desktop audio when no render endpoint exists. My report's signing plan ("an OV certificate covers the app, service, installer and both UMDF drivers") did not include an audio driver. A Windows audio endpoint driver is a **WDM/PortCls kernel-mode driver** — SysVAD builds `TabletAudioSample.sys` and Microsoft notes "most of these binary files are executed in kernel mode" — and there is no UMDF audio class. So a Sunna virtual speaker/microphone needs **attestation signing (EV cert + Partner Center + an organisation)**, which my report said could be "deferred, possibly forever". Correction to my report: it can be deferred only if (a) desktop-audio capture is accepted to require *some* render endpoint (NVIDIA HDMI endpoints vanish without a monitor; motherboard audio usually remains) and (b) microphone passthrough is dropped from v1 or delegated to an optional third-party component (VB-Cable is attestation-signed; same dependency problem as ViGEm). Both reports should carry this as an open decision.
3. **WGC and the secure desktop.** I stated flatly that WGC cannot capture the secure desktop; Astra marks it UNVERIFIED. Microsoft documents the LOCAL_SYSTEM rule only for DDA. My statement rests on practice (no streaming tool does it) rather than a primary source; Astra's label is more honest. Not a contradiction in recommendation: both say SYSTEM-agent + DDA for lock/UAC.
4. **Where the virtual display lives in the plan.** My report treats the VDD as a headless/convenience component; Astra treats it the same ("§2.5 no display"). Section 1.6 above argues it is also the refresh-rate control that fixes the capture cadence, so it belongs in the latency plan (build order step 2–3), not step 6. Both reports under-rank it.
5. **Agreement worth stating**: both reports independently conclude that nothing on a stock Windows PC gives you a virtual monitor, virtual gamepad or virtual audio device, that Parsec/ViGEm/Voicemeeter on Valkyris must not be depended on, and that DDA from a SYSTEM agent in the console session is the capture model.
