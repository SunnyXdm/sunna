## 1. Verdict

Implementable: yes, by one developer plus agents, provided the first six weeks are re-sequenced (authenticate on the existing Quinn before migrating to iroh; keep Swift out of the cargo workspace) and two protocol contradictions are fixed before the M2 golden layouts freeze. The M0–M4 Mac-only path is the right product and the plan is unusually honest about what is unverified. Competitive credibility: strong against RustDesk and Apple HP on desktop use (exact tiles + bounded queue age attack their real weaknesses); plausible but unproven against Parsec and Moonlight/Sunshine, which sit near the physical floor — the plan already concedes those margins may be unattainable, and the absolute L60 p50 ≤35 ms is the one number I would not bet on with two 60 Hz Air panels. Parsec-level ease is achievable if the co-primary short-code pairing ships in M3, which currently hinges on a PAKE crate requirement that may be unsatisfiable as written.

## 2. Blocking issues (ranked)

**B1 · §6.2 vs §5.3/§10.1/§12.2 — per-client data inside a shared, FEC-protected object.** §6.2 says each frame carries "the cumulative set of changed tile IDs since the last presentation serial acknowledged by *that client*" and "per-client invalidation state is necessary". §5.3 places that metadata inside the 72-byte-prefixed video object, which is FEC-protected as a whole; §10.1 shares one encoded stream across compatible viewers and §12.2 shares payload slabs across transports. Per-client metadata inside the object means per-client objects and per-client FEC, i.e. no sharing — a contradiction that M2's golden layouts would freeze. Fix: the prefix already carries `damage_serial` and `invalidation_baseline_serial` (offsets 64/68); keep only those in the object. Send the cumulative tile-ID/generation lists as a reliable `TileInvalidate` record on the refinement stream (keyed by damage serial, retired by `PresentedDamageAck`). Rule 4 (baseline newer than applied serial ⇒ clear all + snapshot) still works unchanged.

**B2 · §5.2 epoch tags vs §4.4 lease revocation — forced reconnect after 255 lease generations.** §5.2: a codec/display/**input-lease**/audio change creates a fresh `(slot, epoch_tag)` binding, spent tags are never reused within a QUIC connection, and "before 255 bindings for that slot are exhausted, perform the authenticated reconnect". §4.4: focus loss, window close, handoff, denied permission and local override each "revoke the generation". A normal workday of alt-tabbing exhausts the input slot's tags and forces a full reconnect (new session epoch, re-prime, flushed audio). Fix: bind each lease generation to a start packet sequence in `StreamContext`; reject input datagrams whose extended `packet_seq` precedes the current binding's start (the 32-bit extension already exists). Then tags rotate only for codec/display/audio contexts, and the full lease generation lives in the reliable journal plus, if wanted, 2 bytes of the input body.

**B3 · §12.1 + "What to build first" Task 5 — Swift bridges break the owner's dev loop.** §12.1 chooses Swift for SCK/CoreAudio/AppKit lifecycle bridges. The workspace today is Rust-only FFI (`block2`, `core-foundation`; no `objc2`, no Swift), and the development box is a Linux VM whose macOS type-check uses a Zig C wrapper (`cargo check --target aarch64-apple-darwin`), which cannot compile Swift. A `build.rs`/SwiftPM step puts SCK — Task 5, weeks 4–6 — outside what agents can even type-check. Fix: implement SCK/CoreAudio in Rust via `objc2-screen-capture-kit`/`objc2-core-media` (same lineage as `block2` already in use); confine Swift to the SwiftUI shell app built by Xcode on the Macs; state in §12.1 that the cargo workspace stays Swift-free.

**B4 · "What to build first" Task 2 (weeks 1–2) — authentication and the iroh migration at once.** Task 2 bundles device keys, grants, bounded handshake, *and* a "direct-address iroh adapter" plus Noq pinning and SPAKE2 selection into weeks 1–2 alongside Task 1. iroh drags in `noq` 1.3.0 (a Quinn fork) next to the workspace's `quinn` 0.11; both use rustls 0.23 so coexistence is feasible, but that is unverified and it doubles the transport surface exactly when the security invariants are being introduced. Fix: weeks 1–2 = Ed25519 device key + pinned-key rustls verifier on the *existing* Quinn transport + host-local grants + `connect_insecure` removal. That is the "direct upstream-Quinn seam" for free, and iroh's `SecretKey` is Ed25519 so no identity migration later. The iroh adapter becomes the probe lane in weeks 3–6 (verify quinn/noq coexistence, #4390/#4476 cases). D-01 is untouched; only order changes.

**B5 · §8.2/§14.2 — the SPAKE2 requirement may be unsatisfiable as written.** The plan mandates "RFC 9382's P-256/SHA-256/HKDF/HMAC suite … from a maintained reviewed implementation" and makes short-code pairing *required* for product pairing at M3. To my knowledge no widely used Rust crate implements that exact suite; the established `spake2` crate (magic-wormhole lineage) uses the Ed25519 group and its own construction (verify during the M0 selection task). The plan's fallback (stay private) means M3 cannot close. Fix: require "a reviewed, established PAKE crate with key confirmation and transcript binding" and name acceptable candidates (`spake2` Ed25519-group; a reviewed CPace crate), dropping the P-256 stipulation. Security comes from the reviewed PAKE + transcript + host grants, not from the curve.

**B6 · Small inconsistencies to correct.** (a) §13.2 M4 exit "≥500 attempts" vs §11.5 "≥1,000 automated attempts for an initial gate". (b) §5.2's 1,180-byte ceiling: with `initial_mtu=1200` (§5.8) Quinn's max datagram is ≈1,170; the `D_max=min(...)` formula copes, but say so to avoid an agent hard-coding 1,180. (c) `sunna-cli/main.rs:95` → `:103`/`:157`. (d) §11.4 assumes "a dedicated Linux bridge/router … between the actual Macs"; the owner's Linux VM is a GCP instance (kernel `6.8.0-gcp`), which cannot bridge a LAN. Name the actual M2–M3 shaping tool: macOS `dnctl`/`pfctl` dummynet on one Air (endpoint shaping, caveats noted) or the VM as a UDP forwarder with netem (adds real internet RTT).

## 3. Significant concerns (non-blocking)

- **L60 absolute p50 ≤35 ms is unrealistic on two 60 Hz Air panels (§1.2).** Expected phases alone: host compositor vsync (~8 ms mean) + SCK delivery (~3) + encode (~5) + net (~1) + decode (~3) + client vsync (~8) + scanout to patch (~8) + IPS panel response (~5–15) ≈ 44 ms before USB polling and injection. M1's provisional 40/80 quietly admits this. Keep 35/55 for 120 Hz-class rigs; set the 60 Hz-panel L60 gate at ≈45/70. The relative gates (§1.3) are the real test and are fine.
- **M3 is overloaded (§13.2):** tiles + audio + clipboard + private virtual display + SwiftUI shell + *both* pairing flows + Sparkle/notarization in 5–7 weeks. Move link/QR guest pairing, Sparkle and virtual-display productization to M4 (M4 is the first milestone with guests and a public update channel anyway). M3 = short-code pairing + tiles + audio + text clipboard + input fidelity + shell.
- **Two QUIC backends maintained (§7.1, §14.2).** Restrict the upstream-Quinn lane to `testkit`/simulator/loopback bench; only promote it to a product backend if a concrete iroh blocker survives the spike. As worded it reads like a second shipped transport.
- **Process count (§2.1).** Five process types are right for the end state; say explicitly that through M4 macOS ships two processes (Sunna.app with embedded broker+agent; `sunna-viewer`) and that the supervisor/broker split is an M4+/unattended deliverable. Same for the twenty-crate layout — the caveat exists, but the first-six-weeks table should name which crates actually get created (`identity`, `media`, `metrics`).
- **Encoder depth "1 submitted frame initially" (§2.5).** At native 2560×1664@60 on a warm M1, VT encode can approach the 16.7 ms interval, guaranteeing skips with depth 1. Allow depth 2 from the start under the age bound and measure, rather than requiring proof to raise it.
- **Scope creep at M4:** mDNS + rendezvous + manual discovery "from the first connectivity release", hash-chained signed audit log, cohort rollout. For an alpha of tens of users: JSONL append-only audit, manual channel gating, mDNS in M5+. The owner's own use case is WAN over Tailscale.
- **Lost in the merge from my proposal (honest assessment).** Materially better and worth restoring: F Phase 0 step 1 — a half-day *probe battery on both Airs in week 1* (VT HEVC/H.264 profile+chroma enumeration via `VTCopySupportedPropertyDictionaryForEncoder`, LTR token semantics, `BaseLayerFrameRateFraction`, `DataRateLimits`, `Max/MinAllowedFrameQP`, `CGVirtualDisplay`+SCK on the shipping macOS, clamshell). The final plan defers these to Task 5/M3 (§14.2 "M0–M1"), yet M2's repair design, M3's tile/4:4:4 tier and §3.3's settings all hinge on them; they are cheap and shape the M2 backlog. Also F Phase 0 step 0 "land the working tree" — the plan says "review and preserve" but never says *commit*. Where the adjudication was right against me: my 32-focused-week schedule, auth-last ordering and own-puncher choice; the plan's 18–30 months and auth-first are more honest given the current code.
- **Length.** 284 KB is the reference; the developer will live in "What to build first" and §13. A 2-page operating summary (invariants + current milestone + gates) would help agents more than more prose.
